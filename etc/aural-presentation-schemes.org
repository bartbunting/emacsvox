#+title: Semantic Aural Presentation Schemes
#+author: Emacsvox Contributors
#+date: <2026-07-25 Sat>

* Purpose

Build one semantic aural-presentation system for Emacsvox.

Speech labels, voice changes, auditory icons, pauses, ordering, and spatial
placement are alternative and composable ways to present meaning.  Modules
should describe what an object, state, or event means; a user-selected scheme
should decide how that meaning is rendered.

For example, an Org heading may be presented with any combination of:

- a distinct voice for its level;
- spoken text such as "Heading 1" before its contents;
- an auditory icon before or after its contents;
- a pause;
- a stable spatial position;
- a spoken or sounded indication that it is folded.

The system must not force those choices into mutually exclusive "voice",
"speech", or "sound" settings.  It must produce an ordered render plan that can
contain all of them.

This plan supersedes the narrower semantic auditory-icon theme plan.  Auditory
icon themes become resource providers within the broader system, and existing
ACSS personalities become one source of voice styling.  Both remain usable
through a staged, backward-compatible migration.

* Design Summary

The proposed flow is:

#+begin_example
aural object
  +-- semantic facts and source context
  `-- one or more formatting runs
      |
      v
matching scheme rules
      |
      v
backend-independent aural render plan
  +-- object before: speech, cue, pause
  +-- run presentation: speech, cue, pause, voice, and spatial style
  +-- object content: one or more styled speech runs
  `-- object after: speech, cue, pause
      |
      v
backend compilation and queueing
      |
      v
speech and audio services
#+end_example

The central design invariant is:

#+begin_quote
Resolve semantic facts, scheme rules, context, icons, and voice styles while
the source buffer and Emacs state are available.  Queue only a concrete,
ordered render plan.  The speech server must not need to understand modes,
modules, semantic names, schemes, inheritance, or user override precedence.

An aural object is not the same thing as a face or personality run.  Object
feedback such as "Heading 2", a heading cue, and folded state is resolved once
for the heading.  Its contents may contain several formatting runs, each with
its own compatible face-derived or personality-derived voice.  Splitting text
for styling must never repeat the complete semantic presentation.
#+end_quote

* Goals

1. Define a stable semantic vocabulary for aural objects, events, states, and
   their attributes.
2. Let a module express meaning once without choosing whether the user hears
   speech, a voice change, a sound, spatial placement, or a combination.
3. Let schemes compose ordered actions before, during, and after spoken
   content.
4. Give users deterministic global, module, major-mode, derived-mode, and
   buffer-local customization.
5. Preserve ACSS as the device-independent voice description and preserve
   existing face-to-personality behavior during migration.
6. Turn auditory-icon themes into validated resource packs with documented
   semantic intent and fallback.
7. Resolve concrete voice commands and sound resources before queueing them.
8. Provide portable stereo positioning and optional richer spatial audio with
   documented fallback.
9. Make the system discoverable through completion, validation, preview,
   explanation, and an accessible scheme editor.
10. Keep existing one-argument icon calls, =personality= properties, face
    mappings, and bundled sound-pack identifiers working while modules migrate.

* Non-Goals

- Replace the speech server or audio server in the first implementation.
- Rewrite every Emacsvox integration in one change.
- Move or rename the existing =sounds/= tree during the initial migration.
- Redesign the bundled audio samples.
- Make pronunciation, punctuation, capitalization, or language selection part
  of the first rule schema.  The render-plan contract should leave room for
  them, but existing TTS preprocessing remains authoritative initially.
- Require full three-dimensional audio on every backend.
- Require every scheme or sound pack to implement every third-party semantic
  extension.
- Infer module ownership from the Lisp call stack.
- Store arbitrary executable Lisp forms in portable scheme data.

Minor-mode selectors are deferred from the first implementation.  Several
minor modes may be active simultaneously, so they require an explicit ordering
and conflict policy rather than an accidental list order.

* Motivating Org Example

An Org module should be able to expose facts equivalent to:

#+begin_src emacs-lisp
(:role heading
 :level 1
 :visibility folded
 :states (folded))
#+end_src

The presentation context is captured separately:

#+begin_src emacs-lisp
(:module org
 :mode org-mode
 :occasion navigation)
#+end_src

The exact public API and data representation are implementation decisions, but
semantic facts and presentation context must not prescribe a presentation.

One scheme might add rules equivalent to:

#+begin_src emacs-lisp
(:id org-heading-level-1
 :match (:role heading :module org :level 1 :occasion navigation)
 :render
 (:before ((:kind speech :text "Heading 1")
           (:kind cue :name heading-1))
  :content (:voice voice-bolden
            :space (:balance -0.2))))

(:id org-folded-heading
 :match (:role heading :module org :visibility folded)
 :render
 (:after ((:kind speech :text "folded"))))
#+end_src

Another scheme could omit the spoken level, put the cue after the contents,
represent =folded= with a sound, or leave the heading unchanged.  The second
rule demonstrates composition: state presentation is independent of heading
level presentation.

This example establishes requirements rather than committing to these keyword
names:

- selectors can match roles, modules, attributes, and states;
- selectors can require an attribute without fixing its value;
- before and after actions are explicitly ordered;
- safe speech templates can insert guaranteed semantic values;
- content can retain its text while receiving voice and spatial styling;
- independently matched rules can contribute to one render plan;
- a user can replace or suppress each contribution.

** Presentation occasions

The same semantic object may need different presentation when it is reached
through different interactions.  Presentation occasion is context, not part of
the object's identity.

The initial occasions are:

| Occasion       | Meaning                                             |
|----------------+-----------------------------------------------------|
| =navigation=   | Point or focus moved to the object                  |
| =continuous=   | Continuous reading reached the object               |
| =state-change= | An action changed a registered state                 |
| =edit=         | The object was created or changed                    |
| =inspection=   | The user explicitly requested detail or explanation |
| =notification= | An asynchronous event requested user attention      |

For an Org heading:

| Occasion       | Facts retained                    | Additional event context |
|----------------+-----------------------------------+--------------------------|
| =navigation=   | heading, level, folded state      | focus entered            |
| =continuous=   | heading, level, folded state      | continuous reading       |
| =state-change= | heading, level, new folded state  | folding changed          |
| =edit=         | heading, level, folded state      | heading changed          |
| =inspection=   | heading, level, folded state      | explain presentation     |

This distinction lets a user retain level voices during continuous reading
while hearing "Heading 1" or a cue only during navigation.  Modules must use a
registered occasion rather than treating the command name as presentation
semantics.

* Prior Art

** JAWS Speech and Sound Schemes

JAWS Speech and Sound Schemes associate controls, states, document elements,
and text attributes with voices, spoken text, or sounds.  Published examples
include piano notes for heading levels and a deeper voice for bold text.
Schemes can be selected by application.

The useful ideas for Emacsvox are:

- one user-facing scheme spans speech, voices, and sounds;
- rules are based on recognized semantics rather than file names;
- application-specific selection is visible to the user;
- preview is part of editing;
- training mode plays the configured presentation and then identifies the
  underlying semantic object or state.

The published JAWS editor exposes a fixed taxonomy and appears oriented toward
selecting a presentation for each recognized item.  Emacsvox needs an explicit
composition and ordering contract so that a heading can use speech, a voice,
and a cue together and so independent state rules can add presentation.

References:

- [[https://www.freedomscientific.com/SurfsUp/Speech_Sounds_Schemes.htm][JAWS Speech and Sound Schemes]]
- [[https://support.freedomscientific.com/support/technicalsupport/bulletin/513][JAWS scheme configuration by application]]
- [[https://blog.freedomscientific.com/increase-productivity-with-new-sound-features-in-jaws-and-fusion-2022/][JAWS split sound]]

** Aural CSS and CSS Speech

The CSS2 aural style model combines voice properties, =cue-before=,
=cue-after=, pauses, and spatial azimuth and elevation.  Its examples style
headings with both a voice and a preceding cue.  The CSS Speech module retains
voice styling, pauses, and cues and defines a portable stereo =voice-balance=
property.

Emacsvox already uses ACSS concepts for device-independent voice definitions.
The proposed system extends that architectural idea from voice alone to an
ordered aural presentation.

References:

- [[https://www.w3.org/TR/CSS2/aural.html][CSS2 Aural Style Sheets]]
- [[https://www.w3.org/TR/css-speech-1/][CSS Speech Module Level 1]]

* Current Architecture

** Voice and personality

=lisp/voice-setup.el= defines ACSS with the dimensions =family=,
=average-pitch=, =pitch-range=, =stress=, and =richness=.  =defvoice= creates a
named personality and customizable ACSS settings.  Engine adapters translate
the ACSS values into device-specific voice commands.

Text can carry a =personality= property.  If it does not, =tts-get-style= maps
its =face= property through =voice-setup-face-voice-table=.  Explicit
=personality= therefore takes precedence over face-derived voice styling.
=tts-audio-format= identifies style runs and queues the corresponding voice
commands and text.

This is already a useful separation:

- a face or module selects a semantic personality;
- ACSS describes it without depending on one TTS engine;
- an engine adapter generates concrete commands.

The missing pieces are a common semantic registry, contextual scheme rules,
ordered non-speech actions, spatial styling, and an explanation of why a voice
was selected.

** Auditory icons

=lisp/emacsvox-sounds.el= maps an icon symbol such as =open-object= to an Ogg
file in the selected directory.  =emacsvox-icon= either invokes a local player
or sends the resolved resource to the speech server.

The current cache is populated from =sounds/prompts/= and then the selected
sound pack.  Bundled packs live below =sounds/packs/=.  Unknown names silently
use =button=.  Theme selection knows the built-in names =chimes= and =3d=.

** Queued properties

=tts-audio-format= handles an =auditory-icon= property at the beginning of a
text run separately from =personality=.  It queues the icon and then formats
the text and voice.  This supplies only an implicit "before" ordering and
cannot express an after cue or spoken state annotation.

=tts-speak= copies text and its properties into = *tts-scratch-buffer* =.  It
captures the source =major-mode= in =orig-mode= for limited preprocessing but
does not make the scratch buffer use that mode.  Future mode-, module-, and
buffer-specific scheme resolution must therefore happen before the source
context is lost, or the required context must be captured explicitly with the
semantic annotation.

** Spatial audio

The =sounds/packs/3d/= sound pack contains Csound-generated HRTF assets.
Several source files under =sounds/packs/3d/src/= use azimuth, elevation,
panning, or movement.  =etc/pipewire/= also contains experiments with HRTF
virtual devices and left/right or upper/lower speech routing.

Spatial behavior is currently baked into assets or output devices.  It is not
a semantic property that a scheme can apply independently to a cue or speech.

* Terminology

** Semantic fact

A registered statement about meaning.  Examples include =:role heading=,
=:level 1=, =:state folded=, =:event open-object=, and =:severity warning=.

** Aural object

Content with an identity and lifecycle that may be rendered before, during,
and after its spoken text.  A heading is an aural object.

** Event

A semantic occurrence such as opening an object, completing a task, reaching a
boundary, or receiving mail.  An event may have associated content but need
not correspond to a persistent text range.

** State

A fact that qualifies an object or event, such as =folded=, =checked=,
=selected=, or =unavailable=.

** Presentation occasion

Context describing why an object or event is being rendered, such as
=navigation=, =continuous=, =state-change=, =edit=, =inspection=, or
=notification=.  Occasion affects rule matching but does not change semantic
identity.

** Scheme

A named, versioned collection of declarative rules plus references to resource
packs and voice palettes.  A scheme may inherit from another scheme.

** Rule

A selector and presentation contribution.  A selector matches semantic facts
and context.  Its contribution adds, changes, reorders, replaces, or suppresses
parts of a render plan.

** Render phase

One of =before=, =content=, and =after=.  Phases make order explicit without
requiring modules to coordinate separate speech and sound calls.

** Render action

A backend-independent instruction such as:

- speak literal text;
- speak the object's content;
- apply a voice or ACSS style;
- play a semantic cue;
- insert a pause;
- apply volume or spatial placement.

** Formatting run

A contiguous part of an aural object's content whose source presentation
hints are unchanged.  Explicit =personality=, named =face= and
=font-lock-face= values, and source overlay faces may create formatting-run
boundaries.  A formatting run is not a semantic object and must not by itself
repeat object-level labels, cues, pauses, or state feedback.

** Action anchor

The lifecycle point at which an ordered action is emitted.  Object-anchored
actions occur once before or after the complete aural object.  Run-anchored
actions follow a matching formatting run.  Transition-anchored actions occur
only when entering or leaving a matching run presentation.  Slice 26 must
finalize the declarative syntax, defaults, and compatibility inference for
these anchors before changing transport behavior.

** Render plan

The ordered, fully merged result of semantic and scheme resolution.  It still
uses backend-independent voice and spatial values, but contains no unresolved
scheme rules.

** Concrete queue plan

The render plan after backend compilation.  Cue names have become file paths
or sample identifiers, voices have become supported engine settings or
commands, and spatial values have been reduced to backend capabilities.

** Sound pack

A named collection of concrete assets implementing registered cue names.
=3d=, =chimes=, and personal collections such as =bart= are sound packs.
An earcon is one asset within a pack.  “Aural presentation scheme” is reserved
for the semantic rules that select cues, voices, wording, and spatial intent;
it does not name a directory of sound files.

** Module resource overlay

A module-owned collection of portable default earcons plus themed overrides
supplied by the selected sound pack.  The overlay registers one owner and may
contain only cue identifiers owned by that module.  It augments a sound pack;
it never selects or replaces the user's pack.

** Voice palette

A named collection of device-independent voice styles.  Existing ACSS
personalities provide the initial palette.

* Semantic Contract

** Registry entries

The semantic registry is the authority for documentation, completion,
validation, and development-time auditing.  It should describe:

- a stable identifier;
- whether the entry is an object role, event, state, or attribute;
- concise user-facing intent;
- owning module for extensions;
- valid attributes and value types;
- valid states;
- lifecycle or allowed render phases where relevant;
- semantic fallback;
- optional default presentation;
- usage guidance and examples.

Semantic identifiers must not encode a chosen modality.  For example,
=open-object= can remain a useful event name, but a new identifier should not
be called =play-open-sound=.

Core names should express reusable interaction semantics.  A module registers
an extension only when no core meaning is suitable.  Extension registrations
must document an owner and a core fallback where one exists.

The registry owner defines each property's intent, value type, and allowed
values.  Modules capture those facts; schemes and feature fragments only
choose their presentation.  For example, core owns =visibility= with
=folded= and =expanded= values, and the Org integration reports the current
value.  A random rule cannot invent a property merely by using a new keyword.

Registration collisions, invalid attributes, unknown states, and fallback
cycles must be diagnosed.  Development checks should reject new unregistered
literal semantics in the repository.

** Module contract

A module may:

- annotate a text range with registered facts;
- present a registered event with optional content;
- provide default rules scoped to its own semantics;
- register module-specific roles, states, attributes, or events;
- register stable module-owned cue intent with a generic fallback;
- distribute an owner-scoped default resource overlay.

A module must not:

- choose or play a sound filename at the presentation call site;
- assume a bundled sound pack;
- infer that a semantic event will necessarily be a sound;
- depend on a particular TTS engine;
- hide undocumented meaning inside a newly invented cue name.

The emitting module supplies module context explicitly.  The resolver obtains
the source buffer and major mode directly while they are available.  Context
must not be guessed from the call stack.

* Scheme and Rule Contract

** Selectors

The first implementation must support selectors over:

- semantic role or event;
- state;
- registered attributes and values;
- module;
- presentation occasion;
- exact major mode;
- derived major-mode ancestry;
- current buffer through a buffer-local rule layer.

Selectors may combine axes.  For example, a rule can target folded Org
headings without affecting headings rendered by another module.

Minor modes, window context, frame context, and workspace/project context may
be added after their ordering semantics are specified.

** Contributions and composition

Rules contribute to =before=, =content=, or =after=.  The merge contract must
distinguish scalar style properties from ordered action sequences.

Recommended initial behavior:

- scalar values such as voice, balance, volume, and speaking state use the
  most specific winning value;
- ordered actions compose in deterministic rule order;
- a rule can explicitly prepend, append, replace, remove, or suppress an
  action or phase;
- semantic identity is never changed by a presentation rule;
- silence can target a cue, speech annotation, content speech, a phase, or the
  complete presentation;
- duplicate suppression is based on stable action identifiers, not coincident
  text or file names.

The final data syntax and merge operators must be agreed and tested before
runtime integration.  Plain "last writer wins" is not sufficient because
independent rules such as heading level and folded state must compose.

** Cascade

Origin and selector specificity are separate concerns.  The implemented
origin layers, from strongest to weakest, are:

1. current-buffer overrides;
2. temporary session overrides;
3. persistent personal user rules;
4. ordered enabled feature fragments;
5. active scheme rules;
6. module-provided defaults;
7. core fallbacks.

Exactly one base scheme is active.  Feature fragments are independent
rules-only additions that can be enabled and disabled without changing the
base scheme.  Their explicit enabled order runs from weaker to stronger.
They cannot inherit schemes or select a resource pack or voice palette.
This lets one fragment append a cue while another appends speech, preserving
the base scheme's inherited presentation.  Persistent personal rules remain
stronger than every fragment.

A scheme is therefore a global base recipe, not a mode hook or a complete
snapshot of all current presentation settings.  It contains named rules and
may choose default resource-pack and voice-palette providers.  Core,
integration, and third-party provider libraries may register read-only
built-in schemes; personal data may register editable personal schemes.
Activating a scheme is always explicit.  Entering a mode does not select a
scheme bearing that mode's name.  Every presentation resolution consults the
active scheme, but only matching selectors contribute.  Applying a saved
profile may explicitly select the scheme recorded by that profile.  The
integration's automatic compatibility fragment continues to supply its
defaults, and module selectors decide which scheme, option, or override rules
apply there.

There are two deliberately different fragment concepts:

- a module compatibility fragment is an automatic, read-only default that
  preserves an integration's established presentation;
- an optional feature fragment is exposed to users as a *presentation
  option*.  Core, an integration module, a third-party extension, or personal
  data may provide one.

Every presentation option has a collection, such as =org=, =mail=,
=agent-shell=, or =personal=.  The collection is navigation metadata: it
groups related options in the manager but does not affect matching,
specificity, or precedence.  An integration may use its own collection, while
an option shared by several integrations may use a broader collection such
as =mail=.

Providers may also register curated, data-only preview examples for individual
option rules.  Each example names its option and rule and supplies a short
summary, semantic facts, and source context.  Registration normalizes the
input and rejects an example unless the named rule actually matches it.
Examples are runtime metadata rather than persistent personal configuration;
they cannot execute code or change the cascade.  Rules without a curated
example receive a selector-derived simulation automatically, so every enabled
rule remains previewable.

Data-only integration providers use the flat library name
=emacsvox-aural-provider-SCOPE.el=.  They may register semantics, schemes,
module compatibility fragments, presentation options, and preview examples,
but must not load the external package, inspect live buffers, install package
hooks or advice, or produce speech directly.  The corresponding
=emacsvox-SCOPE.el= integration owns those runtime responsibilities and
requires its provider.  Shared domains use a descriptive scope such as
=workflows= rather than pretending that reusable mail, filesystem, version
control, programming, or completion semantics belong to one integration.

Presentation-option order is stored independently from enablement.  The
stable order contains disabled options as well as enabled ones.  Disabling
and later re-enabling an option therefore restores its former precedence
instead of moving it to the strongest end.  Only an explicit reorder in the
active-order view changes precedence.

Within one layer, the resolver orders rules by documented selector
specificity:

1. combined module, exact mode, semantic identity, attributes, and states;
2. exact major mode;
3. nearest matching derived-mode ancestor;
4. module;
5. semantic identity, attributes, and states without context;
6. layer-wide defaults.

Additional selector fields increase specificity only according to a documented
comparison; registration order must not accidentally change behavior.  A
stable explicit rule order breaks genuine ties and is visible in the editor.

** Resolved rule representation and specificity

Schemes use safe, versioned keyword plists for persistence and interchange.
The pure resolver compiles them into validated internal structures.  Module
defaults are read-only scheme fragments in the same declarative format.

Schema version 1 rules accept optional =:enabled nil= or =:enabled t=, with
omission meaning enabled.  Disabled rules remain in scheme data, retain their
stable identifiers, and are fully validated, but do not match, contribute
actions, or add resource requirements.  Identifier uniqueness includes
disabled rules so disabling cannot hide an ambiguity that reappears later.

=content= is a distinguished scalar-style phase.  =before= and =after= contain
ordered actions.  Scalar values use the strongest matching contribution.
Sequences append by default and support explicit =prepend=, =append=,
=replace=, =remove=, and =suppress= operations.  Actions have stable
identifiers so inherited contributions can be removed without comparing text
or filenames.

A selector may use =:requires (level)= when an attribute must be present but
its value should remain dynamic.  Speech actions accept either literal
=:text= or safe =:text-template= data such as ="Heading {level}"=.  Template
fields are limited to =role= and registered attributes, and the selector must
guarantee each field through an exact match or =:requires=.  Templates perform
substitution only; arbitrary Lisp cannot run.  Emacs renders them to concrete
text at the source boundary before anything is queued.

Rules are applied from weakest to strongest using a fixed vector:

1. origin layer;
2. matched semantic identity;
3. combined module and exact mode;
4. exact mode or nearest derived-mode ancestor;
5. module;
6. matched states, attributes, and compatibility hints;
7. parent-to-child order within an inherited origin;
8. explicit visible rule order;
9. stable rule identifier for a genuine tie.

This makes resolution independent of hash-table and registration order.  The
resolved plan retains the matching rule identifiers, score vectors, action
sources, and scalar-property provenance.

** Storage and versioning

Persistent scheme data must:

- carry a schema version;
- have stable scheme and rule identifiers;
- be readable without evaluating arbitrary code;
- preserve comments or user-facing descriptions where practical;
- support validation without selecting the scheme;
- support inheritance without mutating the parent;
- provide explicit migrations when the schema changes.

The native representation may be declarative Lisp data.  Import/export can use
another safe format later, but the semantic and merge contracts must not
depend on the serialization.

The initial persistent implementation uses the data-only file
=~/.emacsvox/aural-schemes.el=, configurable as
=emacsvox-aural-schemes-file=.  The Emacs Lisp reader rejects evaluation
syntax; the loader accepts one validated data form, saves through a mode-0600
temporary file and atomic rename, and retains the previous file as =~=.  User
data and individual schemes are independently versioned; migration functions
must explicitly advance an older version.  Invalid replacement data is fully
staged and validated before it can replace the live personal registry.

Personal data schema version 6 stores named presentation profiles and the
single selected profile identity alongside
personal presentation-option definitions, their stable order, their ordered
enabled identifiers, voice palettes, schemes, and persistent rules.  Versions
1 through 5 migrate automatically.  The version 4 migration derives stable
order from the former enabled order, followed by disabled personal options,
so toggling no longer changes precedence.  The version 5 migration adds an
initially empty =:active-profile= reference.

=emacsvox-aural-active-scheme= is a Customize option.  Startup loads the
personal data, validates scheme inheritance and providers, and selects the
active scheme's inherited resource pack.

* Voice Integration

ACSS remains the device-independent voice layer.  The first implementation
should not replace =defvoice=, engine-specific voice adapters, or existing
=personality= text properties.

The renderer should accept:

- a named existing personality;
- a named voice-palette entry;
- an ACSS style or partial ACSS override;
- the default voice;
- =inaudible= where content suppression is intended.

Compatibility rules:

1. Text with no registered semantic annotation follows the current
   =personality=, then face-to-personality behavior.
2. Existing =personality= values become legacy presentation hints when the
   text also has semantic facts.
3. A user rule can deliberately override a legacy personality for matching
   semantics.
4. Face mappings remain a fallback source of presentation; visual face names
   do not become the canonical semantic vocabulary.
5. Backend compilation uses existing ACSS-to-engine adapters wherever
   possible.

The pure resolver should output a named or ACSS voice style.  The TTS adapter
then converts it to concrete engine commands before queueing.  This keeps
engine codes out of schemes while keeping the speech server simple.

* Cue and Resource Integration

The registry distinguishes a semantic cue from its concrete asset.  A resource
pack maps registered cue names to files and declares:

- name, version, summary, and optional parent;
- file or sample mapping;
- supported cues;
- required and optional coverage;
- format, channels, and duration where known;
- whether an asset is position-neutral, stereo, or already spatialized;
- fixed position or trajectory metadata for pre-spatialized assets;
- semantic fallback and aliases.

The default mapping may remain =CUE.ogg=.

** Sound-pack storage and discovery

Repository-owned resources have distinct roles:

#+begin_example
sounds/
├── packs/
│   ├── 3d/
│   └── chimes/
├── modules/
│   └── OWNER/
└── prompts/
#+end_example

=sounds/packs/= contains bundled sound packs.  =sounds/modules/= contains
portable defaults owned by mode integrations.  =sounds/prompts/= contains
theme-independent prompts.  Unrelated sound resources, such as the speaking
clock, may retain their own named directory and are not sound packs.

Personal sound packs do not normally live in the source tree.  Their canonical
root is configurable with
=emacsvox-aural-personal-sound-packs-directory= and defaults to:

#+begin_example
~/.emacsvox/sounds/packs/PACK/
#+end_example

For example, Bart's complete personal pack is
=~/.emacsvox/sounds/packs/bart/=.  Keeping personal assets outside the checkout
avoids dirty worktrees, accidental commits, and upgrade conflicts.  A separate
version-controlled repository may be used for that directory.

An immediate child of a discovery root is dynamically registered when it
contains =button.ogg=.  A partial pack can opt in with a data-only
=emacsvox-sound-pack.el= manifest:

#+begin_src emacs-lisp
(:schema-version 1
 :summary "Personal overlay"
 :parent chimes
 :profiles nil
 :default-spatialization neutral)
#+end_src

The identifier comes from the directory name.  The optional manifest may set
=:summary=, =:parent=, =:profiles=, and =:default-spatialization=; it cannot
run code because reader evaluation is disabled.  A pack with all 55 legacy
cues automatically claims =legacy-complete=.

Explicit registrations for =prompts=, =chimes=, and =3d= remain authoritative.
Other duplicate identifiers use discovery-root precedence:

1. =~/.emacsvox/sounds/packs/=, or its configured replacement;
2. =sounds/packs/=;
3. direct =sounds/PACK/= children as a deprecated compatibility source.

The compatibility root keeps existing installations working during migration.
New personal packs must use the personal root.  If the same personal identifier
exists in both locations, the canonical personal copy wins; removing it makes
the compatibility copy visible again.

Discovery synchronizes when completion or theme selection asks for available
packs.  It adds new directories, reloads manifests, and removes registrations
for directories that have gone away.  The explicit command
=emacsvox-aural-refresh-discovered-resource-packs= is available when immediate
refresh is useful.  One synchronization stages and validates the complete
replacement registry before publishing a single pack-change notification.  A
failed synchronization publishes nothing.  If a removed directory supplied
the selected pack, the live sound cache moves silently to the active scheme's
registered pack, then to =chimes= when necessary, so semantic and legacy cue
paths cannot disagree.

** Module-distributed earcons

A mode integration may register one resource overlay for its semantic owner:

#+begin_src emacs-lisp
(emacsvox-aural-register-resource-overlay
 'notmuch-earcons
 :summary "Notmuch-specific earcons"
 :owner 'notmuch
 :directory
 (expand-file-name "modules/notmuch" emacsvox-sounds-dir)
 :default-spatialization 'neutral)
#+end_src

The module registers every cue before registering the overlay.  Cue filenames
are =CUE.ogg= and must belong to the overlay owner.  Unknown or foreign files
in a packaged default are registration errors.  A second overlay for the same
owner is rejected so package load order cannot change resolution.

Built-in portable defaults live below:

#+begin_example
sounds/modules/OWNER/CUE.ogg
#+end_example

An external package uses the same flat cue directory inside its own package
tree and registers that absolute directory.  It does not copy files into the
Emacsvox installation.

Sound packs may theme module earcons without duplicating module registration.
The path is relative to the concrete pack directory:

#+begin_example
PACK-DIRECTORY/OWNER/CUE.ogg
#+end_example

For example, Bart's personal Notmuch override is
=~/.emacsvox/sounds/packs/bart/notmuch/notmuch-attachment.ogg=.  A bundled
Notmuch override in the =3d= pack would live below
=sounds/packs/3d/notmuch/=.  Within each inherited pack layer, the owner
subdirectory is stronger than the flat pack directory.  A child pack remains
stronger than its parent.  Complete resolution is:

1. the selected pack and its parents, including owner-subdirectory overrides;
2. the module's packaged default;
3. the cue's registered fallback, resolved again through the same layers.

This order lets a user pack provide a themed version, lets a mode work out of
the box, and retains a coherent generic cue when no additional asset exists.
=emacsvox-aural-disabled-resource-overlays= suppresses both the packaged
default and owner-subdirectory overrides for named overlays.  It does not
change the selected sound pack.  Registration, refresh, or enablement changes
refresh the live effective sound cache without playing a notification cue.

Pack validation reports unknown or foreign files below an enabled owner
subdirectory as =OWNER/CUE=.  Concrete-plan compilation still freezes the
resolved file, owning provider's spatialization, and content-addressed sample
identifier before queueing.

Theme selection must build a fresh effective resource cache.  It must not
retain an asset merely because the previous pack supplied it.  Unknown names,
unreadable files, aliases, missing required assets, and fallback cycles must be
diagnosed rather than silently becoming =button=.

A scheme may select a default resource pack and voice palette.  Users may
override either component without changing the scheme's semantic rules.

** Resolved resource-pack completeness

Resource packs use requirement profiles rather than one universal all-or-none
definition of completeness.

- Every standalone sound pack must resolve =button= as its emergency fallback.
- =legacy-complete= contains the 55 cues shared by =chimes= and =3d=.
- Both bundled sound packs satisfy =legacy-complete=.
- =shutdown= is optional: a direct resource wins, otherwise it falls back to
  =close-object=.
- A scheme derives additional required cues from its compiled rules.
- Parent packs may satisfy requirements for focused child packs.
- Partial packs remain valid providers but do not claim profiles they cannot
  satisfy.

All bundled filenames, prompt names, and compatibility aliases have registered
intent.  =emacsvox= falls back to =startup=, =repeat-stop= to =repeat-end=, and
=unmark-object= to =deselect-object=.  The existing 25 ACSS personalities are
exposed through the =acss-default= voice palette.

* Spatial Presentation

Spatial styling belongs to render actions and applies independently to speech
and cues.

The implemented portable level is normalized stereo balance.  =-1.0= is full
left, =0.0= is centre, and =+1.0= is full right.  Scheme data uses either
=(:balance NUMBER)= in that range or listener-relative
=(:azimuth DEGREES)= from =-180= through =+180=.  Positive values are right,
negative values are left, zero degrees is directly in front, and either 180
degree value is directly behind.

Azimuth is currently a portable input rather than a claim of 3D output.  It
reduces to stereo using:

#+begin_example
balance = sin(azimuth in radians)
#+end_example

This preserves front and rear at the centre, maps 90 degrees right to =+1.0=,
and maps 90 degrees left to =-1.0=.  A richer future level may add native:

- elevation;
- distance;
- width or spread;
- a time-varying trajectory.

The coordinate system must be listener-relative and documented.  Backend
capability fallback should be deterministic:

#+begin_example
3D position or trajectory -> stereo balance -> centred mono
#+end_example

Backends report capabilities.  The resolver does not inspect PipeWire, SoX,
Csound, or speech-server details; the backend compiler reduces the requested
style to what is available and records the degradation for explanation.

The concrete compiler reports =stereo=, =mono=, or =centered= independently
for speech, ordered speech-server cues, and standalone local cues.  The
current local SoX adapter implements balance using two-channel =remix=.
Current speech and ordered-cue transports centre requests unless an adapter
installs the corresponding ordered balance function.  A declared mono output
always centres requests.  The concrete plan records requested space, compiled
balance, capability, and every reduction before anything is queued.

Pre-spatialized assets must not be spatialized a second time by default.
Resource metadata must distinguish position-neutral material from assets such
as the current HRTF-generated =3d= sounds.  The compiler obtains this metadata
from the pack that owns the resolved file, including inherited and prompt
resources; a requested balance is not applied to a =pre-spatialized= asset.

Users need independent controls to:

- disable all spatial presentation;
- disable spatial speech while retaining spatial cues;
- reduce the maximum left/right separation;
- remap positions for unilateral hearing or speaker layouts;
- choose a non-spatial speech or cue fallback.

The stable schema uses audible centred output as its non-spatial fallback.
Whether a critical alert may instead be suppressed remains a separate policy
decision.  =emacsvox-aural-spatial-enabled=, the independent speech and cue
toggles, =emacsvox-aural-spatial-maximum-separation=,
=emacsvox-aural-spatial-remapping=, and =emacsvox-aural-spatial-output=
implement the other controls without changing scheme data.

Stable positions are preferable to arbitrary motion because they can convey
source or role without reducing speech intelligibility.  Motion should be an
optional later capability, not a requirement for the first portable contract.

* Resolution and Queueing

Resolution has four stages:

1. Capture registered semantic facts and source context.
2. Match and merge scheme rules into a backend-independent render plan.
3. Resolve cues, voices, pauses, and spatial properties through selected
   resource and backend capabilities.
4. Queue a concrete ordered plan.

Concrete cue files or sample identifiers must be selected before queueing.
The speech server should only receive actions it can execute, such as a voice
command, text, silence duration, concrete sound resource, and supported spatial
parameters.

The queue contract must preserve the order of:

- before actions;
- content speech and its style runs;
- after actions.

If audio and speech use separate processes, the adapter must define whether
actions are strictly serialized, overlapped, or mixed.  A scheme must not rely
on accidental process scheduling.  Concurrent and background actions should
be explicit future action modes.

Immediate event presentation and text-property presentation must use the same
resolver and concrete-plan compiler.  A plain symbol-valued =auditory-icon=
property remains valid and maps through a compatibility adapter.

Context must be captured before =tts-speak= moves text into its scratch
buffer.  The boundary is entry to =tts-speak= or =tts-notify=, before process
initialization, notification logging, or stream switching can change the
current buffer.  Each aural object is resolved there as one immutable
object-level plan containing one or more concretely styled content runs.
Formatting-run boundaries may select compatible face or personality
presentation, but they do not receive duplicate copies of the complete
object-level plan.  Pronunciation, punctuation, capitalization, and Unicode
cleanup may still replace text payloads, but must preserve the frozen object
and run decisions and must not rerun semantic, scheme, resource, or voice
resolution.

All multi-action plans use one ordered speech-server queue.  This includes
spoken annotations, pauses, concrete cues, content speech, and trailing
actions.  The only local-player exception is a compatibility call whose
entire presentation is exactly one standalone cue.  A scheme cannot split one
ordered presentation across independently scheduled local and server
processes.

Pulse/PipeWire samples use readable content-addressed identifiers of the form
=emacsvox-PACK-CUE-DIGEST=.  Emacsvox records only identifiers it successfully
uploaded, unloads obsolete owned samples when the selected pack changes, and
releases remaining owned samples at exit.  It never unloads samples owned by
another application.

=emacsvox-set-aural-scheme=, =emacsvox-reset-aural-scheme=,
=emacsvox-copy-aural-scheme=, =emacsvox-delete-aural-scheme=,
=emacsvox-rename-aural-scheme=, and =emacsvox-reset-aural-overrides= provide
the lifecycle operations.  Scheme copying creates an editable inheriting
child by default; a prefix argument creates a flattened copy.

The scheme editor should use an accessible Emacs buffer and completion rather
than requiring users to edit raw data.  Its workflow should be:

1. choose the semantic object, event, state, or current item;
2. narrow its context and attributes;
3. add and order before, content, and after actions;
4. select voice, speech, cue, pause, and spatial settings;
5. preview;
6. inspect conflicts and effective fallback;
7. save to the desired scope.

Customize may expose simple settings, but a dedicated editor is needed for
ordered actions, inheritance, rule explanations, and previews.

Add a training mode inspired by JAWS.  It should perform the normal
presentation and then speak a concise semantic explanation.  A more detailed
command should identify every matched rule and why it won or composed.

The implemented =emacsvox-aural-training-mode= adds its concise semantic
identification after the concrete plan, including after a standalone cue
played through a local adapter.  It queues concrete explanatory text directly
and never recursively invokes semantic resolution.  During an interactive
command, explanations are retained until =post-command-hook= so an
icon-then-speech sequence cannot flush the icon's explanation before it is
heard.  The explanation names the concrete earcon that survived rule
composition, rather than a legacy cue that may have been replaced or
suppressed.  Training narration uses the palette-aware
=emacsvox-aural-training-voice=, which defaults to =annotate=, and returns to
the default voice afterward.  Detailed inspection uses
=emacsvox-explain-aural-presentation=.

** Accessible aural-home contract

=emacsvox-aural= is the stable discovery and interaction entry point.
=C-e H= opens it from any ordinary buffer and remembers that buffer as the
source for contextual explanation and buffer-local editing.  The first row is
=Explain at point=; =C-e E= invokes the same
=emacsvox-aural-explain-presentation= diagnosis directly from an ordinary
buffer.  The next row is =Remap voice at point=; =r= invokes it from anywhere
in the home.  =Remap earcon at point= follows it; =R= invokes that workflow.
The fourth row is =Recent aural feedback=; =H= opens the exact presentation
history without changing the remembered source.

The normal point-remapping workflow is:

1. move to the object whose voice should change;
2. press =C-e H= and then =r=;
3. choose a voice from the active palette;
4. choose personal, session, or current-buffer lifetime;
5. review the generated rule and press =s= to save it.

For example, on a Dired directory this derives =filesystem-entry=,
=entry-kind directory=, and =module dired=.  It does not retain the
=focus-entered= movement event or the navigation occasion, so the voice
follows Dired directories rather than one arrow-key action.  The resulting
semantic override supersedes the compatibility =dired-directory= face
mapping without changing that global face table.

Earcon remapping starts from the exact concrete plan last heard at point, or
from a selected recent-feedback record.  It distinguishes each cue by before
or after phase, action identifier, and source rule when a presentation has
several.  The selected concrete file is auditioned in isolation before the
user chooses to replace or suppress that action, or to remove a prior
generated override and restore inherited behavior.  A replacement is also
auditioned through the active sound pack before its unsaved rule opens.
Generated rules remove only the chosen action identifier at its frozen
object, run, or transition anchor; they do not copy the rest of the phase.
If separate contributions reuse the same action identifier in that phase and
anchor, the wizard refuses the ambiguous removal instead of changing both.
Unlike object-wide voice remaps, earcon selectors retain the exact semantic
event and occasion so a state-change sound cannot leak into routine
navigation.  The replacement preserves any requested volume and spatial
placement from the original action.  Personal, session, and live-buffer
scopes use stable generated identifiers, allowing a later =Restore inherited
behavior= operation to prepare the corresponding rule deletion for review.

The recent-feedback browser displays exact spoken content, semantic object,
source name, occasion, voice request, ordered earcons, degradation or semantic
fallback status, and queue time.  =RET= or =e= explains the frozen plan, =P=
replays its complete before/content/after sequence, =c= directly auditions
only its concrete earcons without speech or history, =r= starts the same
review-before-save voice-remapping workflow from the selected record, and
=R= remaps one of that record's exact earcons.  A historical record never
retains a source buffer.  Buffer-local persistence is therefore offered only
when the browser remains attached to a live source whose name matches the
record; personal and session remaps remain available after the source closes.

Presentations originating in registered Aural interface buffers are excluded
from history by default, so opening, closing, navigating, previewing, and
speaking manager state cannot displace source-buffer feedback.  The exclusion
is frozen into the presentation context before text reaches the speech
scratch buffer.  Set
=emacsvox-aural-history-record-interface-presentations= non-nil, or press =i=
in Recent Aural Feedback, to include those presentations temporarily while
diagnosing the Aural UI.  The toggle's own announcement is always excluded.
=L= changes =emacsvox-aural-presentation-history-limit= for the current Emacs
session and immediately trims excess oldest records.  The limit accepts any
natural number; larger values retain proportionally more frozen spoken text
in memory.  Customize the variable to persist a larger value, or use zero to
disable and clear history.

The home is a status-and-routing view rather than another editor.  Its rows
lead to:

| Row                  | Destination or operation                              |
|----------------------+-------------------------------------------------------|
| Explain at point     | Spoken and detailed presentation provenance           |
| Remap voice at point | Prepare a scoped named-voice override for the item     |
| Remap earcon at point | Replace, suppress, or restore one exact cue action    |
| Presentation overrides | Unified personal, session, and buffer rule manager  |
| Recent aural feedback | Exact heard-output browser and replay                 |
| Schemes              | Base-scheme manager                                    |
| Presentation options | Grouped, independently enabled presentation layers    |
| Current buffer rules | Advanced editor scoped to the remembered source       |
| Semantic vocabulary  | Registered roles, events, states, and attributes       |
| Sound packs          | Spoken pack manager and cue-provenance browser          |
| Spatial capabilities | Current backend support and fallback                   |
| Spatial settings     | =emacsvox-aural-spatial= Customize group               |
| Training mode        | Concise semantic-identification toggle                 |
| Diagnostics          | Active-scheme validation                               |

=n=, =p=, Up, and Down move by row.  Left and Right move by column and speak
the column title and value.  =.= repeats the titled cell, =SPC= speaks the
complete row, =RET= performs its primary operation, =x= always explains the
remembered source, =r= prepares a point voice remap, =R= prepares a precise
earcon remap, =O= opens presentation overrides, =H= opens recent feedback,
and =?= displays and speaks help.
Top, bottom, first
column, and last column boundaries are announced instead of silently
repeating a value.  Every routed aural manager and editor binds =h= to return
home without losing the remembered source.  Every aural manager, browser, and
editor binds =q= to a shared semantic dismissal command that presents
=close-object= and speaks the destination mode line.  Editors retain their
unsaved-change confirmation before that dismissal feedback.
Every Aural manager, browser, preview, doctor, and editor also presents the
scheme-resolved =open-object= cue with semantic event
=aural-interface-opened= after it becomes current.

speech/voice/position, and after feedback.  Common label, cue, ordering, and
left/centre/right placement choices use natural prompts.  A clearly labelled
advanced-details field appears for legacy selectors, phase merge/removal,
pauses, per-action voice/volume, or advanced content styling.

=emacsvox-edit-aural-scheme-advanced= opens the complete
=emacsvox-aural-scheme-editor-mode= rule view.
=emacsvox-edit-aural-rules= uses the same advanced view for a persistent
personal, temporary session, source-buffer-local, or explicitly selected
personal-scheme or personal-feature-fragment scope.  Built-in schemes and
fragments remain read-only.

The advanced buffer exposes these stable operations:

| Key                  | Operation                                      |
|----------------------+------------------------------------------------|
| =n=                  | Add a guided rule                              |
| =RET= or =e=         | Edit the complete rule at point                |
| =c=                  | Copy a rule under a new stable identifier      |
| =d=                  | Remove a rule                                  |
| =t=                  | Enable or disable a rule without losing it     |
| =M-up= / =M-down=    | Reorder rules and their explicit visible order |
| =m=                  | Edit scheme inheritance and providers          |
| =p= / =x=            | Preview or explain the unsaved rule            |
| =v= / =s=            | Validate or atomically save/apply               |
| =A=                  | Return to the simple editor                     |
| =h=                  | Return to the aural home                         |
| =?=                  | Describe the completion-driven workflow         |

Selectors are assembled from registered semantic, module, major-mode,
occasion, and compatibility fields.  Before and after phases explicitly
choose append, prepend, replace, remove, suppress, or unchanged behavior and
then build ordered speech, cue, and pause actions.  Content prompts distinguish
unchanged, spoken, silenced, default voice, named voice, and inaudible
presentation.  Guided spatial prompts offer unchanged, centred, normalized
balance, or listener-relative azimuth values and validate them against the
portable contract.  Registered attribute prompts can choose an exact value or
require its presence, and speech prompts can choose literal text or a safe
semantic template.

1. Existing =(emacsvox-icon ICON)= calls remain valid.
2. Existing symbol-valued =auditory-icon= text properties remain valid.
3. Existing =personality= properties and face-to-personality mappings remain
   valid.

5. Existing =chimes=, =3d=, and =prompts= identifiers remain valid; bundled
   pack files move below =sounds/packs/=.
6. Existing player selection remains supported.
7. Unknown legacy icons warn once and fall back during migration; new in-tree
   semantics must be registered.
8. Module context and richer semantics are optional until a module is
   deliberately migrated.
9. No repository-wide mechanical caller rewrite is part of an initial slice.
10. Compatibility adapters are removed only through a separately reviewed
    public API change.

** Deep-Dive Findings after Slice 25

A source and runtime review after the first visual-face slice confirmed that
the semantic architecture is still the correct direction, but found several
contract and implementation gaps that must be corrected before further module
migration:

1. =emacsvox-aural-prepare-text= currently resolves the complete semantic
   before/content/after plan for every personality or face run.  A mixed-face
   Org heading can therefore speak its heading label and play its heading cue
   several times.  Semantic object lifetime and formatting-run lifetime need
   distinct representations.
2. The queued string contains ordinary text properties but not overlay
   properties.  Point explanation can observe an overlay face that actual
   speech never captures.  Current transport also chooses =face= instead of
   =font-lock-face= when both are present and ignores string-valued named
   faces.  A narrow, authoritative named-source-face snapshot is required at
   the source boundary.
3. Existing Voice Lock controls legacy personality derivation, while new face
   rules can still add presentation when Voice Lock is disabled.  The policy
   must be explicit and visible in explanation rather than accidental.
4. Legacy face lists can compile as a sequence of partial ACSS personalities,
   but scheme =:content :voice= is one strongest-wins scalar.  The model needs
   to distinguish a complete voice preset from composable ACSS dimensions.
5. Only the built-in =acss-default= palette is registered.  Users have no
   spoken palette manager, palette-entry provenance, or common persistence
   path for creating and editing device-independent voice styles.
6. Semantic fallback is validated and documented but does not participate in
   matching.  Registered occasions, phases, role attributes, and state
   combinations are not yet enforced as semantic contracts.  Semantic names
   also have no alias, deprecation, or data-migration policy.
7. Fact merging can leave duplicate plist keys, making displayed and resolved
   input disagree about which value is authoritative.
8. Overlay compatibility advice mirrors a resolved overlay voice into one
   scalar text property.  Overlap, priority, removal, and original face
   identity are not preserved reliably.
9. Explanation usually re-resolves current facts and scheme state.  It must
   distinguish simulation from inspection of the exact frozen plan that was
   actually queued.
10. Several aural modules are absent from =lisp/Makefile=, and stale source-tree
    byte-code can shadow newer source during an ordinary interactive startup.
    The isolated compiled test is useful but does not make the normal build
    complete.
11. Rule collection and scheme compilation, voice/resource lookup, and sound
    file digesting are repeated at formatting-run frequency.  Correct object
    boundaries should also provide a safe cache boundary.
12. The current repository audit reports 1,548 literal and 104 dynamic legacy
    presentation references across modules.  Further migration should wait
    until object lifetime, source-face capture, and Voice Lock policy are
    stable.

These findings add corrective slices rather than reopening the completed
vertical migrations.  Compatibility behavior stays supported while the shared
transport and contracts are repaired.

- Runtime spatialization of the existing =3d= assets could position them
  twice.
- Unstable or excessive spatial speech could reduce intelligibility.
- Requiring every scheme to cover every extension would make third-party
  schemes impractical.
- An editor that cannot explain rule provenance would make a powerful cascade
  impossible to debug.
- Migrating every caller at once would obscure semantic review and make
  regressions difficult to isolate.

The staged plan addresses these risks with a registered semantic vocabulary, a
pure and explainable rule engine, concrete pre-queue resolution, capability
fallback, an Org vertical slice, and small subsequent migrations.

* Definition of Done

The migration is complete when:

- registered semantic facts are the documented source of truth;
- modules describe meaning without choosing a modality or file;
- schemes can compose speech, voice, cues, pauses, and spatial style in
  explicit before, content, and after phases;
- users can inspect and override presentation globally and by module, major
  mode, combined context, derived mode, or buffer;
- independent rules such as heading level and folded state compose
  deterministically;
- one semantic object may contain several face or personality runs without
  repeating object-level feedback;
- actual speech and point explanation use the same frozen named-source-face
  snapshot;
- Voice Lock and face-presentation policy are independent, documented, and
  visible;
- existing ACSS personalities and sound packs are providers within the common
  system;
- the concrete render plan is resolved before queueing;
- the speech server contains no scheme, mode, module, or semantic resolution;
- supported backends honor the same ordering, silence, and fallback behavior;
- portable spatial presentation degrades predictably and can be disabled;
- training and explanation commands identify what was presented and why;
- schemes, resource packs, voice palettes, and semantic extensions validate;
- existing icon calls, =personality= properties, face mappings, and bundled
  sound-pack identifiers remain functional through documented compatibility
  adapters;
- the Org vertical slice and representative module migrations pass all
  required test gates;
- public documentation explains authoring, customization, migration, and
  backend capability behavior.
