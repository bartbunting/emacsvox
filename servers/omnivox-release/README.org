#+title: Omnivox Windows Release Contract

* Ownership

Omnivox owns its committed =Cargo.lock=, exact Rust version, and the C# source,
build targets, tests, and GPL notice for its 32-bit Eloquence and DECtalk
helpers.  Emacsvox owns the complete Windows bundle it stages: the pinned
Windows-GNU and helper compiler inputs, invocation and deterministic validation
of those builds, the Omnivox-built RHVoice and Flite companions, runtime DLLs,
eSpeak data, content hashes, and launcher selection.

* Pinned tools

=Dockerfile= uses an official Rust 1.97.1 image by immutable amd64 digest and
an immutable Debian snapshot with exact direct MinGW package versions.  The
image builds both the native eSpeak data source and the Windows executable, so
neither is taken from an arbitrary host compiler.  =toolchain.lock= also pins
the official Roslyn Framework compiler and .NET 4.0 reference-assembly NuGet
packages by version and SHA-256.  They are downloaded into the ignored
=cache/= directory and run through the .NET Framework already present on
Windows; they are neither installed system-wide nor staged with Omnivox.
The same lock pins the official Omnivox 1.5.1 Windows Piper companion by
release URL, archive SHA-256, and source commit.  The preparation target
rejects an Omnivox checkout at another commit before combining the helper with
the Piper-enabled Windows-GNU executable.  Flite's source archive, source tree,
and compiled SLT voice are separately locked and verified by the Omnivox
checkout.
The Windows Rust link disables GNU ld's otherwise variable PE timestamp.
The staged executable is stripped with the pinned MinGW =strip= because GNU
ld emits the remaining COFF symbols in a variable order.  The exact
symbol-bearing executable and a local manifest are retained under the ignored
=cache/diagnostics/= directory; they are never staged or committed.
=SOURCE_DATE_EPOCH=0= also prevents =strip= from adding a new PE timestamp.
The container workspace, Cargo home, and target paths are fixed by the Makefile
because Rust artifacts can retain registry paths; changing those internal paths
changes the executable identity even when the source is identical.

Run =make verify-windows-omnivox-toolchain= to build and validate this
environment.  Deterministic compilation makes identical helper sources and
inputs produce identical executables.  Compiler, reference-assembly, or
framework-baseline updates remain explicit reviewed changes.

* Licensed runtimes

Licensed runtime binaries are never committed to Emacsvox or Omnivox.

- Eloquence's ECI runtime remains user supplied and is not copied into the
  staged bundle.  If =OMNIVOX_ECI_DLL= is visible while staging, its content
  hash is recorded without its private path; otherwise provenance records that
  the external runtime was not observed.
- The DECtalk release archive is downloaded to an ignored directory and must
  match the reviewed SHA-256 supplied to its Makefile by =toolchain.lock=.  Its
  extracted DLL and dictionary hashes are recorded in the staged bundle.
- The open helper executables are rebuilt from Omnivox's committed C# sources
  with the pinned compiler.  They are not treated as opaque runtime inputs,
  and their GPL-2.0-or-later license text is staged beside them.
- The MIT-licensed RHVoice helper is built from the selected Omnivox source.
  RHVoice itself, its language data, and its voices remain user supplied and
  are never copied into this payload.
- The Flite helper and its compiled-in CMU US SLT voice are built from
  Omnivox's checksum-locked Flite 2.2 source input.  Its source provenance,
  complete upstream license, and internal checksums are staged with it.
- Piper's open native companion is a checksum-pinned official Omnivox release
  input.  Its source provenance, internal checksums, helper, DLLs, private
  eSpeak data, and complete staged tree are verified.  Voice models remain
  external user-supplied inputs and are not added to the runtime manifest.

* Staging and verification

=make windows-omnivox= refuses tracked source changes, performs locked builds,
validates and recreates only its literal dedicated generated Cargo target,
builds the RHVoice and Flite companions, creates a content-addressed version
containing the matching Piper companion, and writes =PROVENANCE= and
=SHA256SUMS= beside the payload.  Symlinked or unexpected clean targets are
rejected.  The dependency download cache is retained.  The provenance file
contains source revisions, toolchain and lock identities, artifact hashes, and
the licensed-runtime policy, but no machine-local paths.  It records the
deterministic stripped executable hash; the deliberately non-reproducible
unstripped hash is kept only in its local diagnostics manifest so it cannot
perturb the staged build identity.

Set =OMNIVOX_PIPER_MODEL= to an absolute =.onnx= path when staging a locally
reviewed voice.  Its adjacent configuration is required.  The target copies
both into a separate content-addressed Windows =LocalAppData= cache, records
their hashes, and writes a launcher path pointer.  It does not include either
file in the runtime payload.  Omitting the setting stages Piper support without
registering a Piper engine.

For local testing from active changes, use =make windows-omnivox-dev=.  It uses
the same pinned build and staging path without requiring either worktree to be
clean, labels the result =local-dirty-worktree=, and records SHA-256 hashes of
both repositories' tracked diffs in the runtime provenance and build identity.
It builds RHVoice and Flite, including Flite's SLT voice, but deliberately
omits Piper so a current Omnivox checkout is never combined with the 1.5.1
Piper companion.  It therefore rejects =OMNIVOX_PIPER_MODEL=.  Advance the
Piper lock to a companion built from the same Omnivox commit before using the
clean release path for these integrations.  The development target does not
weaken the clean-worktree requirement of =make windows-omnivox=.

To preserve an external RHVoice installation across fresh Emacsvox processes,
pass =OMNIVOX_RHVOICE_LIBRARY= and =OMNIVOX_RHVOICE_DATA= to
=windows-omnivox-dev=; pass =OMNIVOX_RHVOICE_CONFIG= too when that installation
uses a separate configuration directory.  The target validates WSL or Windows
absolute paths, includes content digests and the recorded path values in the
local build identity, and writes machine-local Windows path pointers beside
the selected repository runtime.  The launcher reads those pointers only when
the corresponding environment variable is unset.  RHVoice itself remains
external and is not added to =SHA256SUMS= or copied into the Windows runtime.

=make verify-windows-omnivox-runtime= verifies the repository stage, build-kind
and worktree-digest agreement with local diagnostics, the Windows-local runtime
copy, the external eSpeak cache digest, and launcher selection through
=servers/omnivox-bin/current=.

Staging changes what a newly launched speech process selects.  An existing
Omnivox process continues running the content-addressed executable with which
it started, so restart Emacsvox, or otherwise start a fresh speech server,
after staging a new runtime.
