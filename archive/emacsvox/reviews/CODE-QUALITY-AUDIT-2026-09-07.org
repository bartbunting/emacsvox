* Assessment

The repository has substantial regression coverage and explicit architecture
and release policies. All existing checks run for this audit passed. The
highest-priority findings are nevertheless concrete: EWW and EPUB paths can
interpret external input as shell syntax. Further defects affect process
cleanup, delayed voice configuration, installation payloads, compiler
selection, and freshness checks. Passing migration and structural checks do
not establish these behaviours.

The most useful sequence is to fix those bounded defects, add behavioural
regressions at their boundaries, then address module organisation. Agent Shell
is the clearest candidate for decomposition. The existing aural refactoring
backlog already identifies several sound improvements; this report supports
that work without presenting its previously fixed defects as new findings.

This report contains 20 items: 15 confirmed code or documentation defects, one
CI coverage gap, and four maintainability concerns. It is a broad audit with
deeper investigation of selected paths, not a line-by-line review of the
entire codebase or certification of every platform and integration.

** Priority and evidence scale

- P1: fix promptly; an ordinary feature can cross an execution boundary.
- P2: a concrete reliability, accessibility, testing, or maintenance problem
  worth scheduling in a bounded task.
- P3: useful documentation or organisation work with lower immediate impact.
- Confirmed: established from an inspected call path and, where practical,
  an isolated reproduction. A confirmed client-side defect does not imply
  that its acoustic or platform-specific impact was tested live.
- Concern: structural evidence supports attention, but no production failure
  is asserted. Hypotheses and acceptance work are identified explicitly.

* Findings requiring attention

** AUD-01 — EWW passes URL contents into shell syntax
:PROPERTIES:
:AUDIT_PRIORITY: P1
:CLASSIFICATION: Confirmed defect
:CONFIDENCE: High
:END:

Evidence: [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-eww.el#L2359][URL command entry point, line 2359]] constructs
=%s '%s'= at [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-eww.el#L2372][line 2372]]. A URL containing an apostrophe closes the
quoted argument. The downloader repeats the pattern and also interpolates an
unquoted directory at [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-eww.el#L2690][lines 2690–2693]]. The URL can come from the
link under point, rather than solely from an explicitly typed shell command.

The isolated probe replaced the chosen command with =:= and supplied a
synthetic URL containing an apostrophe followed by =printf=. Executing the
captured command emitted the marker as a separate shell command. No network
access or document download was involved. Spaces in the download directory
are a separate ordinary failure case.

Impact: invoking these helpers on a crafted link can execute shell commands
with the user's permissions. The existing
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/test/emacsvox-eww-tests.el#L168][EWW advice and URL tests]] cover navigation and dispatch, but do not exercise
these argument boundaries.

Recommendation: pass program arguments through a process API; where the
configured value intentionally remains a shell command, quote the URL with
=shell-quote-argument=. Use =default-directory= for the download directory.
Test apostrophes, spaces, semicolons, dollar signs, and executable paths with
spaces. Verify the destination program receives exactly one literal URL.

** AUD-02 — EPUB mixes raw paths and shell-quoted paths
:PROPERTIES:
:AUDIT_PRIORITY: P1
:CLASSIFICATION: Confirmed defect
:CONFIDENCE: High
:END:

Evidence: [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-epub.el#L219][archive extraction]] and
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-epub.el#L245][TOC]], [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-epub.el#L302][OPF]], and
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-epub.el#L313][archive listing]] interpolate the book filename. Some callers quote it, such
as [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-epub.el#L678][the caller at line 678]], while the Dired branch of
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-epub.el#L850][emacsvox-epub-eww]] supplies a raw filename. That function also constructs
a shell =cd= command from the path at line 875. The representation is further
complicated by [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-epub.el#L366][emacsvox-epub-shell-unquote]], which invokes a shell to
recover a filename.

An isolated call to the real listing helper with a nonexistent synthetic
filename containing a semicolon executed an inert =printf= marker. This
establishes the execution boundary; the Dired caller establishes a route for
unquoted filenames to reach it. Ordinary filenames containing spaces also
depend on which entry point was used.

Recommendation: keep EPUB object paths as raw filenames, use argument-list
process calls, and parse listing output in Lisp. Inventory callers before
changing the path representation; this needs a coordinated small migration,
not a quote added at one random layer. Preserve externally used interfaces
until their compatibility requirements are understood. Add tiny local EPUB
fixtures with spaces, apostrophes, metacharacters, and malformed metadata.

The [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/test/emacsvox-epub-tests.el#L16][focused EPUB test]] checks Locate. The
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/test/emacsvox-reading-dom-tests.el#L90][DOM tests]] replace extraction helpers, so their passing results do not
validate archive execution or argument handling.

** AUD-03 — Scanner acquisition reverses the keep-original option and reports failures as success
:PROPERTIES:
:AUDIT_PRIORITY: P2
:CLASSIFICATION: Confirmed defect
:CONFIDENCE: High
:END:

[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-ocr.el#L199][emacsvox-ocr-keep-uncompressed-image]] promises to retain the uncompressed
image. [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-ocr.el#L425][emacsvox-ocr-scan-image]] instead appends =rm -f temp…= when this
option is true. Its use of a fixed temporary filename also makes concurrent
acquisition fragile. The neighbouring photo path at line 450 treats the keep
option in the expected direction.

The scanner command at [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-ocr.el#L410][line 410]] ignores the shell exit status, then announces
that it acquired the image. An intercepted-command probe confirmed both the
deletion command with keep enabled and the success announcement when the
stubbed shell returned failure.

Impact: a requested original can be deleted, and spoken success can mislead a
user when scanning or compression failed. This is the optional SANE
acquisition path, not a demonstrated fault in PaddleOCR recognition.

Recommendation: correct retention semantics, use an owned temporary file,
and validate each acquisition/compression result before advancing page state
or announcing success. Test keep enabled/disabled and scanner/compressor
failure independently. Extend [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/test/emacsvox-ocr-tests.el#L118][the existing literal-argument OCR tests]] to
the acquisition path. Real scanner acceptance remains necessary.

** AUD-04 — A stop-hook or send error can interrupt process retirement
:PROPERTIES:
:AUDIT_PRIORITY: P2
:CLASSIFICATION: Confirmed defect
:CONFIDENCE: High
:END:

[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/tts-speak.el#L563][tts--retire-process]] marks a process as retiring, calls interruption,
then deletes it. [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/tts-speak.el#L546][tts--interrupt-process]] protects tracked callback cancellation,
but its send error or =tts-stopped-hook= error can escape before retirement
reaches =delete-process=. The sentinel at [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/tts-speak.el#L499][line 499]] suppresses normal failure
handling for a process already marked as retiring.

A pipe-process probe with a failing stopped hook left the process live and
marked as retiring. Callers include [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/tts-speak.el#L3000][server initialization]],
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/omnivox-remote.el#L270][explicit remote disconnect]], and
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-omnivox-components.el#L214][component removal]]. During replacement, an error can also interrupt
publication of the new main process.

Recommendation: give retirement an unconditional final cleanup boundary,
preserve useful error reporting, and ensure one failing observer cannot
prevent the remaining essential cleanup. Test send failure, hook failure,
reentrant stop, already-dead processes, and replacement identity. Existing
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/test/emacsvox-tts-tests.el#L2421][retirement tests]] cover normal ownership and terminal events but do not
exercise this failing-hook path.

** AUD-05 — Timed-out voice applies retain callbacks and can continue sending changes
:PROPERTIES:
:AUDIT_PRIORITY: P2
:CLASSIFICATION: Confirmed defect
:CONFIDENCE: High
:END:

[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/omnivox-voices.el#L1301][omnivox-apply-voice-configuration]] completes its aggregate on timeout at
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/omnivox-voices.el#L1451][line 1451]]. It does not retire the corresponding entries in the
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/omnivox-voices.el#L365][process control-request table]]. Its policy-response closure can still
store a late acknowledgement and call =register= after the aggregate has
already reported failure.

A probe used the actual request table and response dispatcher. After the
timeout, one callback remained pending. Delivering the late policy response
caused a second outgoing request, =register_logical_voices=, while the caller
had already received one terminal failed result.

Impact: Workbench status can say failure while an operation continues making
changes; repeated unacknowledged operations retain captured state on a live
process. The probe proves client-side post-timeout transmission, not whether
a particular backend accepts it.

Recommendation: record request ownership, retire callbacks on terminal
completion, and prevent terminal operations from initiating another phase.
Decide and document how a late acknowledgement of an already-sent change is
reported; client cancellation cannot undo server work already performed.
Extend [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/test/emacsvox-tts-tests.el#L1857][overlapping-apply tests]] with timeout/late reply, process replacement,
and pending-table cleanup assertions. This is concrete additional evidence
for the existing [[file:../../../docs/developer/backlog.org][explicit-operation backlog item]], not a reason to silently
serialize all applies or alter the accepted overlap contract.

** AUD-06 — Initial remote notification failure has no automatic recovery trigger
:PROPERTIES:
:AUDIT_PRIORITY: P2
:CLASSIFICATION: Confirmed defect
:CONFIDENCE: High
:END:

[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/tts-speak.el#L3013][tts-initialize]] catches notifier startup failure and keeps main speech
available. For a failed initial remote handshake, no managed notification
process exists to trigger [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/omnivox-remote.el#L145][the reconnect sentinel]]. The ordinary
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox.el#L492][startup path]] calls =tts-initialize= directly. Unlike
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/omnivox-remote.el#L251][omnivox-remote-connect]], it does not schedule a retry when only the main
lane succeeds.

The isolated startup probe left a live main process, no notification process,
and no retry timer. A transient notification failure can therefore leave
notifications degraded to main speech until a manual reconnect/restart or
another event triggers recovery. Keeping main speech usable is correct; the
missing recovery trigger is the defect.

Recommendation: schedule remote recovery after partial initial startup,
respecting suspension and the auto-reconnect setting. Test a failed first
notifier handshake followed by success, disabled notifications, and explicit
disconnect. The [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/test/omnivox-remote-tests.el#L12][five focused remote tests]] currently cover tokens, resources,
filter composition, intentional retirement, and inventory, not this path.

User recovery documentation belongs in
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/docs/manual/chapters/speech-backends.org#L123][the remote backend guide]]; detailed lifecycle guarantees belong in
=docs/developer/integration-maintenance.org=.

** AUD-08 — Some recursive Make paths lose the selected Emacs
:PROPERTIES:
:AUDIT_PRIORITY: P2
:CLASSIFICATION: Confirmed defect
:CONFIDENCE: High
:END:

The root reads =local.mk=, but the recursive invocations in
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/Makefile#L1263][config]] and [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/Makefile#L338][emacsvox]] do not pass =EMACS=.
The child [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/Makefile#L39][Lisp Makefile]] sets =EMACS = emacs=. A Makefile variable is not
automatically passed to a recursive make as a command-line override.

A non-building probe included the actual root and child Makefiles and printed
their selections: the parent selected =/home/bart/opt/emacs-31/bin/emacs=;
the child selected =emacs=, which here resolves to system Emacs 30.2.
The [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/Makefile#L125][bytecode recipe]] passes the selection for compilation, but its =config=
prerequisite can regenerate autoloads using the wrong Emacs. The =emacsvox=
target can compile with that wrong selection too.

Impact: =check-emacs= can validate one executable while later work uses
another. On this machine that means exact-version mismatch; on other machines
it could mean an unsupported system Emacs. No wrong-compiler build was run.

Recommendation: propagate the selected executable through every recursive
configuration/build path. Test with =local.mk= alone and distinguishable stub
executables, plus an explicit command-line override. Existing
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/.github/workflows/ci.yml#L101][compatibility CI]] supplies =EMACS= on the command line, which masks this
selection gap.

** AUD-10 — Autoload regeneration depends on only one source file
:PROPERTIES:
:AUDIT_PRIORITY: P2
:CLASSIFICATION: Confirmed defect
:CONFIDENCE: High
:END:

The [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/Makefile#L491][emacsvox-loaddefs.el rule]] depends only on
=emacsvox-omnivox-components.el=. The generator scans the whole Lisp directory
at [[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox-autoload.el#L41][lines 41–42]]. Changes to autoload cookies or definitions in other files do
not invalidate the target.

With =make --question -W=, a simulated change to =emacsvox-wizards.el= left
loaddefs considered current, while a simulated component-manager change
invalidated it. No timestamps or generated artifacts were changed.

Impact: an incremental build can pass freshness checks while a newly added
autoloaded command is missing from a fresh session, or an old signature or
docstring survives. Full rebuilds and explicit release/package generation
mitigate this; they do not repair the incremental rule.

Recommendation: make all relevant source/generator changes invalidate
loaddefs, including additions/removals if supported by the chosen Make
approach. Add a fixture that changes a second module, then verifies that the
new command is available in a fresh process. Existing
[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/test/emacsvox-autoload-tests.el#L25][generator tests]] prove invocation and initial generation, not incremental
dependency completeness.

** AUD-17 — Background startup work has no explicit completion/error owner
:PROPERTIES:
:AUDIT_PRIORITY: P2
:CLASSIFICATION: Maintainability concern
:CONFIDENCE: High for structure; medium for user-visible failure modes
:END:

[[https://github.com/bartbunting/emacsvox/blob/96b8e634b25accc99057c9da48c4929991e2a5b4/lisp/emacsvox.el#L498][Startup]] starts threads for core advice loading and package preparation
