* Status and scope

Implemented on 2026-09-24 following the maintainer's instruction to proceed.
Regression, graphical, compiled and muted native checks pass; listening
acceptance remains open. Personal settings and existing Emacs sessions have
not been changed. The maintainer selected promotion of an existing matching
choice with its tuning preserved, retention of shared settings and fallback
tuning, and applying to all voices with a choice of a new or existing palette.
The detailed rules below record the delivered behavior and editor contracts.

Parham's example is an English eSpeak base voice with the Max variant. The
operation also accepts other supported physical voices. The first version
targets every effective named voice, including =default= and inherited names;
subset selection is deferred. It is a one-time bulk edit, with no ongoing link
between named voices and no propagation from later edits to =default=.

All ADRs were reviewed. In particular, retain complete ownership and copy rules
from [[file:adr/0018-unified-voice-palette-model.org][ADR 0018]], ordered saving from [[file:adr/0015-palette-owned-voices-and-migration.org][ADR 0015]], private previews from

* Choice and tuning rules

Match only an exact selector with the same engine ID and physical voice ID.
Use the validated local selector for persistence; a browser's session selector
does not become saved session state. An eSpeak base-plus-variant identity is
one exact voice. Display names, engine-default selectors and property selectors
that happen to resolve to that voice today are not matches.

- When a match exists, move the first matching record in the original order
  to the front. Preserve its choice ID, common adjustments and native settings.
- If several records match, retain every other record in its relative order,
  including differently tuned matches. Do not merge tuning or delete duplicates.
  Show the promoted record and retained matches in the review details.
- If the first choice already matches, keep its record and order unchanged.
- If none matches, prepend a new exact local choice with a fresh choice ID,
  empty common adjustments and no native patch. It follows the named voice's
  shared settings and the selected engine's existing mappings/defaults. Do not
  copy tuning from the old preferred choice, even within the same engine, or
  from a physical audition.

Keep all other choices, including unavailable choices, in their original order
with their full tuning. Preserve each named voice's definition representation,
language, relative rate, omitted values, explicit nil, zero and optional effects.
Shared settings are not flattened into choice patches. Existing matching native
settings remain subject to ordinary runtime qualification and degradation
reporting; preservation does not guarantee audible equivalence.

An Automatic entry has no explicit choices. Adding the selected voice gives it
one explicit choice; ordinary workstation fallback still applies. Do not invent
an Automatic row or copy the workstation's current physical choice into storage.

For an existing personal palette, retain its identity, parent and metadata.
Materialize each inherited entry as a complete local entry, with local snapshots
owned by the destination, even when its preferred choice already matches. This
pins the reviewed entries to that palette. Preserve unchanged direct entries
without allocating replacement snapshots. If every entry is already direct and
preferred, report that there are no changes; saving need not rewrite the stores.

A new palette is an independent copy of the chosen source's effective entries,
with =acss-default= as parent and fresh destination-owned local snapshots. Later
source-palette edits do not affect those entries. New standard names can still
be inherited, and retained personality definitions keep their normal external
settings dependency. Names introduced after the bulk edit do not acquire the
selected physical voice automatically.

* Interaction and review

1. Offer /Use this voice across a palette/ in both physical-voice and eSpeak
   variant browsers. Keep the existing single-voice action available. Resolve
   the selected base and variant through current-worker inventory.
2. Offer /Update an existing personal palette/ and /Create a new personal
   palette/. Updating selects a writable personal destination. Creating selects
   a source palette, defaulting to the current palette, and an unused name;
   the standard palette is a valid source. Explain that creating copies the
   source's adjustments and fallbacks. No palette is created at this step.
3. Prepare an unsaved review containing every effective named entry in a stable
   order. Summarize the source/destination, chosen voice, total names, added or
   promoted choices, inherited entries becoming local, and unchanged entries.
   Show known uses and affected descendant palettes for an update, once for
   the operation. Keep raw IDs and detailed provenance in expandable details.
4. Each row offers /Play original/, /Play proposed/ and /Compare/. Start at
   =default= and offer a short representative sequence including available
   =indent=, =animate= and =bolden= entries. Allow inspection of every row.
   Use identical comparison text, captured relative-rate basis and private
   complete-chain previews. Report actual fallback and unsupported tuning;
   a successful fallback must not be presented as hearing the chosen voice.
5. Offer /Save and apply/, /Save to collection/, /Back/ and /Cancel/. Saving
   and applying selects the destination through the existing palette service.
   Saving to collection does not select it or request application. If the
   destination is already selected, make saved-versus-applied status clear.
   Startup selection remains the separate existing action.

Use the existing spoken UI controls and navigation conventions. Opening,
comparison and cancellation before Save write nothing and do not publish draft
voices to live speech. Stop or leaving the view cancels its pending previews;
late results cannot update another view or revision. The review is for listening
and saving, not another full tuning editor; individual tuning remains available
through the common editor after the bulk operation.

* Conflicts, saving and recovery

Capture the source entries, ancestry, full local choice records and destination
identity for the review. Before preparation and again before saving, check for
conflicting dirty drafts or unfinished saves affecting the source, destination,
or descendants whose voices would change. List them with access to their existing
editors; preserve them and require resolution before proceeding. Do not merge,
save or discard individual drafts automatically. Refresh clean affected views
after successful publication; recheck drafts opened while the review was active.

Recheck source definitions, local snapshots, effective name inventory,
destination availability and store fingerprints before writes. A changed input
requires a refreshed review. Missing local snapshots or invalid ownership block
the whole proposal with an explanation, rather than copying a degraded portable
chain or silently skipping a voice. Ordinary physical unavailability remains
visible and retains the saved fallback policy; it does not remove entries.

Build one complete destination and one frozen save proposal for the entire
operation. Reuse the existing coordinator: persist immutable local snapshots
first, then the palette references, then publish the complete registry state.
Do not save or activate one voice at a time. No atomic transaction across the
two files or speech streams is claimed.

- Before any successful write, failure leaves the old palette and live state.
- If the local-store write succeeds but palette publication fails, retain the
  previous palette and old referenced snapshots. Report the partial save and
  retry the same proposal after conflict checks, without allocating new IDs.
- Once saved, an application failure does not undo or resave the palette.
  Report each stream's acknowledgement, timeout, failure or degraded tuning;
  offer retry through the existing apply path. Claim full application only
  when both streams confirm the required settings.
- A retry must not overwrite newer saved data or reselect a palette after the
  user has chosen another configuration. Report superseded state and let the
  existing palette selection workflow handle a deliberate later application.
  Stale callbacks cannot mark newer edits saved or applied. Never replay speech.

   generated reference/manuals. Remove the backlog item only after the feature

server contract or broader architecture change is a separate design question.

* Acceptance

Extend the existing voice-data, voice-editing, voice-drafts, voice-editor,
voice-palettes, voice-workbench and eSpeak-variants ERT suites as appropriate.
Expected results must cover observable saved data and behavior:

- First-match promotion, differently tuned duplicates, already-preferred
  choices, exact identity versus dynamic selectors, and repeated application.
- New untuned choices; shared nil/zero/omission and relative-rate preservation;
  native patches on promoted and retained choices; cross-engine insertion.
- Automatic entries, inherited ownership, all effective names including
  =default=, independent copies, descendant impact and missing local snapshots.
- Cancellation without writes, private before/after previews, unsaved-draft
  conflicts, edits during review, source/local-store drift and partial writes.
- One coordinated save, both save actions, idempotent retries, per-stream
  application failures, stale callbacks and superseded configurations.
