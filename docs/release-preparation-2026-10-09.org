#+title: Emacsvox 2026.10.0 Release Preparation
#+date: 2026-10-09

* Release identity and status

The release target is =2026.10.0= with Omnivox =1.17.0= or newer.
Preparation follows =a2421702f=, which adds the quiet HTML table cue.
=VERSION=, the Lisp package header and the current NEWS heading agree.
The Debian package recommends =omnivox (>= 1.17.0)=; remote Emacs and WSL
retain the optional local-package relationship in ADR 0013.

Omnivox [[https://github.com/bartbunting/omnivox/releases/tag/v1.17.0][1.17.0]] was published on 2026-10-09 from commit
=8a2c3328d34e75b311647db2db6830a90f876ea7=. Its CI run
[[https://github.com/bartbunting/omnivox/actions/runs/37881289669][37881289669]] completed successfully. Release publication remains a separate
approval; this record does not authorize a tag or publication.

* Prepared changes

The core and component manifests now pin the published Windows x64 and ARM64
archives. The developer Piper staging lock uses the matching archive and
source commit. TGSpeechBox is bundled in both core archives; the component
installer now recognizes its ARM64 standalone module and installed status.
A regression covers available and bundled ARM64 states.

The Windows source index binds the new core hash to its exact Omnivox commit,
Piper source archive and TGSpeechBox source archive. Both source archives
passed every internal manifest checksum: 15,653 Piper entries and 15,647
TGSpeechBox entries. The runtime Cargo.lock matches the source archive and
release tag after newline normalization. TGSpeechBox's native input archive
and commit match the bundled helper's provenance. Its runtime preserves
TGSpeechBox and eSpeak notices. Emacs, Inno and their dependency pins and
notices are unchanged.

README, the installation and speech-backend chapters, the developer staging
example and NEWS now describe the 1.17.0 requirement and verified inputs.
The maintained manual was regenerated. Archived release notes remain intact.
The untracked =etc/#NEWS#= autosave was preserved outside release staging.

* Omnivox release acceptance

All nine downloaded Windows core and companion ZIPs passed the published
SHA-256 checks and ZIP integrity checks. Both corresponding-source archives
also matched the release checksums before their internal manifests were read.

The real WSL installer used a separate source export, XDG configuration/cache
and Windows temporary LocalAppData directory. It installed the published
Windows x64 core and recorded selection only in that isolated configuration.
The real component installer installed and checked Flite and RuTTS, verified
Piper provenance and installation, and recognized TGSpeechBox from the core.
No production speech process or personal server selection was changed.

Two fresh Windows workers independently advertised palette letters, named
punctuation profiles and engine configuration. WinRT, eSpeak, TGSpeechBox,
Flite and RuTTS all completed their diagnostic synthesis/playback checks with
null output. This checks generated audio consumption, not audible output.
The published Linux core passed native engine-configuration and punctuation
service round trips and the two-worker frozen punctuation-catalogue test.

Isolated WSL and component tests passed 48 cases; three graphical component
manager cases skipped. The tests cover x64 and ARM64 selection. Actual ARM64
execution and macOS acceptance were not performed on this x64 WSL host.

* Final release checks

After the pins, instructions and NEWS settle, regenerate the maintained
manual with =make docs-update= and validate =make docs-release-check=.
Commit the completed preparation, create a separate clean release worktree,
and run =make bytecode-rebuild= followed by =make release-artifact=.
Inspect the archive, checksum and recorded source commit. Run
=make release-deb= for the Debian asset. Check the supported Emacs matrix;
local Emacs 31.0.90 results do not establish Emacs 30.2 and 31.1 acceptance.

The native Windows setup remains a development/preview route under ADRs
0024 and 0025. A stable source release does not complete its remaining
installer acceptance or integrate it into stable release publication.

Tagging and publication require fresh explicit approval naming
=2026.10.0=. Prepare the public manual from the same clean committed source
using the existing documentation publication workflow.
