* Status and scope

Implementation authorised on 2026-10-18. [[file:adr/0029-lisp-source-layout.org][ADR 0029]] accepts the directory
and bootstrap contract. Nested-path infrastructure is implemented, and the
three pilot integrations have moved to =lisp/integrations/=. These two slices
pass their focused checks and native lifecycle acceptance and are committed as
=01784f036=. The remaining migration is authorised in reviewed batches.

The aim is to make related code easier to find and ownership easier to
understand as Emacsvox grows. Preserve behaviour, filenames, provided
features, public commands, personal settings, speech protocols and package
requirements. Directory moves do not establish new dependency boundaries by
themselves. Function extraction, compatibility removal, feature retirement
and changes to when integrations load are separate work.

The original investigation baseline was =master= at =b8ccb8d6c=. The
implementation baseline is =98b3263ea=. The existing changes to
[[file:ui-settings-plan.org][the UI settings plan]] are independent work and must be preserved.
Recheck the inventory and active development branches before implementation;
the counts and examples below describe this investigation, not a permanent
module manifest.

* Findings

At the implementation baseline there are 329 tracked =lisp/*.el= files and
324 unique modules in =make -C lisp documentation-modules=. The five sources
outside that ordinary compiled inventory are =.skeleton.el=,
=emacsvox-autoload.el=, =emacsvox-muggle-org-navigation.el=,
=emacsvox-muggles.el= and =extra-muggles.el=. The Muggles sources have separate
build targets. Generated =emacsvox-loaddefs.el= is ignored and is not a
tracked source. Do not confuse the tracked, compiled, autoload-scanned and
distributed inventories.

The tree contains 51 =emacsvox-aural-*= files and 15 =omnivox-*= files.
Those prefixes span several responsibilities. For example:

- =emacsvox-aural-voice-data= and =emacsvox-aural-voice-runtime= own data and
  resolution; the voice editor and workbench own interaction.
- =emacsvox-aural-voice-drafts= coordinates persistence and acknowledged
  application independently of view buffers. It is more than editor UI.
- =omnivox-library= contains a tabulated interface as well as runtime calls;
  =omnivox-library-apply= owns a separate activation operation.
- =emacsvox-spelling= requires both the Flyspell integration and the shared
  tone editor. A directory named UI will not be independent of integrations.
- =emacsvox-table-reader= supplies common logical table operations used by
  Agent Shell, Markdown and Org. It should not be owned by one integration.
- =emacsvox-aural-home= retains shared helpers and public entry points under
  ADR 0027. Moving it must not become an incidental removal of those APIs.

Build prerequisites also cross the proposed groups. =tts-speak= depends on
aural transport; =voice-setup= depends on TTS and the compatibility voice
bridge; =omnivox-voices= depends on voice resolution and protocol codecs;
voice editing depends on the aural compiler. Preserve these relationships.
An inventory of literal =require= forms is useful evidence, but is not a
complete graph: backend names are constructed dynamically, and advice,
autoloads, deferred requires and callbacks introduce other dependencies.

* Accepted directory layout

Use one level of subdirectories initially. The =core/= directory gives
shared reading and navigation code an explicit destination.
Do not introduce per-package subdirectories or a catch-all =misc/= directory.

| Location | Responsibility and representative candidates |
|----------+---------------------------------------------|
| =lisp/= | Stable bootstrap and package entry: =emacsvox-setup.el=, =emacsvox-preamble.el=, =emacsvox-paths.el=, =emacsvox-version.el=, =emacsvox.el=, =emacsvox-autoload.el=, generated =emacsvox-loaddefs.el= and =Makefile=. |
| =lisp/core/= | Shared reading, command/advice infrastructure and navigation, including =emacsvox-speak=, =emacsvox-advice=, =emacsvox-keymap= and =emacsvox-table-reader=. |
| =lisp/aural/= | Presentation contracts, rules, resources, providers, compilation, planning, submission, transport, history and replay. |
| =lisp/speech/= | TTS process and queue lifecycle, wire codecs, remote transport and engine adapters, including =tts-speak=, =tts-queue-state= and =omnivox-voices=. |
| =lisp/voices/= | Logical voice definitions, palette data, resolution and save coordination, including =voice-defs= and the aural voice data/runtime/draft services. |
| =lisp/ui/= | Settings menus and dedicated editors: tone, voice, palette, rule and sound editors, plus diagnostic views where their ownership is clear. |
| =lisp/integrations/= | Adaptations for Emacs modes and external packages; keep Agent Shell's two files and EAT's four files together within this directory. |

The full allocation review is recorded in [[file:lisp-layout-inventory.org][the migration inventory]]
and the implementation checkpoints below. All placement decisions are settled;
existing mixed modules remain intact. The inventory records this migration,
not a second source of build dependencies.

* Loading and inventory contract

Keep =lisp/Makefile= as the canonical compiled-module/dependency inventory,
following ADR 0011. Do not create independent handwritten module lists for
Windows, documentation and packaging. The data-only =etc/lisp-directories=
registry is specified in ADR 0029; check that every manifested module's parent
belongs to it. The first slice supplies its Lisp reader and preamble loading;
the other consumers remain subsequent infrastructure work.

Provide a small bootstrap facility usable by setup, preamble, batch tests and
documentation without starting speech. It should register only explicit
repository-owned directories in a deterministic order. Do not recursively add
every directory found on disk, which could admit fixtures, obsolete copies or
private packages. Retain globally unique library basenames and provided
features so ordinary =require= and autoload names remain stable.

Validate relative paths: reject absolute paths, parent traversal, unexpected
directories and duplicate basenames/features. Native paths must remain inside
the selected checkout. Exercise spaces in installation paths and Windows case
handling. Preserve the distinction between compiled modules, optional sources,
templates, generated autoloads and shipped runtime files.

Maintain the documented root setup entry point for source, Debian, WSL,
remote and native Windows routes. Audit direct internal file-path consumers
in launch scripts, tests and local configuration before moving a batch. Update
reviewed local callers explicitly; do not rewrite personal files wholesale.
Avoid permanent duplicate libraries or forwarding files at every old path.
Any additional compatibility requirement discovered in that audit must be
decided before its affected batch moves.

Capture newly discovered architectural problems as separate work. A module
may remain at the root with a recorded reason until its destination is clear.

* Verification and rollback

For each implementation batch, run affected source tests first. After moves,
run =make check-emacs=, =make bytecode-rebuild= and =make bytecode-check=,
then verify in a fresh Emacs that moved features load from the intended tree.
Cover missing optional dependencies as well as prepared integration packages.
Do not use a live session reload as proof of a filesystem migration.

Before accepting the pilot and final layout, cover:

- Make/native inventory and dependency parity, nested autoload discovery,
  orphaned old byte-code, removed sources and compiler-version mismatches.
- Source and compiled core/aural tests, affected integrations and the Emacs
  30.2 compatibility route with the supported Transient version.
- Debian and source-archive installation; native Windows bundle/setup tests,
  plus a real Windows build and lifecycle check. Mocked packaging tests do not
  establish native acceptance.
- A fresh graphical settings/editor check when moving UI files, including
  entry, Help, return focus, preserved drafts and preview/Apply/Save behaviour.
- Representative reading, integration loading, main/notification readiness
  and interruption. Listening remains distinct from captured submissions.
- Header checks, regenerated references/manuals when affected, and the
  non-mutating =make docs-release-check= gate after byte-code is current.

On a failed batch, retain diagnostic evidence and correct it or revert only
that batch's commits. Rebuild byte-code after reverting paths. Never reset,
clean or stash unrelated source work to obtain a passing baseline. Generated
cleanup must remove only owned build outputs, including obsolete locations;
it must not sweep personal files or follow arbitrary directory links.
