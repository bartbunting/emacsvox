A concrete migration conflict is possible today: one routing profile explicitly
assigns =voice-bolden= to DECtalk, and another assigns it to Eloquence, while
both are used with the same palette. There is no saved fact saying either
explicit route belongs to that palette.
A single new palette-owned choice cannot preserve both as automatic alternate
definitions without retaining sharing or introducing explicit variants.

* Selected migration: independent conversion on first save

The maintainer selected option A on 2026-09-08.
Opening and auditioning remain read-only; the normal save proposal names the
new palette and source routing profile. Subsequent edits use that converted
palette directly. The original palette and its presentation-profile references
remain available. This is a one-time conversion for each chosen palette, not
a new palette on every save.

| Option | Result | Pros | Cons |
|--------+--------+------+------|
| A. Copy when first saved (selected) | Create a personal palette with independent definitions and choices copied from the selected legacy palette and routing profile. | Leaves old setups intact; scope and rollback are visible; avoids guessing which unused profiles to convert. | Adds a palette; retaining its selection after restart requires the existing explicit Presentation Profile action; the copy no longer follows the old palette's parent edits. |
| B. Upgrade the selected palette in place | Personal palettes keep their IDs while acquiring owned choices; built-ins still need personal copies. | Fewer duplicates; existing presentation profiles keep selecting the upgraded palette. | Every reference to that palette changes semantics; later routing-profile switches stop replacing its owned choices; inheritance and recovery require more migration work. |
| C. Unify the editor over shared routing first | Keep current stores and ownership while improving navigation, drafts and saving. | Fastest route to a usable editor; smallest initial migration risk. | A physical assignment still affects multiple palettes; palette switching cannot restore complete voice choices; ownership migration remains later work. |

The migration contract is:

1. Choose a source palette and saved routing profile explicitly in the proposal;
   default the latter to the current saved selection when available. Do not
   treat an unrelated Presentation Profile as a route mapping.
2. Copy effective named definitions into an independent personal palette,
   retaining their representation. Do not bake adapter normalization, inferred
   physical realization, or contextual rule results into saved values.
3. Copy ordered explicit selectors and language metadata, preserving exact,
   engine-default and property choices, including unavailable choices. Keep
   exact IDs local. Report conflicting routes for portable and legacy aliases
   instead of arbitrarily selecting one; preserve unrelated logical IDs.
4. No explicit route means Automatic. Keep global engine priority, disabled
   engines and fallback policy as workstation policy; do not expand them into
   per-voice exact assignments. Automatic remains subject to that policy.
5. Session overrides remain temporary and visible. They are not silently saved
   as the new base. Pinning a temporary choice requires an explicit editor
   action. Show when the proposed saved result differs from current speech.
6. Persist and validate the complete proposal before selecting the new palette
   and applying its configuration. Leave original data and Presentation Profile
   selections intact. Retaining the new selection across restarts is the
   existing explicit profile workflow.
7. Preserve old readers/commands through the transition. Legacy palettes use
   legacy shared routing; converted palettes use their owned choices. Label
   the scope accurately wherever both models are exposed.

* Selected preview: complete voice through a private routing snapshot

Runtime inspection after storage commit =052dade27= found an unplanned protocol
boundary. =omnivox--preview-one= sends one =:selector=; the sibling Omnivox
=ControlRequest::Preview= also accepts one =VoiceSelector=. Its server handler
builds a private logical definition with =preferences: vec![selector.clone()]=.
Normal logical-voice registration accepts an ordered preference list. The
current preview therefore cannot submit an unsaved DECtalk-then-Eloquence chain
unchanged. Choosing one candidate from inventory would not test runtime fallback.

The maintainer selected option 1 (A below). [[file:adr/0016-complete-voice-preview.org][ADR 0016]] and the
[[file:voice-editor-preview-contract.org][preview contract]] now define the additive capability, request, response, policy
isolation, compatibility behavior and acceptance cases. Shared adjustments remain
the current scope; individual fallback tuning is still slice 7.

| Choice | Benefit | Cost or limitation |
|--------+---------+--------------------|
| A. Add ordered-choice preview support (selected) | Unsaved and inactive voices can exercise their whole chain through a private server routing snapshot, with shared tuning and actual realization feedback. | Requires coordinated Emacsvox/Omnivox protocol work, capability negotiation and an explicit older-server behavior. Check workstation fallback-policy parity as part of the contract. |
| B. Keep individual-choice auditions initially | Retains the current preview API and lets the base editor proceed sooner. | Clearly label each audition as one choice. Unsaved chain fallback is unverified until save/apply and normal speech; this defers the original full-preview acceptance case. |
| C. Register temporary logical voices for previews | Could use existing logical routing to exercise full chains without a new preview request format. | Adds temporary registry identities and lifecycle coordination, including both lanes, cancellation and concurrent applies; more state than a private preview request. Feasibility needs review. |

The selected design preserves individual auditions and adds a separate complete
voice preview. Full previews send a frozen choice/policy snapshot, retain applied
server disablement, and report accepted-audio realizations. Older servers report
full preview unsupported; no first-choice substitution or temporary application.
The XHI contract is complete; implementation resumed after the requested High
handoff.

The initial runtime wiring was preserved as a local scratch patch, then removed
from the source tree so this checkpoint contains only tested storage code.
Slice 3 has since replaced that scratch work with tested runtime integration.
The server preview slice below has changed Omnivox source. No live personal settings changed.

** DONE 3. Resolve owned choices through normal speech and preview

The pure resolver is implemented and tested as the first part of this slice.

** DONE 4. Add draft and save coordination

Create one draft per destination and scope, with immutable save proposals and
operation IDs. Track changed fields, completed persistence steps, desired
selection, lane acknowledgements, and retryable failures. Reuse atomic writers
and adapter apply services; two file renames are not one atomic transaction.

Check conflicts before writes; test failure between writes, cancellation before
save, idempotent retry, timeout, stale callback, buffer destruction, and newer
edits while an old proposal applies. A partial save remains recoverable and
visible. No callback can clear changes it did not save or select another draft.
Keep inactive-palette saving and restart selection distinct from runtime apply.

The private session draft registry now retains working, saved and last-applied
snapshots independently of view buffers. Frozen proposals retain destination and
source watches, file fingerprints, immutable choice IDs and completed writes.
Both stores are checked before writing, local snapshots are published first,
and live registry/hooks follow only after both writes succeed. Retry recognizes
a completed rename even if its writer reported an error afterwards. Changed
files conservatively require a fresh review; the coordinator does not silently
merge a concurrent external edit into an already approved proposal. These are
optimistic conflict checks, not an exclusive lock against arbitrary external
writers. Newer edits, duplicate or stale callbacks, timeouts and palette switches
retain truthful save/apply state. Saving an unrelated inactive palette leaves
current selection and apply ownership intact. Draft retention is session-only;
no editor entry point or live personal data changed in this service slice.
