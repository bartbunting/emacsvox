* Selected migration: independent conversion on first save

The maintainer selected option A on 2026-09-08.
Opening and auditioning remain read-only; the normal save proposal names the
new palette and source routing profile. Subsequent edits use that converted
palette directly. The original palette and its presentation-profile references
remain available. This is a one-time conversion for each chosen palette, not
a new palette on every save.

| Option | Result | Pros | Cons |
|--------+--------+------+------|
| A. Copy when first saved (selected) | Create a personal palette with independent definitions and choices copied from the selected legacy palette and routing profile. | Leaves old setups intact; scope and rollback are visible; avoids guessing which unused profiles to convert. | Adds a palette; retaining its selection after restart requires the existing explicit Presentation Profile action; the copy no longer follows the old palette's parent edits. |
| B. Upgrade the selected palette in place | Personal palettes keep their IDs while acquiring owned choices; built-ins still need personal copies. | Fewer duplicates; existing presentation profiles keep selecting the upgraded palette. | Every reference to that palette changes semantics; later routing-profile switches stop replacing its owned choices; inheritance and recovery require more migration work. |
| C. Unify the editor over shared routing first | Keep current stores and ownership while improving navigation, drafts and saving. | Fastest route to a usable editor; smallest initial migration risk. | A physical assignment still affects multiple palettes; palette switching cannot restore complete voice choices; ownership migration remains later work. |

The migration contract is:

1. Choose a source palette and saved routing profile explicitly in the proposal;
   default the latter to the current saved selection when available. Do not
   treat an unrelated Presentation Profile as a route mapping.
2. Copy effective named definitions into an independent personal palette,
   retaining their representation. Do not bake adapter normalization, inferred
   physical realization, or contextual rule results into saved values.
3. Copy ordered explicit selectors and language metadata, preserving exact,
   engine-default and property choices, including unavailable choices. Keep
   exact IDs local. Report conflicting routes for portable and legacy aliases
   instead of arbitrarily selecting one; preserve unrelated logical IDs.
4. No explicit route means Automatic. Keep global engine priority, disabled
   engines and fallback policy as workstation policy; do not expand them into
   per-voice exact assignments. Automatic remains subject to that policy.
5. Session overrides remain temporary and visible. They are not silently saved
   as the new base. Pinning a temporary choice requires an explicit editor
   action. Show when the proposed saved result differs from current speech.
6. Persist and validate the complete proposal before selecting the new palette
   and applying its configuration. Leave original data and Presentation Profile
   selections intact. Retaining the new selection across restarts is the
   existing explicit profile workflow.
7. Preserve old readers/commands through the transition. Legacy palettes use
   legacy shared routing; converted palettes use their owned choices. Label
   the scope accurately wherever both models are exposed.
