* Integration Maintenance
:PROPERTIES:
:TEXINFO_NODE_NAME: Integration Maintenance
:DESCRIPTION: Maintain optional integrations and release staging.
:END:

This chapter collects source-level contracts that are deliberately omitted
from the user task guides.  Optional package APIs and renderers evolve, so
recheck the upstream interfaces and keep compatibility behavior bounded when
changing an integration.

** Source checkout and byte-code lifecycle
:PROPERTIES:
:TEXINFO_NODE: no
:END:

Use the Emacs selected by the ignored repository-local ~local.mk~.  When Emacs
30.2 or newer is not the system ~emacs~, set its absolute path there:

#+begin_example
EMACS=/path/to/emacs-31/bin/emacs
#+end_example

Run ~make check-emacs~ before diagnosing compilation.  After an ordinary Lisp
edit, use the incremental build:

#+begin_example
make bytecode
#+end_example

After switching branches, pulling changes, or changing a macro or public
interface, use:

#+begin_example
make bytecode-rebuild
#+end_example

That target removes ignored generated ~.elc~ files and recompiles them with
the selected Emacs; it does not clean or discard source changes.
~make bytecode-check~ is the non-mutating preflight for startup or deployment.
It reports missing, stale, orphaned, or wrong-Emacs byte-code.

Tests deliberately prefer source and therefore do not prove that the
byte-code used by a live profile is current.  Verify rebuilt byte-code in a
fresh Emacs rather than relying on a file reload when compiled dependants may
already be resident.

During development, load the changing setup source explicitly:

#+begin_src emacs-lisp
(load-file "/path/to/emacsvox/lisp/emacsvox-setup.el")
#+end_src

The setup entry point warns and prefers source when newer Lisp would otherwise
be hidden by stale local byte-code.  In a stable checkout with current ~.elc~
files, ~(load-library "emacsvox-setup")~ may be used.  Do not use
~load-library~ as the first load after editing the source tree: Emacs can
select an old ~emacsvox-setup.elc~ before the newer source checker runs.

*** Supported Emacs versions
:PROPERTIES:
:TEXINFO_NODE: no
:END:

The Lisp runtime and all platform routes support Emacs 30.2 and newer. Run
~make compat-test~ for the core compatibility contracts without installing
third-party packages. CI builds all maintained modules and runs this gate on
Emacs 30.2 and 31.1. The full ~make test~ suite additionally requires the
optional integration packages, including ~lua-mode~ on Emacs 30.

Keep each Emacs version's build in a separate checkout; never reuse ~.elc~
files across versions. All platforms, including native Windows x64, use this minimum.
The documentation toolchain retains its independent pin.

*** Native Windows builds
:PROPERTIES:
:TEXINFO_NODE: no
:END:

Use a separate checkout on a Windows drive.  The native installer regenerates
autoloads and all modules from the =lisp/Makefile= inventory with the selected
Windows Emacs.  Its launcher verifies that byte-code in a fresh process.
Do not share generated byte-code with a WSL checkout using another Emacs.

Run the native installer checks from that Windows checkout:

#+begin_src powershell
.\test\emacsvox-windows-install-tests.ps1 -Emacs "C:\path\to\emacs.exe"
.\bin\emacsvox-install.ps1 -Role Desktop -Check
.\bin\emacsvox-install.ps1 -Role Desktop
.\bin\emacsvox.ps1 -Check
#+end_src

The PowerShell tests use temporary fixtures and an existing native Emacs.
They check doctor behavior, explicit selections, incomplete installations,
platform rejection, checksums, archive paths, argument handling, and atomic
configuration replacement.  =test/emacsvox-native-bytecode-tests.el= compares
the native inventory with GNU Make and checks dependency order and byte-code
preflight failures.  Keep the WSL x64/ARM64 and remote installer tests passing.

Actual acquisition acceptance must start with a private toolchain and the
pinned archives, not a reused developer runtime.  Keep MSYS2 package versions,
compiler/configure/build/install logs, and =emacsvox-build.json= with the
installed Emacs.  The installation logs also include
=native-install-provenance.json= with Lisp source hashes and selected pins.
MSYS2 packages are signed rolling inputs; these records do not claim a frozen
or bit-identical compiler environment.  Verify fresh graphical startup,
acknowledged routing, and tracked completion on both speech lanes with a PATH
that contains neither WSL nor MSYS2 tools.  Human listening remains a separate
acceptance step. Native Windows x64 is supported; remote workstation speech
remains preview, as recorded in
[[file:../adr/0014-native-windows-support.org][ADR 0014]].

*** Remote preview validation
:PROPERTIES:
:TEXINFO_NODE: no
:END:

Keep remote installer fixtures separate from connected acceptance. In the
Omnivox checkout, run ~make dev~ followed by ~make remote-test~; set
~OMNIVOX_REMOTE_TEST_SLOW=1~ to cover heartbeat expiry. Set
~OMNIVOX_REMOTE_TEST_EMACS~ to the selected Emacs and
~OMNIVOX_REMOTE_TEST_EMACSVOX~ to the matching Emacsvox checkout for client
acceptance. The Omnivox ~docs/REMOTE.md~ guide records Windows relay tests,
real-device options, and retained evidence. Null-output tests do not establish
audible playback or acceptance through a separate SSH host. Remote access
remains preview independently of native Windows desktop support.

** Debian package builds
:PROPERTIES:
:TEXINFO_NODE: no
:END:

~make deb~ builds a local development package in ~dist/~ using Python 3,
~dpkg-deb~, Git and the selected Emacs. It stages runtime sources and generates
autoloads in a private directory, preserving checkout byte-code and personal
configuration. The deb has architecture ~all~, an Emacs 30.2 dependency
(including terminal and graphical alternatives), and an Omnivox recommendation.
It loads source and does not install emacsen-common hooks or compile on install.
The ownership and release boundaries are recorded in
[[file:../adr/0013-debian-package.org][ADR 0013]].

~make deb-test~ checks the actual archive, reproducibility, source startup,
remote diagnosis, dependency metadata and refusal of an unprepared release.
CI additionally installs, reinstalls and purges the package in a disposable
Ubuntu 26.04 container using ~test/debian-install-smoke.sh~. It uploads the
development deb and checksum as CI artifacts, without publishing a release.

After preparing the checked source archive using the release procedure below,
~make release-deb~ produces ~dist/emacsvox_VERSION-1_all.deb~ and its checksum.
The script itself verifies the existing clean-source artifact gate before and
after packaging. Local versions instead contain ~+git~ with the source commit
and source hash, and revision ~-0local1~. The included ~BUILD-INFO.json~ records
the exact source identity and autoload Emacs version. Neither package target
creates a tag, uploads release assets, adds an apt repository or changes the
manual release publication approval boundary.

After a maintainer publishes a stable GitHub release, the Release Debian
package workflow checks out its exact annotated tag and downloads the source
archive, checksum and provenance from that release. It checks the source
identity, installs from the archive, builds the release deb, and tests install,
startup, reinstall and removal in Ubuntu 26.04 before attaching the deb and
checksum. Build jobs have read-only repository access; only the attachment job
can write release assets. A rerun accepts identical existing assets and refuses
to replace different files. CI does not create tags or releases.

This workflow uses Emacs 30.2 for autoload generation; its recorded toolchain
can differ from a locally prepared package. Let CI attach the release deb
instead of uploading a differently built local package with the same name.

** Emacsvox release staging and publication
:PROPERTIES:
:TEXINFO_NODE: no
:END:

The repository-level ~VERSION~ file is the canonical stable release
identifier.  Calendar-versioning policy, including delayed patches and
backports, is recorded in
[[file:../adr/0002-calendar-versioning.org][ADR 0002]].  When advancing a release, update ~VERSION~, the literal
package header in ~lisp/emacsvox.el~, and the current heading in ~etc/NEWS~
together, then run:

#+begin_example
make version-check
#+end_example

Between releases, ~etc/NEWS~ uses the ~Emacsvox Unreleased~ heading, so changes
can be recorded before deciding whether the next publication is a patch or a
new feature-release series.  After publishing, preserve those notes verbatim
as ~etc/NEWS-VERSION~ and start a new unreleased file.  Ordinary
~version-check~ accepts that state; ~release-check~, ~release-tag~, and
~release-publish~ require the current NEWS heading to match ~VERSION~ exactly.

Prepare an artifact only from a separate clean, committed worktree.  Build
fresh byte-code and run the guarded artifact target:

#+begin_example
make bytecode-rebuild
make release-artifact
#+end_example

~release-artifact~ runs the complete test and documentation gates before
creating ~dist/emacsvox-YYYY.MONTH.PATCH.tar.bz2~, its SHA-256 checksum, and a
provenance record naming the checked source commit.  For a patch-zero feature
release, the series must match the current month.  A corrective or backport
release retains its original non-future series as required by ADR 0002.
The source archive includes the maintained ~utils/~ tools needed by the
installers, launchers and build. Before recording checked provenance, the
artifact target extracts the actual archive into a temporary directory and
runs the remote-only installer with the selected Emacs in a private home. It
checks fresh compiled startup, the offline manual and the remote helper's
credential validation without opening a workstation connection or playing
speech. ~make source-archive-check~ repeats this check on an existing archive;
~make source-archive-test~ checks export contents and rejection of missing
helpers, local configuration and byte-code. CI runs both checks before a
release as well. On native Windows, run
~test/emacsvox-source-archive-tests.ps1 -Archive PATH -Emacs PATH~ to check the
actual archive's installer doctor, complete native compilation and fresh
byte-code validation in a temporary Windows directory.

Inspect the archive, checksum, and provenance before proceeding.

Stop after artifact inspection unless fresh explicit permission names the
release to be tagged and published.  Preparing an artifact, committing or
pushing a branch, publishing documentation, or receiving a general instruction
to continue is not permission to create or push a release tag.  Once that
separate authorization has been given, the guarded commands are:

#+begin_example
make release-tag
make release-publish
#+end_example

~release-tag~ validates the artifact against the still-clean ~HEAD~ and creates
a local annotated, unsigned tag; it does not push the tag.  The unsigned-tag
policy and its trust boundary are recorded in
[[file:../adr/0006-annotated-unsigned-release-tags.org][ADR 0006]].  ~release-publish~
repeats the artifact and source-commit validation, pushes only that exact tag,
and creates the GitHub release in the repository identified by
~RELEASE_REMOTE~.  This explicit selection prevents the GitHub CLI from
choosing an ~upstream~ remote when releasing from a fork.  No release target
pushes ~master~ or the documentation branch.  Use ~make release-check~ alone
when a non-mutating preflight is wanted without creating an artifact.

** Future Aural contract decisions
:PROPERTIES:
:TEXINFO_NODE: no
:END:

The completed Aural implementation diary is preserved under
~archive/emacsvox/migrations/~ rather than serving as current instructions.
Three questions from that diary remain deliberately undecided and require an
explicit architecture decision before implementation:

- whether a critical alert may be completely suppressed or must retain an
  alternative presentation;
- which deterministic ordering policy would apply before minor-mode selectors
  can participate in the presentation cascade; and
- whether a new presentation occasion belongs to the core semantic contract
  or to a module-owned extension.

Do not infer answers from the archived proposals.  Current behavior is defined
by the Aural implementation, its generated reference, and accepted ADRs.

** Aural interface source ownership
:PROPERTIES:
:TEXINFO_NODE: no
:END:

Ordinary-buffer entry captures a source buffer, a marker, and a guarded source
line.  Child interfaces and Help inherit that context through the inspection
and shared UI helpers.  Use ~emacsvox-aural-inspection-call-in-source~ for
contextual commands so that moving the source cursor does not retarget an
open interface.  Re-entry from an ordinary buffer deliberately captures a new
target.  A dead or replaced source is reported rather than resolved through
an unrelated recent-buffer fallback.

Current-item lookup may reuse a frozen history record only when the captured
source identity, position, and modification tick still match.  Source identity
is a buffer-local, data-only token that distinguishes buffers sharing a name;
history continues to retain no buffer objects or markers.  Explicit historical
selection remains valid after the source changes and is explained from its
frozen plan.  Prepared current-item rules carry a source guard checked before
their saved or live rule layer changes.

Find rule editors by scope and target identity, not by a formatted buffer
name.  Buffer scopes belong to buffer objects, fragment scopes to fragment
identifiers, and personal/session scopes each share one working editor.
Reopening a dirty editor preserves its draft and source association.

** Notmuch contracts
:PROPERTIES:
:TEXINFO_NODE: no
:END:

The live module is registered as an optional package integration.  Its stable
extension points are the Hello, Search, Show, and Tree mode hooks; Search and
Show mode maps; public interactive commands; and public Search/Show accessors.
Advice is installed only when a target exists and is target-aware, so a nested
or programmatic upstream call does not claim the outer user's feedback.

The Show landing and visibility paths also read renderer metadata such as
~:headers-overlay~, ~:message-visible~, message extents, ~:notmuch-part~,
part-hidden state, and Notmuch part-button types.  Missing optional metadata
should reduce presentation detail rather than authorize an operation.  Review
these adapters whenever the Notmuch renderer changes.

Each user-owned asynchronous Search process carries its own completion state
as a process property.  The upstream sentinel renders first; Emacsvox then
clears that property before delivering exactly one terminal result.  The
owning buffer and process status are authoritative.  A killed owner remains
silent, concurrent buffers cannot overwrite one another, and the global
refresh-all path intentionally acquires no ownership.

Run ~make notmuch-test~ for the explicit source suite.  After current byte-code
exists, run ~make compiled-notmuch-test~; it verifies the exact loaded
~emacsvox-notmuch.elc~, compiler version, and the same focused selector,
including real displayed-window reading for both advance paths.

** Agent Shell contracts
:PROPERTIES:
:TEXINFO_NODE: no
:END:

Use ~M-x emacsvox-agent-shell-enable~ to reinstall speech hooks after
deliberately disabling them or while testing live integration changes.

The integration uses three deliberately different contract layers:

#+attr_texinfo: :columns .18 .37 .45
| Layer | Agent Shell owner | Emacsvox rule |
|---+---+---|
| Public structured API | ~agent-shell-subscribe-to~, ~agent-shell-unsubscribe~, ~agent-shell-status~, and ~agent-shell-shell-buffer~; lifecycle, permission, and tool events | Primary authority for processing, completion, errors, permission urgency, and tool status. The public turn boundary triggers inspection of renderer-owned response sections. Event and response data is treated as untrusted content and bounded before automatic Aural submission. |
| Experimental renderer metadata | ~agent-shell-ui-state~, ~agent-shell-ui-section~, rendered Markdown table/source properties, and renderer-owned faces | Feature-detected navigation and presentation input. Renderer group provenance outranks provider-controlled IDs; prose and IDs cannot manufacture structured permission or lifecycle authority. |
| Private compatibility fallback | The aggregate ~agent-shell--state~, the legacy viewport ownership resolver, viewport position helpers, and legacy face, prompt, or ID inference | Kept in narrow adapter functions for older Agent Shell releases or incomplete renderers. A missing optional detail may reduce header or navigation richness but must not create a permission action or completed response. |

The lifecycle subscription currently consumes ~init-started~,
~init-finished~, ~session-selected~, ~session-restored~, ~input-submitted~,
~turn-complete~, and ~error~.  Dedicated subscriptions consume
~permission-request~, ~permission-response~, and ~tool-call-update~.  Add new
semantic behavior at the public event layer when Agent Shell exposes it; keep
renderer and private fallbacks isolated and covered by compatibility tests.

The lifecycle subscription also observes ~config-option-update~.  Configuration
snapshots suppress initial inventory and duplicate callback/event confirmation.
Late tool details are compared only for permissions established by a public
~permission-request~ event, and their snapshots are removed on resolution.

Current Agent Shell omits rendered Codex ~rawOutput~ and textual diffs from
~tool-call-update~.  A narrow ~agent-shell--on-notification~ adapter joins that
public event to the body rendered during the same call, matching both the
owning buffer and qualified fragment ID.  Full tool speech is submitted after
rendering returns.  Output digests and lifecycle statuses are tracked separately
so late output is spoken without repeating identical updates.  Renderer IDs
without a matching public event do not authorize tool feedback.

Until upstream exposes public steering and push lifecycle events, small
adapters wrap the structured steering request's callbacks and the accepted
~session/push~ lifecycle.  Push speech finishes before the original completion
callback can drain the next queued prompt.  Callback generations invalidate
pending speech feedback on session change or integration cleanup; original
transport callbacks still run.  No transcript text is interpreted as a
steering outcome or push completion.

The queue adapter marks actual queue draining and lets ~input-submitted~
confirm that a queued prompt started.  Prompt list editing and diff entry have
native command feedback.  New asynchronous tool, queue, steering, setting, and
permission-detail submissions explicitly select the notification lane; list
editing and diff entry remain foreground interactions.  All new events and
their outcome, count, or setting attributes are registered by the workflow
semantic provider so Aural rules can customize their presentation.

** Magit contracts
:PROPERTIES:
:TEXINFO_NODE: no
:END:

Staging and selected synchronous operations collect Git outcomes at
~magit-process-finish~, before Magit can raise an error.  One interactive
command owns the aggregate result across nested calls.  A process that Magit
starts and waits for contributes only to the collector attached when it was
started; unrelated process callbacks cannot change that result.  Uncollected
asynchronous completions explicitly select the notification lane.  Neither a
command's return value nor the absence of an Emacs error proves Git succeeded.

Magit's positional highlight overlays must not become source personalities.
The integration suppresses legacy overlay voice mirroring for those highlights
and excludes their faces from source capture.  It preserves text faces,
deliberate personalities, and customized hash voices.  Navigation still emits
section facts; empty lines supply the core line-condition facts without a
competing selection icon.

Regression tests use isolated repositories for real Git failures and real
section trees for highlighting and visibility.  Run the Magit tests from
source, then again in a fresh Emacs with ~EMACSVOX_MAGIT_TEST_LOAD=compiled~
after bringing byte-code current.  A live buffer created with the former
highlight mirroring needs a Magit refresh to rebuild its source properties.

** WSL2 Omnivox development staging
:PROPERTIES:
:TEXINFO_NODE: no
:END:

The ordinary WSL2 user route is implemented by
~bin/emacsvox-wsl-install~ and pinned by ~etc/wsl-install.conf~.  Treat either
file as release tooling.  When advancing GNU Emacs or Omnivox, update the
version, archive name, URL, and SHA-256 together; exercise x64 and ARM64
selection in the isolated installer tests; and perform one real installation
of the newly pinned archive before updating the user manual.  The installer
must remain per-user, must not invoke ~sudo~ or edit shell startup files, and
must preserve an explicit ~EMACS~ or ~local.mk~ selection rather than silently
replacing it.

The installed Omnivox executable is recorded as an absolute WSL path in the
data-only ~$XDG_CONFIG_HOME/emacsvox/omnivox-program~ file.  Launcher selection
is explicit ~OMNIVOX_PROGRAM~, that per-user file, developer staging, then
~PATH~.  Keep the selection tests synchronized with this order.  A configured
but invalid path is a visible configuration error; silently falling through
would hide a stale or damaged user installation.

This section describes the reproducible source-build path, not the ordinary
pre-built WSL2 installation.  The complete source-build prerequisite checklist
is in
@@texinfo:@ref{Building Omnivox For WSL2}@@.  Dependency ownership is deliberately
split across three boundaries:

#+attr_texinfo: :columns .18 .30 .52
| Boundary | Supplied by | Dependencies |
|---+---+---|
| Windows and WSL host | Maintainer | WSL interoperation, ~powershell.exe~, ~wslpath~, Windows .NET Framework 4.7.2 or newer, Docker with Linux/AMD64 support, Git, Make, download and checksum tools, standard GNU shell utilities, network access, and writable Windows ~LocalAppData~. |
| Pinned release toolchain | Emacsvox target | The immutable Rust/Debian container, MinGW cross tools and runtime DLLs, CMake, Clang and libclang, eSpeak build dependencies, Roslyn, .NET 4.0 reference assemblies, and official Windows Piper companion.  The exact versions, source commit, and downloaded-package hashes live in ~servers/omnivox-release/toolchain.lock~. |
| Build source | Git checkouts | The current Emacsvox checkout and the Omnivox checkout selected by ~OMNIVOX_DIR~, including Omnivox's locked Rust dependencies and checksum-locked Flite and RuTTS source inputs. |

~make verify-windows-omnivox-toolchain~ prepares the cached Roslyn inputs,
builds the Docker image, and validates this boundary before compilation.  The
full target then builds Omnivox's two 32-bit helper sources deterministically,
builds native Windows Omnivox plus its RHVoice, Flite, and RuTTS helpers in the
container, and stages their licenses, provenance, and checksums.  The clean
target also builds Piper support and verifies that the pinned companion and
main executable identify the same Omnivox source commit.  A host Rust
installation, MinGW installation, Visual Studio, .NET SDK, or system eSpeak
installation is not an input to this release path.  RHVoice's native library,
languages, and voices remain external user-supplied runtime inputs.  Flite's
CMU US SLT voice is compiled into its checksum-locked helper.  RuTTS's built-in
male and female Russian voices are compiled from the checksum-locked 6.3.3
source; RuLex is not included.

After staging, the static verifier rechecks manifests, provenance, the
Windows-local copy, and all configured external inputs.  The separate live
verifier executes that exact Windows-local runtime, prewarms the bounded eSpeak
voice cache tied to the verified content-addressed data, discovers the compiled
Flite and RuTTS voices, and requires real WAV synthesis from both helpers.
Use ~make verify-windows-omnivox-live~ to repeat only the executable smoke gate.

~OMNIVOX_PIPER_MODEL~ is an optional staging input, not a release payload.
When supplied, the target validates the adjacent configuration, copies both
files into a content-addressed Windows-local model cache, records their hashes,
and writes the Windows path used by the launcher.  The recursive runtime
manifest deliberately excludes model files.  A different model therefore
creates a distinct local build identity without changing the pinned companion.
The public-domain engineering voice used in Omnivox CI is approved only for
that bounded test purpose and is not a model-distribution default.

Maintainers testing tracked Emacsvox or Omnivox changes may use
~make windows-omnivox-dev~.  That target records both worktree-diff hashes and
labels the result as a development build.  It builds the RHVoice, Flite, and
RuTTS companions but omits Piper, because the currently pinned Piper companion
must not be mixed with later Omnivox source.  It also rejects
~OMNIVOX_PIPER_MODEL~.  Advance the checked Piper companion and source commit
together before these integrations enter the clean release path.  See
~servers/omnivox-release/README.org~ for the pinned toolchain, licensing,
provenance, and restaging contract.

To test Piper before that release-pin advance, commit and push a clean Omnivox
revision and run its ~Piper Native Validation~ workflow.  Download the
~omnivox-piper-windows-x64~ artifact, which contains the companion archive and
~piper-sha256sums.txt~, then stage it with a reviewed model:

#+begin_example
OMNIVOX_PIPER_DEVELOPMENT_ARCHIVE=/absolute/path/to/omnivox-1.7.1-piper-windows-x64.zip \
  OMNIVOX_PIPER_DEVELOPMENT_ARCHIVE_SHA256=64-character-sha256 \
  OMNIVOX_PIPER_MODEL=/absolute/path/to/voice.onnx \
  make windows-omnivox-piper-dev
#+end_example

This is a development-only bridge, not a release-pin bypass.  It verifies the
outer archive hash, rejects unsafe archive members and symbolic links, checks
the companion's internal manifest, and requires its source provenance to name
the exact clean Omnivox ~HEAD~ and the Windows MSVC target.  The staged runtime
records the artifact hash and companion tree hash and labels the companion
~github-actions-native-development-build~ with version ~development-ci~.  The
version-looking archive filename comes from Omnivox's current package metadata
and does not assert that post-tag code was released.  The final live gate loads
the separately cached model and requires Piper to enumerate that voice and
synthesize a non-empty WAV.

The ordinary ~windows-omnivox-dev~ target remains appropriate for uncommitted
Omnivox work because it rebuilds all included companions locally and omits
Piper.  The CI-artifact target deliberately rejects a dirty Omnivox checkout:
commit and push the change, let the native workflow build that exact commit,
then use its new artifact.  Emacsvox itself may contain tracked changes; their
diff hash remains part of the local runtime identity.

After one complete development runtime has been staged, use
~make windows-omnivox-main-dev~ for changes confined to the main Rust server or
its main-only audio output.  This guarded path uses the same pinned toolchain
to rebuild only ~omnivox.exe~, derives a new content-addressed runtime from the
current hash-verified development payload, records the original complete build
and reused manifest in provenance, hard-links the unchanged payload, and runs a
focused live check of the new Windows main executable.  It refuses reuse when
helper, helper-protocol, dependency, toolchain, or companion inputs changed; in
that case rerun ~make windows-omnivox-dev~.  Run
~make verify-windows-omnivox-runtime verify-windows-omnivox-live~ when a
complete development audit is useful.  The clean ~make windows-omnivox~ release
path always rebuilds and verifies every payload and never uses incremental
reuse.

The development target accepts ~OMNIVOX_RHVOICE_LIBRARY~ and
~OMNIVOX_RHVOICE_DATA~ together, plus an optional
~OMNIVOX_RHVOICE_CONFIG~ directory.  It resolves WSL or Windows absolute paths,
requires the C API DLL and the language/voice data layout, records content
digests in provenance and machine-local Windows path pointers beside the
selected runtime, and leaves all RHVoice files external.  Those pointers let
the launcher restore the variables for every fresh Emacsvox process.  The
runtime verifier rejects missing or changed external inputs.  Omitting all
three variables leaves RHVoice unconfigured without affecting Flite, RuTTS,
or the other engines.  RuTTS requires no external installation; the staged
helper always provides its built-in male and female Russian voices without
RuLex.

Do not bypass the Omnivox release target manually or clean either repository
to make its release guard pass.  Use ~make windows-omnivox~ only for the
reproducible clean-release path documented in the user-facing WSL2 route.

** Aural experiments and guided changes
:PROPERTIES:
:TEXINFO_NODE: no
:END:

Physical experiments reuse the tuner with an exact engine/voice selector,
an immutable opening snapshot, a mutable working style, and undo history.
They do not modify the palette registry, active palette, or route profile
until the user explicitly keeps a reviewed result.  Navigation and Help use
the working style.  A failed exact preview must be reported before ordinary
speech can provide navigation fallback; a fallback sample must never be
reported as the requested physical voice.

Keep proposals snapshot the destination palette and routing profile as well
as the proposed result.  Check those snapshots before writing, and retain
separate completion flags for palette write, route write, and route apply.
A retry must not repeat a successful write.  If routing saves but application
fails, keep that distinction visible and retry the application step.  Never
report the combined operation complete while one selected destination failed.
Portable style storage and machine-local routing storage remain separate.

Labelled comparisons use one controlled preview sequence, with identical
sample text and separately configurable labels.  Each sequence belongs to
its speech lane.  Stopping that lane cancels remaining entries and invalidates
late callbacks; stopping foreground speech must not cancel notifications.
Requested parameters and advertised capabilities are distinct from playback
reports.  Do not fabricate exact effective numeric values when the adapter
reports only support, acceptance, or degradation.

Guided feedback changes use existing declarative rules and registered facts.
The draft selects a component, matching criteria, and lifetime separately;
preview dynamically overlays the intended layer without mutating live rules.
Explicit buffer-rule snapshots in captured context must also be overlaid.
Generated IDs remain stable for the matched component; new rules follow
existing explicit order within the layer.  Apply checks a Current-item source
guard and refuses to overwrite another unfinished editor for the same scope.
Historical selection chooses a frozen part when a transaction contains
several runs.  Original replay uses that part; proposed preview deliberately
resolves it with current rules and the captured buffer context.

Shared Help and offline task nodes preserve the original source and exact
return position.  New interfaces should use the shared parent modes and add
a task-node mapping to ~emacsvox-aural-ui-manual-nodes~.  Row action predicates
should hide operations that cannot apply to that row; this includes editing
built-in options and reordering items outside the active-order view.
