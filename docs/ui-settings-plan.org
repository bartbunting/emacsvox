* Interaction contract

Use focused Transient menus for actions and repeated adjustments. Use
searchable, sortable lists for inventories such as voices, palettes, rules,
and sound packs. Use expandable Outline details for explanations, inheritance,
effective settings, and diagnostic evidence.

- Up/down selects items. Plain left/right changes menu sections.
- Shift-left/right adjusts a selected numeric control. Enter activates a
  choice or edits an exact value. Announce bounds and unavailable controls.
- Announce menu and section names on entry or section changes. Repeated
  adjustments speak the new value promptly and replace obsolete feedback.
- Show effective values, available choices, scope, and where a value comes
  from: a buffer override, mode policy, global default, palette, or engine.
- Offer only scopes the underlying setting supports. Explain when a global
  operation also changes the originating buffer.
- Make saving, applying, selecting a palette, and restarting speech distinct
  actions. Menu entry and preview must not silently persist changes.
- Provide representative previews and a reliable stop action. Audit existing
  keys before assigning preview, stop, or save keys in another interface.
- Return to the originating menu or list with its selection, filters, source
  context, and draft intact. Preserve existing editor decisions about keeping
  or discarding unsaved work. Whole-stack exit remains available.
- Validate the captured source item before contextual edits. Handle changed
  text, closed buffers, unavailable voices, and missing capabilities clearly.
- Explain what Reset restores: an inherited value, a mode policy, a standard
  value, or an engine default.

* Longer-term voice experience

** Listing and discovery

Keep clearly labelled views for physical voices and named palette voices.
Preserve filters, sort order, selected row, preview text, and originating buffer
across editing and return. Show useful availability and inheritance information
without repeating an entire engine or palette description on each movement.

** Common tuning

Begin with a small set of supported controls such as rate, pitch, pitch range,
and volume. Use the agreed arrows and exact-value editing. Preview the draft
and compare original/edited versions with the same sample and rate context.
An optional automatic-preview experiment must replace obsolete previews and
remain easy to stop; manual preview remains the initial acceptance path.

** Drafts, ownership, and saving

Retain drafts when returning to a browser. Explain whether an edit changes a
named voice wherever it is used or changes one contextual presentation rule.
Offer the existing save/apply, save-to-collection, experiment destination,
reset, and discard behaviours. Use private previews rather than temporarily
publishing the draft as a live voice.

** Fallback and native controls

Expose shared tuning first, then individual fallback adjustments and advanced
engine controls. Obtain controls, types, bounds, and qualified defaults from
the engine catalogue. Distinguish Follow shared/common settings, Set value,
and Engine voice default. Reordering choices must retain their adjustments.

Explain the physical voice that actually spoke, any fallback or degraded
capability, and the contextual settings that affected the result. Preserve the
accepted shared, choice, then context precedence. Relevant contracts are
[[file:adr/0016-complete-voice-preview.org][complete private preview]], [[file:adr/0017-per-fallback-voice-tuning.org][per-fallback tuning]],
[[file:adr/0018-unified-voice-palette-model.org][palette ownership and inheritance]], [[file:adr/0022-engine-described-voice-parameters.org][engine-described parameters]],
and [[file:adr/0026-palette-default-reading-voice.org][the palette default reading voice]]. Read all applicable ADRs before
implementation; these links are not a substitute for the repository rule.

* Longer-term editor improvements

Menu coverage and editor conversion are separate checkpoints. Give every
inventoried action a discoverable route first. Keep dedicated buffers for
voice, palette, sound, punctuation, and rule inventories rather than expanding
them into long Transient menus. Audit all existing Home actions before claiming
complete coverage; retiring Aural Home remains a separate decision.

After connecting each editor, evaluate its ordinary Emacs editing behaviour:

- Use searchable, sortable lists and preserve selection, filters, and return
  context. Use foldable Outline sections for structured details.
- Provide a clear major mode, standard movement and help, an accurate modified
  indicator, and undo appropriate to that editor's draft model.
- Audit existing bindings before adopting familiar save, finish, and cancel
  conventions. Saving, applying, previewing, and restarting must remain
  distinct when they have different effects.
- Retain unfinished drafts on ordinary return. Make destructive discard
  explicit and keep the existing save-failure recovery behaviour.
- Keep rare settings reachable through Customize or their specialist editor;
  record each deliberate exception to a focused menu.

These are proposed follow-on slices, not a completed conversion or an
authorization to rewrite all editors at once.

Persistence remains owned by existing subsystems. Ordinary defaults use
Customize; capitalization cues use personal aural rules; voices, palettes,
and other structured objects use their existing stores; punctuation definitions
are saved on the Omnivox host. Emacs pronunciation dictionaries use their own
file. Unsaved drafts remain session state. The implemented Changed settings view
separates loaded options and retained drafts and identifies storage boundaries.
Comparing those stores with disk or live host state remains deferred.

The punctuation connection opens the existing character/pronunciation table
from level/profile selection and preserves drafts on return. Saving and the
explicit speech-worker restart remain separate. The table remains the editor
for individual characters.

* Acceptance tasks and development cycle

Use complete tasks as milestones:

- Find an installed voice, audition it, tune a named draft, compare, save,
  and return to the source item.
- Distinguish a single capital from an all-caps word, tune each cue, and
  verify the chosen presentation after saving and restarting.
- Make coding punctuation more detailed while retaining the prose policy.
- Reduce notification sounds and verify which output changed.
- Change feedback for one heading, explain the winning rule, then restore it.
- Leave an unfinished draft, return later, and resume without losing edits.
- Find a setting by name or from the current buffer without knowing its key.

Implement one usable path at a time. Run affected tests and real graphical
checks where focus, layout, or keymaps matter. Build incrementally and verify
actual loaded paths before listening in a fresh normal Emacsvox session.
Commit accepted behaviour in small slices. Batch user documentation, generated
references, and broader checks at accepted milestones or before review.
Expand checks when shared behaviour changes or a failure warrants investigation.

* Maintaining this plan

When a new setting, cue, missing action, or awkward interaction is found:

1. Add it to the appropriate inventory section, or the findings queue below
   if its destination is still unclear. Name the concrete behaviour.
2. Record its existing command, option, cue, or editor when known; otherwise
   mark that investigation as open. Avoid inventing an underlying setting.
3. Record applicable scope, persistence, preview, and capability constraints.
4. Assign a milestone and a small acceptance task. Distinguish proposed,
   implemented, automatically checked, listening-accepted, and committed work.
5. Update this document when findings or milestones change. Keep test evidence
   concise and date completed checkpoints; do not turn it into a command log.

Plan-only discoveries can be recorded without regenerating the public manual.
The repository's documentation review gate still applies at review checkpoints.
Keep durable decisions in ADRs and accepted usage in the user manual when the
behaviour settles. Preserve earlier evidence without treating it as current
verification of subsequently changed code.
