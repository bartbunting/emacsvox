#+title: Emacsvox responsiveness and speech investigation
#+date: 2026-11-15

* Findings and fix order

Four reproducible performance problems deserve fixes. They run synchronously
in Emacs, so they can delay input as well as speech. The most severe work
happens before the speech submission boundary; fast Omnivox queue statistics
do not rule it out.

| Order | Finding | Severity | Measured effect |
|-------+---------+----------+-----------------|
| 1 | Comint final-line regular expression | P1 | 16 KiB line plus newline through the output filter: 2.48 seconds |
| 2 | Rebuilding source tables during navigation | P1 | Down Arrow in a 2,000-row Markdown table: 584 ms |
| 3 | Recopying unfinished Comint output | P2 | Building a 1 MiB unfinished line: 2.614 seconds cumulatively |
| 4 | Repeating missing ffprobe discovery | P2 | Cold scan of 40 local recordings: 1.476 seconds |

P1 means a substantial foreground stall on a plausible input. P2 means a
noticeable delay or accumulating cost under the stated conditions. These
priorities describe this audit, rather than existing issue-tracker labels.
Confidence in the four mechanisms is high. A deleted-file metadata cache
also needs cleanup, with lower practical urgency.

The recommended sequence is the small Comint regex correction, table snapshot
reuse, unfinished-output assembly, and one executable lookup per library scan.
The lookup correction is sufficiently independent and small to prepare alongside
the earlier fixes. Address deleted cache entries after that. Investigate backend
tail latency and styled speech preparation separately, using the boundaries
described below. Do not weaken speech ownership, cancellation, provenance,
presentation history, or text fidelity to obtain faster benchmark results.

This is an investigation. No application fix, dependency change, live reload,
configuration change, commit, or push was performed. The initial worktree was
clean. Only this report and its evidence were added.

* Confirmed: Comint final-line matching can block Emacs for seconds

Severity P1; confidence high. Affects Shell and other Comint process output
after the integration is loaded. A single long newline-terminated line, such
as unwrapped JSON or other tool output, is sufficient. The work also runs before the automatic-feedback check, so disabling
automatic speech does not bypass it.

Locations: [[file:../../lisp/integrations/emacsvox-comint.el::259][split-final-prompt]], lines 278 and
317 in [[file:../../lisp/integrations/emacsvox-comint.el::285][partition-output]],
[[file:../../lisp/integrations/emacsvox-comint.el::334][present-process-output]], and the synchronous
[[file:../../lisp/integrations/emacsvox-comint.el::801][comint-output-filter advice]].

Both searches ask the regex engine to find the final newline-free suffix,
anchored at the end, starting its search at the beginning of the string.
For a long line followed
by a newline, repeated starting positions scan and fail across the line,
producing quadratic work. This search is then repeated by partitioning.

| Line bytes | Without newline, median ms | With newline, median ms | Newline range ms |
|------------+----------------------------+-------------------------+------------------|
| 256 | 0.006 | 0.477 | 0.410–0.559 |
| 1,024 | 0.017 | 8.148 | 7.091–11.259 |
| 4,096 | 0.079 | 130.959 | 118.390–183.929 |
| 8,192 | 0.152 | 636.161 | 524.730–743.605 |
| 16,384 | 0.388 | 2,334.867 | 2,286.096–2,398.549 |

There were 20 timed repetitions per smaller case and 5 at 16 KiB. No GC occurred
inside these measured blocks. An earlier oversized disposable benchmark timed
out; interrupting that test process captured its stack in =string-match=.
The running Emacs was not interrupted. A separate disposable Comint buffer
with a real pipe process exercised the complete advised =comint-output-filter=
with automatic speech disabled. It inserted the correct 16 KiB line and took
2,481.093 ms median, 2,428.502–2,612.034 ms range, over five timed runs with no
GC. This establishes the foreground filter cost beyond the partition helper.

Reproduce with [[file:data/2026-11-15-performance-audit/streams.el][streams.el]]. A scoped diagnostic substitution of a linear
last-newline search reduced the 16 KiB helper case to about 0.008 ms and
preserved output/pending values for seven short prompt/line examples. That is
a mechanism check, not a production patch or complete correctness proof.

Proposed small fix: use one private linear final-line-start helper at both
sites. Preserve text properties, recognized prompts, split prompt padding,
carriage-return replacement, Unicode, and pending-output behavior. Avoid simply skipping
partitioning when speech is disabled: prompt processing can also update Shell
directory tracking.

Existing coverage: =test/emacsvox-comint-tests.el= checks incomplete lines,
trailing and split prompts, carriage motion, and feedback controls. It does
not protect large-line scaling. Add long newline-terminated lines and chunk
boundaries, compare the complete inserted buffer and semantic events, and check
the disabled/background path. Run the Comint suite, incremental compilation,
byte-code preflight, and fresh-Emacs verification before trying a fix live.

* Confirmed: table navigation rebuilds the entire table repeatedly

Severity P1 for large Markdown tables; P2 for the measured Org case; confidence
high. The trigger is ordinary movement while source table reading is active.
It affects source tables even when no speech is synthesized.

Locations: [[file:../../lisp/core/emacsvox-table-reader.el::895][source-cell]] rebuilds every logical row,
cell and position. [[file:../../lisp/core/emacsvox-table-reader.el::679][move]] requests snapshots before and
after moving, and [[file:../../lisp/core/emacsvox-table-reader.el::563][post-command]] requests another.
[[file:../../lisp/integrations/emacsvox-markdown.el::899][Markdown region discovery]] walks rows in both
directions, checking candidate syntax, while
[[file:../../lisp/integrations/emacsvox-markdown.el::965][cell cleaning]] creates a temporary buffer even
for plain text. The Org adapter enters the same reconstruction path at
[[file:../../lisp/integrations/emacsvox-org.el::2740][emacsvox-org--table-snapshot]].

Tables contain four columns, a header/delimiter, and 10 to 2,000 data rows.
The 2,000-row source is 95,832 characters, so a very large document is not
necessary. Uninstrumented batch results with pinned Markdown 2.9-alpha:

| Data rows | Org move plus post-command, median ms | Markdown move plus post-command, median ms |
|-----------+---------------------------------------+--------------------------------------------|
| 10 | 0.173 | 2.245 |
| 100 | 2.287 | 22.088 |
| 500 | 10.331 | 111.688 |
| 2,000 | 27.343 | 413.954 |

The actual graphical key path does more work than the explicit helper sequence.
Using the installed Markdown 2.8-alpha file and the live exec-path in a
disposable graphical Emacs:

| Data rows | Org Down Arrow median/range ms | Markdown Down Arrow median/range ms |
|-----------+--------------------------------+-------------------------------------|
| 500 | 15.840 / 14.052–18.768 | 149.371 / 122.162–234.487 |
| 2,000 | 65.284 / 59.055–70.481 | 583.633 / 507.586–660.271 |

Each graphical block has 10 samples after warm-up and fontification. Eight
collections occurred across the ten 2,000-row installed-Markdown samples;
there were none in Org. This is genuine allocation as part of the operation,
not an instrumentation-only pause. A separate pinned-package graphical run
also reproduced the scaling; it is not a controlled package-version comparison.

A separate call-count probe for one graphical Down Arrow in the pinned
2,000-row table observed four full =source-cell= builds, 32,016 cell-cleaner
calls, 20,026 pipe-span calls, and 12,022 candidate-row tests. Advice used to
count calls was removed afterward. [[file:data/2026-11-15-performance-audit/graphical-counts.eld][Counts]] and
[[file:data/2026-11-15-performance-audit/graphical-live.eld][installed-package timings]] are retained.

Proposed first fixes: share a logical matrix and source positions within a
single command, avoid full reconstruction solely to check whether point left
the table, and add a safe plain-cell fast path. A diagnostic plain-cell shortcut
alone left substantial cost, so that shortcut is insufficient. A longer-lived
cache should be a later, separately verified change keyed to actual source or
render revisions. Do not assume =syntax-propertize(point-max)= reparses every
character on every call; the measured repeated table traversal is enough to
explain the problem.

Risks include stale positions after edits, escaped pipes, code spans/fences,
link labels, titles, blank/ragged rows, narrowing, and rendered layout changes.
Reuse must preserve complete cell text and avoid modifying or aligning source.
Verify real graphical movement, entry/exit/suspension, edits between movements,
and source/render invalidation. Existing table, Org, Markdown and Agent Shell
tests cover many semantics and visual cases. The older 32/256-row benchmark
does not protect this 2,000-row key path, and is not a compatible before/after
baseline for these measurements.

Agent Shell's rendered-table parser is cheaper but still repeats work: a
500-row rendered table snapshot took about 7.4 ms, and its suspended-table
post-command path about 8.2 ms. Check that path when designing snapshot reuse,
without treating ordinary Agent Shell navigation as equally expensive.

* Confirmed: unfinished Comint lines accumulate repeated copying

Severity P2; confidence high. Affects automatic output speech when a process
emits a growing line in chunks without a newline, recognized prompt, or
carriage-return replacement. This is separate from the final-line regex issue.

[[file:../../lisp/integrations/emacsvox-comint.el::300][partition-output]] concatenates the complete pending prefix with
each new chunk, copies its plain text, and examines it again. Pending output
has no explicit length bound. Holding the unfinished line is intentional;
repeatedly copying its entire prefix makes total assembly quadratic.

| 4,096-byte chunks | Final pending size | Total assembly median ms | Range ms |
|-------------------+--------------------+--------------------------+----------|
| 16 | 64 KiB | 11.063 | 9.722–13.656 |
| 64 | 256 KiB | 177.601 | 167.619–192.282 |
| 256 | 1 MiB | 2,613.577 | 2,514.870–2,643.241 |

These are cumulative times for all chunks, not one 2.6-second callback. The
buffer retains the final pending string until it can be emitted or cleared.
This is not evidence of an unrelated lost-reference memory leak. Across five
1 MiB assemblies there were 31 collections at the configured threshold.

Proposed fix: retain incremental chunks or a private accumulator and track
the final-line boundary, avoiding repeated full-prefix copies. Decide an
explicit bounded partial-line delivery policy if output must be streamed
before a delimiter; do not truncate or silently drop content. That policy is
more behavior-sensitive than the first regex fix and should be reviewed
separately.

Existing coverage checks short partial lines and flushing, but not sustained
growth. Verify identical event text/order across arbitrary chunk divisions,
split prompts, final process exit, carriage returns, disabled/enabled speech,
and buffer cleanup. Include a size series and allocation counts as an external
performance check rather than a fragile hard millisecond unit-test limit.

* Confirmed: sound-library discovery repeats slow missing-tool searches

Severity P2; confidence high. Opening or refreshing the library after metadata
cache misses calls [[file:../../lisp/ui/emacsvox-sound-library.el::77][scan]] synchronously from the UI.
For every file, [[file:../../lisp/ui/emacsvox-sound-library.el::66][duration]] calls =executable-find "ffprobe"=.
The program is absent in this environment. The live exec-path contains
31 directories, including 17 Windows mount paths; repeated negative searches
cross those filesystem boundaries.

With the exact live exec-path, one missing-tool lookup took a median 31.184 ms
(24.861–40.037 ms, 20 samples). Scanning 40 unique valid local 0.1-second WAVs
with an empty metadata cache took a median 1,476.083 ms
(1,330.984–1,547.656 ms, five samples). A separate counter confirmed 40
ffprobe lookups for 40 files. No ffprobe subprocess was launched.

The initial shell-environment series used a different, 36-entry path:
1 file took 25.322 ms, 10 took 318.205 ms, and 40 took 1,113.956 ms cold.
The warm 40-file scan took 21.117 ms. Do not compare these as matched runs
against the exact-live-path series.

Proposed small fix: resolve ffprobe once per scan and pass the result to
metadata extraction, including a cached negative result for that scan only.
A scoped diagnostic substitution produced the same recording list and digests
with roughly 22 ms cold scans. Recheck in a controlled before/after run after
implementation. Preserve file stamps, digest/deduplication, missing-duration
behavior, and path changes between scans.

If ffprobe is present, the current =call-process= is also synchronous and has
no explicit deadline. A hung tool or slow recording is a source-level risk;
that configuration was not reproduced. Bounded asynchronous metadata is a
separate improvement, not a prerequisite for the simple negative-lookup fix.

Existing =test/emacsvox-sound-library-tests.el= fixtures replace the duration
function, so they do not exercise this discovery cost. Add a missing-tool test
that counts executable lookups as files increase, plus file-change and
executable-path invalidation checks. Verify library entry, refresh/filtering,
and prompt responsiveness in a graphical Emacs.

The same global cache only inserts entries; scan does not remove entries for
deleted files or former library roots. This is a P3 retention problem with
high confidence in the mechanism and low current practical urgency. A disposable
lifecycle probe scanned five files, deleted them, and rescanned: visible
recordings fell from five to zero while all five cache entries remained.
The probe suppressed duration lookup and did not measure retained bytes or
establish a contribution to foreground stalls. Prune
entries during a completed scan using an explicit root policy, preserving
metadata still needed by other roots. Existing library coverage does not assert
that deleted metadata is removed. A lifecycle test should scan, delete,
rescan, switch roots, and check both visible recordings and retained entries.

* Other measured costs and unverified suspects

** Speech-output bursts copy the remaining suffix repeatedly

Priority P3 pending representative burst evidence. Confidence is high in the copying mechanism, lower in its current practical
impact. [[file:../../lisp/speech/tts-lifecycle.el::945][tts--consume-process-lines]] removes each line by copying
the entire remaining string, and drains complete input in one callback.
An ignored-handler fixture took 0.064 ms for 100 lines/3.8 KB, 4.293 ms
for 1,500 lines/57 KB, and 72.213 ms for 4,000 lines/152 KB; the latter
ranged from 57.325 to 102.600 ms. This excludes decoding and real callbacks.

The live =read-process-output-max= is 65,536, so the 152 KB case requires a
larger chunk or pending/nested accumulation. Existing fragment and queue
bounds prevent unlimited retained input. This is not a demonstrated cause of
ordinary live delays. Consider an offset-based splitter and bounded drain
budget if representative burst captures establish a need. Preserve
consume-before-callback ordering, nested input, cancellation, terminal records,
process death, and exception recovery. Existing lifecycle tests cover many of
those cases; add realistic bursts and ordering checks before changing it.

** Styled speech preparation remains allocation-heavy

P2 preparation cost for the measured styled response, with high confidence
in the fixture result; the contribution to any particular live delay is
unverified. The trigger is submitting text with many style runs, independent
of the size of the buffer holding it.

The existing =test/profile-delivery.el= was rerun with compiled Emacsvox,
the pinned dependency tree, 128 MB GC threshold, five warm-ups and three
20-sample rounds. It renders real Magit/Org/Agent fixtures before timing,
but mocks native capabilities and wire delivery. Magit 83-byte preparation
had round medians near 1.1–1.2 ms; Org 137-byte preparation near 1.7–2.0 ms.
A styled 4,041-byte Agent response took roughly 46–50 ms, with one collection
per 20-sample block. Retained transport owners returned to zero.

A separate three-iteration instrumented run counted 160 anchor resolutions
and 159 voice compilations per styled response. Inclusive function timings
overlap and include instrumentation overhead; they cannot be summed into an
end-to-end breakdown. The result supports the existing allocation diagnosis,
not a newly established regression or a claim about large-buffer navigation.

Potential fix: share exact repeated resolution inputs within one synchronous
preparation, after proving all rule, palette, context, face, naming, routing,
registration and interruption inputs match. Avoid a global memo keyed only by
visible text or voice name. Keep history/provenance and retain ownership/error
checks. The saved =delivery-profile.eld= and =delivery-stages.eld= distinguish
uninstrumented latency from instrumented counts. Profile history limit was 20,
whereas the live limit is 100; rendered setup and native speech are excluded.
Existing preparation, replay and delivery tests protect output semantics and
ownership. Keep the profiler as a separate performance comparison and verify
identical concrete actions, history and failure cleanup after any reuse change.

** Legacy explicit voice queries can block without a deadline

Potential P2 when local discovery is slow or hangs. Confidence is high that
the synchronous path has no deadline, but its current latency is unmeasured.

[[file:../../lisp/speech/omnivox-discovery.el::82][omnivox-query-voices]] invokes synchronous =process-file= for
local discovery. Explicit refresh and cold legacy voice-selection commands
can reach it. Modern inventory-based UI uses the asynchronous path. No hung
local discovery was induced, so this is an unverified availability risk.
Prefer the existing bounded inventory mechanism when adapting these callers;
preserve their public return/error contract rather than removing compatibility
commands. Verify missing executables, malformed replies, timeouts, reconnects,
and both local and remote configurations.

* Passive speech latency across subsystem boundaries

The existing Aural log and one archive for Emacs PID 3376 were read offline,
along with the selected main/notification worker logs. Private text and buffer
names were excluded from saved evidence. There were 56,829 client events,
4,692 submission starts/completions, 11,114 dispatch sends/terminal observations,
and 10,962 observed mixer onsets. Dispatch IDs were matched to native request
identifiers, scoped to the selected worker lanes. The logs span earlier work
and live reloads in this session, so they are historical observations, not a
controlled benchmark of the current commit.

| Boundary | Samples | Median ms | p95 ms | Maximum ms |
|----------+---------+-----------+--------+------------|
| Aural submission start to API completion | 4,692 | 9.994 | 18.944 | 240.403 |
| Client dispatch send to observed mixer onset | 10,962 | 15.322 | 68.664 | 1,195.993 |
| Main worker queue wait | 10,927 | 0.027 | 0.123 | 440.291 |
| Main admission to audio queued | 10,886 | 4.861 | 34.229 | 1,193.029 |
| Main admission to mixer source | 10,870 | 12.252 | 40.867 | 1,194.955 |

These rows are different populations and overlapping intervals. Do not add
their medians or infer complete key-to-audio latency. Admission-to-audio
includes scheduling/engine preparation and initial synthesis, rather than
isolating pure synthesis CPU. Mixer-source onset is an internal audio boundary,
not proof of audible device output. Native worker elapsed time can include
progressive playback and cancellation, so it is not pure synthesis time.

Specific unresolved examples, with durations in milliseconds:

- Main dispatch 2751, DECtalk: queue wait 4.517; first audio queued 1,193.029;
  mixer onset 1,194.955; cancelled terminal at 2,744.956. This delay is mainly
  before initial audio, not waiting for queue admission.
- Main dispatch 4759, Eloquence: queue wait 266.514; mixer onset 413.520;
  cancelled terminal at 443.620. Dispatch 5992 also waited 233.593 ms in queue.
  These justify examining cancellation/drain and engine scheduling under load;
  cancellation itself can be normal navigation.
- Dispatch 9173: Emacs observed onset after 490.772 ms while the matched server
  duration was 13.434 ms. Across matched onsets the client-minus-server duration
  median was 1.435 ms, p95 31.009 ms, and maximum 477.338 ms. The excess includes
  IPC, buffering and Emacs callback scheduling/observation. It does not identify
  GC, the splitter, or audio hardware as the cause.

Do not subtract absolute timestamps from different process clocks. These
comparisons use durations measured inside each process. Further tests should
correlate action/source extraction, submission, dispatch, worker generation,
engine warm/cold state, cancellation acknowledgement, initial audio, and Emacs
callback/GC timing in a disposable session. Test rapid replacement and both
lanes while preserving the final intended utterance. The installed binary's
version/path were verified; an arbitrary sibling Omnivox checkout was not
assumed to match its implementation. No native binary was rebuilt in this audit.

Diagnostics also cost something: 12 short event writes took 1.484 ms median,
1.328–2.470 ms range, versus about 0.003 ms with logging disabled on the local
Linux filesystem. This excludes rotation, huge text, and slow filesystems.
Logging was enabled in the live session. It cannot explain the reproduced
silent Comint regex or table stalls by itself.

* Paths checked without a new problem in the exercised cases

- Agent fragment classification, previous-response location, source-line copy,
  and input synchronization were measured on genuinely rendered fragments at
  about 45 KB, 448 KB, and 2.24 MB. The fixture asserts a nonempty response-body
  location. Previous-response lookup stayed around 0.05–0.07 ms; local helpers
  were approximately 0.001–0.002 ms. This excludes full typing, streaming
  renderer work, redisplay, speech preparation and playback.
- Character echo and deletion advice use local character/word extraction.
  File/buffer changes announce their destination through mode-line/context
  paths. Relevant core regression tests passed. This does not provide a
  controlled full-profile typing or file-open latency guarantee.
- Completion source inspection uses the current candidate, while settings
  search uses a fixed destination catalogue. Graphical menu/Help/return-path
  cases passed in the qualified harness below. No document-size-dependent
  traversal was established there.
- EAT snapshots use visible display bounds rather than all scrollback. Its
  burst and input cases passed in the integration gate. Notmuch MIME traversal
  has explicit node/depth budgets, and search feedback has guards against
  irrelevant callbacks. These protections do not establish a throughput bound
  for every terminal redraw or every mailbox.
- The global reading-place post-command hook compares the current buffer and
  window. Hook/advice registration generally uses named entries; the notification
  cleanup timer is initialized through =defvar=, not recreated on every load.
  No duplicate-registration defect was demonstrated. Agent input sync does
  request a mode-line refresh; its complete redisplay cost remains unmeasured.
- At the live idle snapshot, tracked dispatch, marker, lifecycle and prepared
  owner/preparation tables were empty; both notification queues were empty.
  Presentation history was at its configured bound of 100. The session had run
  about 14 hours and included several large buffers. This is useful cleanup
  evidence, not proof that every cache is bounded or that no session can leak.
- The intentional interruptible isearch debounce and explicitly requested
  synchronous external operations were distinguished from unexpected recurring
  work. No new causal defect was established merely from finding a blocking
  primitive in a source search.

Important limits remain:

- No listening acceptance, physical output-device timing, Windows-native GUI
  interaction, macOS testing, or alternate Emacs-version matrix was performed.
- The normal profile and native speech workers were not restarted. Full cold
  startup, saved-library registration, network/remote startup, and package/init
  effects were inspected but not given controlled timing runs.
- Full typing/deletion, completion over large external candidate sources,
  arbitrary file/remote filesystem opens, and all installed major modes were
  not benchmarked end to end. Passing local helpers does not fill those gaps.
- Large-table tests use four plain columns. Complex markup, many overlays,
  long individual cells, and edits/render changes need additional acceptance
  checks for any proposed cache or parser change.
- Long-running behavior was sampled from an existing session rather than a
  controlled multi-hour soak. Per-submission ownership cleanup is covered;
  every integration's subscriptions, buffers and caches were not exhaustively
  proven bounded.
- The pre-audio backend outliers and delayed client observations remain
  unresolved. No claim is made that fixing the confirmed Lisp stalls removes
  every perceived speech delay.

* Reproducing the measurements

The saved scripts are disposable investigation inputs, not application tests
or startup code. Run them from the source commit recorded above with the
selected Emacs and verified dependency tree. Outputs go to a private temporary
directory; no normal profile or audible backend is started.
The published measurements use shortened paths for loaded libraries.
Versions and content digests are recorded in the accompanying provenance.

#+begin_src sh
export EMACSVOX_AUDIT_DEPS="$HOME"/.cache/emacsvox/test-deps/menu-20261113-emacs-31.0.90
export EMACSVOX_AUDIT_OUTPUT=$(mktemp -d /tmp/emacsvox-audit-replay-XXXXXX)
audit_inputs=docs/benchmarks/data/2026-11-15-performance-audit
"${EMACS:-emacs}" -Q --batch -l "$audit_inputs/tables.el"
"${EMACS:-emacs}" -Q --batch -l "$audit_inputs/streams.el"
python3 "$audit_inputs/generate-fixtures.py" "$EMACSVOX_AUDIT_OUTPUT"
"${EMACS:-emacs}" -Q --batch -l "$audit_inputs/library.el"
"${EMACS:-emacs}" -Q --batch -l "$audit_inputs/navigation.el"
"${EMACS:-emacs}" -Q --batch -l "$audit_inputs/interaction-probes.el"
GDK_BACKEND=x11 timeout --kill-after=5s 60s xvfb-run -a \
  -s '-screen 0 1280x1024x24' "${EMACS:-emacs}" -Q \
  -l "$audit_inputs/graphical.el"
#+end_src

The default scripts select pinned dependencies. The graphical script can
optionally read =live-environment.json= from the private output directory
when =EMACSVOX_AUDIT_LIVE_CONFIG= is set; that input must specify the intended
Markdown file and exec-path. The private snapshot used for this audit remains
under =/tmp/emacsvox-audit-20261115-po8l8cdj/= and was not copied into the
repository. Installed-package results are retained separately from pinned ones.
Rerunning on changed dependencies is a new observation, not an exact replay.

=candidate-probes.el= temporarily substitutes the suspected mechanisms and
restores them on exit. It is a diagnostic aid, not an approved implementation.
The saved =graphical-count.el= repeats the separate table call-count probe;
=focused-graphical-final.el= records the supplemental graphical setup. To use
the same Vertico revision, set =EMACSVOX_AUDIT_VERTICO= to the directory
containing Vertico 20260913.1525.
The existing delivery profiler supports =EMACSVOX_DELIVERY_LOAD=compiled=,
=EMACSVOX_PROFILE_DEPS=, =EMACSVOX_DELIVERY_GC_BYTES=128000000=, and
=EMACSVOX_PROFILE_ITERATIONS=20=. Set =EMACSVOX_PROFILE_STAGES=1= only for
separate instrumented counts. Review the raw samples and configuration before
making comparisons.
