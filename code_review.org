#+DATE: 2026-10-07
#+OPTIONS: toc:nil

* Summary

This review targets Emacsvox at =41828cfe5600= and Omnivox *1.16.0* at
=d4f28f32b127=. All Rust checks and the helper reproduction used that 1.16.0
source. Existing live workers were inspected only to establish runtime identity.

Four correctness defects were reproduced in isolation. A blocked helper write
can prevent Stop from returning. Empty pronunciation matches can loop forever.
Nested list speech can erase the surrounding utterance. Unanswered inventory
requests accumulate without a deadline or general retirement cleanup. The initial
Windows cancellation finding was withdrawn after tracing the server's existing
native-call isolation layer; see the architecture assessment.

The architecture has useful protections: immutable submission data, explicit
speech lanes, bounded admission, process-owned dispatch identities, and prevention
of fallback replay after audio commitment. The highest-value changes are narrow
repairs to cancellation and ownership at the boundaries those protections miss.
Existing test gates passed; that does not establish audible speech correctness.

No fixes were implemented during the review. Locations describe the reviewed
commits; subsequent fixes may move the source lines. Implementation results are
recorded separately under Verification. Existing unrelated work is preserved.

* Correctness Findings

** [High] A blocked helper write can prevent Stop from returning

- Confidence :: Confirmed bug in Omnivox 1.16.0. Reproduced with buffered synthesis and a real child-process pipe; the progressive path has the same locking pattern.
- Location :: [[file:../omnivox/omnivox-tts/src/helper_engine.rs::1807][helper_engine.rs:1807]], [[file:../omnivox/omnivox-tts/src/helper_engine.rs::1968][helper_engine.rs:1968]], [[file:../omnivox/omnivox-tts/src/helper_engine.rs::441][helper_engine.rs:441]], and [[file:../omnivox/omnivox-tts/src/helper_engine.rs::2269][helper_engine.rs:2269]]. The server calls engine cancellation synchronously at [[file:../omnivox/omnivox-cli/src/server.rs::1719][server.rs:1719]] and [[file:../omnivox/omnivox-cli/src/server.rs::3328][server.rs:3328]].
- Trigger :: A helper completes its handshake, then stops consuming stdin. A sufficiently large synthesis request fills the pipe. Word-based chunking does not bound the byte length of a single word; see [[file:../omnivox/omnivox-cli/src/text.rs::55][text.rs:55]].
- Impact :: Synthesis holds the dispatch mutex while writing. Stop waits for that mutex, so the protocol reader cannot finish Stop or handle subsequent commands. Audio cancellation happens before this wait; the demonstrated failure is blocked recovery and subsequent speech, not continued playback of old audio. The other Emacsvox speech process remains independent.
- Evidence :: The synthesis request becomes active only after the blocking send. The response timeout therefore cannot bound this write. Stop also sends cancellation before starting its cancellation watchdog. In the isolated probe, a helper stopped reading after its descriptor, a 128 KiB single-word request was submitted, and Stop was requested after 100 milliseconds. With a 100-millisecond synthesis idle timeout, Stop still had not returned after 750 milliseconds. Both threads finished only when the fixture helper exited at three seconds.
- Recommendation :: Bound request writes and cancellation writes, including waits for their locks. Start an independent termination path before potentially blocking I/O. The existing [[file:../omnivox/omnivox-tts/src/helper_engine/deadline.rs::5][connection deadline helper]] is a useful precedent. Preserve single-request ownership, child reaping, and protection against stale watchdogs terminating a replacement connection. A byte limit can reduce exposure but does not replace cancellation of blocked I/O.
- Regression coverage :: Use a real helper pipe that stops reading after handshake. Exercise buffered and progressive submission, blocked synthesis writes, blocked cancellation writes, prompt Stop completion, and successful subsequent speech. Verify that all fixture children and watchdogs terminate and no cancelled audio is replayed.

Observed probe output:

#+begin_src text

synthesis_result=Err(SynthesisFailed("helper protocol I/O failed: Broken pipe (os error 32)"))
cleanup_completed_after_ms=3000
#+end_src

** [High] Empty pronunciation matches can loop indefinitely

- Confidence :: Confirmed bug.
- Location :: [[file:lisp/tts-speak.el::1731][tts-speak.el:1731]], especially the loops at lines 1739 and 1745. Entry creation accepts the input at [[file:lisp/emacsvox-pronounce.el::131][emacsvox-pronounce.el:131]] and [[file:lisp/emacsvox-pronounce.el::432][emacsvox-pronounce.el:432]]; template entries are defined at [[file:lisp/emacsvox-pronounce.el::404][emacsvox-pronounce.el:404]].
- Trigger :: A dictionary contains an empty literal key, or a template matcher repeatedly returns a zero-width match, such as =re-search-forward= with =$=. Entry creation and application do not reject or safely advance these matches.
- Impact :: Speech preparation does not terminate. An empty replacement spins; a nonempty replacement can also grow the scratch buffer indefinitely. Emacs cannot complete the interaction normally, and a saved dictionary repeats the problem on later speech attempts.
- Evidence :: Source-loaded batch probes used the public local-entry function, then called =tts-apply-pronunciations=. Both an empty literal replaced with =x= and an end-of-buffer regexp replaced with =x= reached a guard on replacement attempt 21. Each had already expanded the six-character input to 26 characters. The guard deliberately stopped the reproduction before it could hang.
- Recommendation :: Reject empty literal keys at interactive, programmatic, and dictionary-import boundaries. Also defend application against existing invalid entries. Give zero-width template matches an explicit progress rule that terminates at the end of the original input, or reject them with a useful error. Preserve legitimate deletion of nonempty matches; checking only whether point advanced would incorrectly reject deletion.
- Regression coverage :: Cover empty literal keys with empty and nonempty replacements, zero-width regexp matches at the beginning and end, mixed consuming and empty matches, and ordinary deletion. Assert termination and resulting text, not just validation helper calls.

** [Medium] Nested list speech overwrites the outer utterance

- Confidence :: Confirmed bug under reentrant speech preparation.
- Location :: [[file:lisp/tts-speak.el::4283][tts-speak.el:4283]] and the erase at [[file:lisp/tts-speak.el::4290][tts-speak.el:4290]]. Ordinary speech already protects nested scratch buffers at [[file:lisp/tts-speak.el::4178][tts-speak.el:4178]].
- Trigger :: A pronunciation callback, or another callback during speech preparation, calls the public =tts-speak-list= function while the outer transaction uses the named scratch buffer.
- Impact :: List assembly erases the outer text before the nested call reaches the normal scratch-buffer protection. The outer transaction can queue truncated or unrelated text without reporting an error.
- Evidence :: A real outer =tts--speak-transaction= prepared =prefix-long-enough outer suffix=. Its pronunciation callback called =(tts-speak-list '("x"))= and returned =replacement=. With transport captured and the inner final speech call suppressed, the outer transaction queued only ="replacementx, "=. Both the prefix and suffix disappeared. This isolates corruption during list construction from any transport or cancellation policy.
- Recommendation :: Assemble lists in a private temporary buffer, or use the same scoped scratch-buffer allocator as ordinary speech. Preserve text properties, grouping, and punctuation behavior. This is a small local repair; it does not require changing the public speech API.
- Regression coverage :: Extend [[file:test/emacsvox-tts-tests.el::1733][the existing nested-speech regression]] with a pronunciation callback that invokes =tts-speak-list=. Assert the complete outer text and the separate inner utterance. Cover nonlocal exit from the callback and preservation of relevant voice properties.

** [Medium] Unanswered control requests have no general terminal lifetime

- Confidence :: Confirmed lifecycle defect when a live worker stops replying.
- Location :: [[file:lisp/omnivox-voices.el::374][omnivox-voices.el:374]], [[file:lisp/omnivox-voices.el::410][omnivox-voices.el:410]], and [[file:lisp/omnivox-voices.el::2726][omnivox-voices.el:2726]]. Process exit and explicit retirement are at [[file:lisp/tts-speak.el::1144][tts-speak.el:1144]] and [[file:lisp/tts-speak.el::1239][tts-speak.el:1239]].
- Trigger :: A control request is written successfully, but the backend never replies. Repeated inventory refreshes each register another request. Generic requests do not receive a deadline, admission limit, or process-retirement completion.
- Impact :: The live process retains an increasing pending table. Inventory remains stale without a terminal failure for the request. Callers such as [[file:lisp/omnivox-voices.el::2748][engine recovery probes]] can wait indefinitely for their callback. Retiring a process leaves these entries on the retained process object; this is not evidence of a permanent leak after that object becomes collectible.
- Evidence :: A private pipe process advertised inventory support while its writer was stubbed to accept without replying. One hundred calls to =omnivox-refresh-voice-inventory= left 100 pending entries. Explicit retirement still left 100 entries while the process object was retained. Generic removal occurs on send failure or response delivery. Some higher-level operations already manage their own deadlines and remove their own IDs, including palette application, previews, parameters, and synchronous library requests; those protections do not cover every caller.
- Recommendation :: Give generic requests a bounded, process-owned lifetime. Coalesce concurrent inventory refreshes, expire unanswered requests, and retire outstanding callbacks once on process exit. Define a consistent failure result and discard late responses. Coordinate existing caller-specific timers before introducing general cleanup, to avoid duplicate completion.
- Regression coverage :: Keep a backend live but silent; verify bounded pending state and timeout reporting. Test process exit, a response arriving at the deadline, late replies after retirement, and independent main and notification request tables.

* Maintainability Improvements

** Centralize control-request lifetime without merging speech ownership

- Relevant code :: [[file:lisp/omnivox-voices.el::374][generic control requests]], [[file:lisp/omnivox-preview.el::321][preview request cleanup]], [[file:lisp/omnivox-parameters.el::110][parameter request cleanup]], and [[file:lisp/omnivox-library.el::405][library request cleanup]].
- Concrete benefit :: One implementation can enforce timeout, terminal completion, and stale-response rules. Today callers independently remove IDs and manage timers, making omissions like the control-request finding easier to introduce.
- Suggested change :: Introduce a small internal request record owned by its process, with one terminal transition. Migrate existing control callers incrementally. Keep operation-specific behavior in those callers and retain separate main and notification ownership.
- Likely scope :: Moderate, across the control helper and its callers. Establish callback error semantics and regression coverage first. This does not justify replacing the speech transport or merging the two processes.

** Make temporary text ownership explicit at speech preparation boundaries

- Relevant code :: [[file:lisp/tts-speak.el::1731][pronunciation iteration]], [[file:lisp/tts-speak.el::4178][transaction scratch allocation]], and [[file:lisp/tts-speak.el::4263][list assembly]].
- Concrete benefit :: Small helpers with explicit input, output, and buffer ownership make reentrancy and progress rules easier to test. They reduce dependence on the current scratch buffer and dynamically bound preparation state.
- Suggested change :: Start with private list assembly and a progress-safe pronunciation iterator. Share scratch allocation only where buffer reuse is measurably useful. Preserve source properties and the existing frozen voice plans.
- Likely scope :: Small to moderate. Fix the two observed defects first, then extract only the common lifetime rules demonstrated by those fixes. A wholesale split of =tts-speak.el= would add review cost without itself proving better behavior.

* Architecture Assessment

** Speech path traced

1. Interactive reading enters through functions such as [[file:lisp/emacsvox-speak.el::1287][emacsvox-speak-line]] and [[file:lisp/emacsvox-speak.el::915][emacsvox-speak-region]]. Source extraction and [[file:lisp/emacsvox-aural-source.el::235][submission context capture]] preserve source facts, visibility, lane, and delivery intent.
2. [[file:lisp/emacsvox-aural-submission.el::411][Submission preparation]] transforms content, captures facts and context, and builds concrete plans. [[file:lisp/emacsvox-aural-voice-runtime.el::54][Voice resolution snapshots]] and [[file:lisp/emacsvox-aural-voice-runtime.el::174][runtime snapshots]] separate the accepted palette and voice choices from subsequent edits. Pronunciation and text cleanup feed the TTS transaction.
3. The aural transport records ordered or replaceable delivery and builds structured timelines. [[file:lisp/emacsvox-aural-transport.el::1905][Timeline framing]] and [[file:lisp/tts-queue-state.el::512][typed queue writes]] carry the prepared submission to its owning process. [[file:lisp/tts-speak.el::680][Dispatch packet writing]] connects transport submission to tracked lifecycle state.
4. [[file:lisp/emacsvox-aural-submission.el::401][Lane selection]] binds notification submissions to the notification process. [[file:lisp/tts-speak.el::4351][Notification process selection]] provides the documented degraded fallback when that process is unavailable.
5. Omnivox parses input, validates transactions, and admits work through [[file:../omnivox/omnivox-cli/src/work_queue.rs::110][bounded atomic admission]]. The [[file:../omnivox/omnivox-cli/src/server.rs::1215][synthesis worker]] resolves routes, prepares chunks, and invokes native engines or helpers.
6. The pipeline submits buffered or progressive PCM to playback. Generation checks suppress obsolete work. [[file:../omnivox/omnivox-cli/src/routing.rs::1267][Progressive fallback handling]] refuses a cross-engine replay after output has been committed. [[file:../omnivox/omnivox-cli/src/server.rs::1194][Playback ticket completion]] distinguishes cancellation from completed playback.
7. Emacs consumes status and marker lines through [[file:lisp/tts-speak.el::1016][bounded line assembly]]. [[file:lisp/tts-speak.el::615][Deferred callback delivery]] and process retirement keep callback execution separate from protocol parsing and dispose of tracked speech ownership.

** State, lifecycle, and cancellation

Submission copies, immutable voice decisions, process generations, and explicit
dispatch ownership provide useful boundaries. The ordinary nested-speech path
already allocates separate scratch buffers. The list path bypasses that rule.
Generic control callbacks likewise have weaker ownership than speech dispatches.
These are local inconsistencies, not evidence that all global or dynamic state
needs replacement.

The main and notification processes have separate queues and cancellation
domains. Navigation interrupting ordered main speech is intentional under
[[file:docs/adr/0009-foreground-and-notification-speech-lanes.org::82][ADR 0009]].
Concurrent notification speech and degraded fallback onto the main process are
also documented policy. No additional lane-isolation defect was established.

Startup distinguishes capability negotiation from acknowledged routing readiness
under [[file:docs/adr/0007-routing-ready-startup-checkpoint.org::24][ADR 0007]].
Retirement cancels pending speech and tracked callbacks, with cleanup errors
recorded independently. [[file:lisp/omnivox-remote.el::165][Remote heartbeat and retry handling]]
uses bounded liveness checks and reconnect backoff; the policy in
[[file:docs/adr/0010-remote-workstation-speech.org::9][ADR 0010]] excludes replay of
old speech. No separate reconnect defect was demonstrated in the inspected paths.

The helper finding exposes an important distinction: rejecting stale playback is
not enough if cancellation itself cannot return. The isolation wrapper calls
the underlying engine's Stop directly, so it does not contain that helper defect.

** Correction: Windows cancellation already has an isolation boundary

The initial review missed [[file:../omnivox/omnivox-cli/src/engine.rs::73][the WinRT wrapper installed by the server]].
Although [[file:../omnivox/omnivox-tts/src/windows.rs::470][WinRT Stop itself is a no-op]],
[[file:../omnivox/omnivox-cli/src/engine_execution.rs::313][the wrapper observes cancellation]],
discards stale results, and releases the synthesis caller while retaining the
native task. It limits outstanding tasks per engine and across the process.
If the old task still occupies its engine, [[file:../omnivox/omnivox-cli/src/engine_execution.rs::214][bounded admission]]
returns an unavailable result so routing can select a fallback.

The claimed indefinite blockage of the shared synthesis worker is therefore not
supported by the complete server path. The finding is withdrawn; no WinRT code
change is proposed. [[file:../omnivox/omnivox-cli/src/engine_execution.rs::1163][The existing isolation regression]]
checks cancellation, discarded stale output, fallback availability, and later
reuse. It passed in the implementation follow-up. Native Windows and audible
acceptance remain coverage gaps, not an established correctness defect.

** Protocol, error handling, and observability

Structured envelopes avoid relying on raw speech text as executable protocol
syntax. The inspected framing and parsing paths include line limits, multipart
limits, identity checks, and Unicode-aware source positions. Existing tests
exercise split output, malformed data, write reentrancy, admission rejection, and
stale completion. No additional framing or Unicode defect was established.
The helper write failure concerns progress through a valid frame, not escaping.

Atomic queue admission preserves previously accepted work when a new request is
rejected. Playback tickets and progressive commitment rules give meaningful
completion and fallback semantics. These areas appeared sound in the reviewed
source and focused tests.

Session, process-generation, submission, and dispatch identifiers make the aural
and Omnivox logs useful for correlation. Bounded log excerpts showed completion
and cancellation reporting, but were not a reproduction of a reported audible
failure. A process being live, or playback being marked complete, does not prove
that the intended text was heard. Preserve those distinctions in diagnostics.

and resident session reported an older Omnivox version, so no 1.16.0 runtime
behavior was inferred from those processes. No launcher pin, live configuration,
loaded Lisp, process, hook, timer, buffer, or draft was changed for diagnosis.

The shared path was traced through source extraction, preparation, voice
resolution, admission, synthesis, playback, and completion. Not every optional
mode integration or vendor helper implementation was audited line by line.
Proprietary synthesis runtimes and Windows operating-system implementation code
were unavailable for inspection. macOS and native Linux device behavior were not
tested. Large frames were exercised in the helper reproduction and existing
protocol tests, not against every production engine.

The original helper blocking failure was reproduced with buffered output;
the follow-up also tests progressive dispatch. The withdrawn WinRT finding
does not justify a native engine change. The control probe demonstrates pending
state accumulation, not a measured long-running memory profile. Temporary probe
files and logs may disappear when =/tmp= is cleaned; the triggering conditions
and observed results are recorded here.

No additional defect was established in atomic admission, lane separation,
structured framing, or prevention of replay after progressive output commitment.
Passing tests and these source conclusions do not prove that a user heard the
intended utterance in a live session.
