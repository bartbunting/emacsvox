4.6 Building Omnivox For WSL2 ¶

Use this advanced route when maintaining the reproducible Emacsvox Windows bundle or its optional engine integrations. Ordinary WSL2 users should use the pre-built release in Install An Omnivox Windows Release Under WSL2. This target builds from source and currently produces an x86-64 Windows runtime.

Before running it, install or configure all of the following:

  • A WSL2 distribution with Windows interoperation enabled. Both powershell.exe and wslpath must run directly from the WSL shell, and the Windows user’s LocalAppData directory must be writable.
  • A working Docker client and daemon with Linux/AMD64 container support. The current WSL user must be able to run docker without adding sudo because the Make target invokes it directly. Docker Desktop with WSL integration is one way to provide this, but it is not the only possible Docker setup.
  • Windows .NET Framework 4.7.2 or newer. This means the Windows-only “.NET Framework”, not merely a modern dotnet SDK. Visual Studio is not required.
  • In WSL, git, GNU make, curl, unzip, sha256sum, and the normal GNU shell utilities supplied by a standard distribution. The build also uses commands such as awk, cmp, find, readlink, sed, sort, and xargs.
  • Network access for the first Docker image build, Rust dependency download, and two checksum-pinned NuGet packages. Later builds reuse the local Docker, Cargo, and .NET package caches.
  • Emacsvox and Omnivox Git checkouts. By default they must be sibling directories named emacsvox and omnivox, although maintainers can set OMNIVOX_DIR to an alternate Omnivox checkout. The Omnivox checkout must be at the exact source commit recorded for the checksum-pinned Piper companion in servers/omnivox-release/toolchain.lock when using the clean release target. The preparation target rejects a different revision instead of combining unmatched native components. The development target described below accepts current source by omitting Piper. Both checkouts need enough free space for the Docker image, native and cross-compiled build products, and caches.

You do not need to install Rust, MinGW, CMake, Clang, libclang, eSpeak NG, Roslyn, Visual Studio, or the .NET reference assemblies in WSL. The target pins or builds those inside its controlled toolchain. Eloquence and DECtalk runtimes and the RHVoice runtime and voice data are optional and are not needed for the normal Windows WinRT voice.

The quickest prerequisite check is: 

cd /path/to/emacsvox
make verify-windows-omnivox-toolchain

This is more than a presence check: on its first run it downloads the pinned .NET compiler packages, builds the pinned Docker image, and verifies the exact Rust, MinGW, libclang, Roslyn, and .NET Framework versions. A failure names the missing host command or unsupported framework before the full Omnivox build is attempted.

Clone Omnivox beside Emacsvox as shown in the source-build section. Then, from a clean Emacsvox checkout whose sibling Omnivox checkout also has no tracked changes, run: 

cd /path/to/emacsvox
make windows-omnivox

This is the reproducible release path. It builds and verifies a pinned Windows-GNU executable and stages a content-addressed runtime beneath servers/omnivox-bin. Once the Piper lock identifies an Omnivox revision that contains these integrations, the payload includes the matching, checksum-pinned Piper companion, the RHVoice helper without an RHVoice runtime, the Flite helper with its compiled CMU US SLT voice, and the RuTTS helper with its built-in male and female Russian voices. It contains no Piper model and no RuLex component. It also copies the runnable payload to a Windows-local directory so native voice and eSpeak data discovery do not pay the WSL filesystem cost. Optional Eloquence, DECtalk, and RHVoice runtimes are not downloaded by this target or required for normal WinRT speech.

The build does not report success on file checks alone. Its final live gate starts the exact Windows-local runtime, discovers Flite’s SLT voice and both RuTTS voices, and requires each helper to synthesize a non-empty WAV. Repeat that gate without rebuilding by running make verify-windows-omnivox-live.

To register Piper, review a model and its model card, keep its adjacent .onnx.json or .json configuration with it, and supply an absolute path while staging: 

OMNIVOX_PIPER_MODEL=/absolute/path/to/voice.onnx make windows-omnivox

The target copies the model and configuration into a separate, content-addressed directory below Windows LocalAppData and records their hashes without bundling them into the runtime. Omitting OMNIVOX_PIPER_MODEL installs the companion but leaves Piper unregistered. After a configured build, start a fresh speech process and confirm that the physical voice is present: 

./servers/omnivox --engine piper --list-voices

In Emacsvox, restart both speech processes or restart Emacs, then press C-e d e. That command lists the engines reported by the live process, so Piper appears only after the newly staged server has started and successfully loaded its model and helper.

Maintainers testing tracked changes should use the development route in Integration Maintenance rather than weakening the clean-release guard: 

OMNIVOX_RHVOICE_LIBRARY=/mnt/c/path/to/RHVoice.dll \
  OMNIVOX_RHVOICE_DATA=/mnt/c/path/to/RHVoice/data \
  make windows-omnivox-dev
./servers/omnivox --engine flite --list-voices
./servers/omnivox --engine rutts --list-voices

This route builds current Omnivox source, stages the RHVoice helper, Flite with its SLT voice, and RuTTS 6.3.3 with its built-in male and female Russian voices, and deliberately omits the older pinned Piper companion. RuTTS needs no separate installation; RuLex is not included. RHVoice appears only after installing a compatible Windows RHVoice.dll plus language and voice data. When its library and data variables are supplied to the development target, staging validates them and records Windows path pointers beside that local runtime; the launcher restores them for later fresh Emacsvox processes. Also supply OMNIVOX_RHVOICE_CONFIG when the installation has a separate configuration directory. The library, data, and configuration remain external and are not copied into the Omnivox payload. Installation and validation instructions are in Omnivox’s checkout under docs/RHVOICE.md and docs/RUTTS.md. Restart both speech processes or Emacs after restaging or changing those inputs, then use C-e d e to inspect the engines reported by the new process.
