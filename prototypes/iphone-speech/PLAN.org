The goal is one foreground iPhone app. With an external
keyboard connected to the phone, you edit files in your existing WSL
Emacs, use the minibuffer and work in a running
Codex conversation. The phone speaks its own frame locally, including
Emacsvox navigation, tones, earcons and permission announcements.

The Expo Go baseline is on the local Emacsvox branch =prototype/iphone-speech=.
The native experiment builds on it on =prototype/iphone-native-audio=. Make reusable Rust changes on a separate Omnivox
feature branch when the audio experiment calls for them. Use a named test
Emacs server until phone and desktop routing pass together. Record a date,
revision and short result under each milestone when its acceptance test passes.
Use a fixed sample for listening tests and keep spoken text out of routine logs.

The earlier local branches named above are stages of this checkout. Emacsvox
revisions in the build notes point to the corresponding commits in this
history. The private signed builds predate the removal of local setup details.

* Delivery plan

Slices 1 through 3 use Expo Go and a named test server in WSL. Slice 4
is the first physical-device build that needs Apple Developer Program
membership. Start that build on hosted macOS from WSL. Keep the normal
desktop profile available throughout the trials.

** NEXT 1. Attach the phone to an existing Emacs

Use the Expo keyboard relay to run =emacsclient -t= against the test
server whose graphical frame already shows an Agent Shell conversation.
Start an unsent draft on the PC and continue it on the phone. Pass when
disconnect closes just the phone frame, the PC still shows the edited
draft, and reconnect opens the same conversation.

The [[file:README.org::*Continue a PC draft on the phone][shared-frame trial]]
is ready on =prototype/iphone-ssh=. The WSL check uses a real graphical
Emacs, a rendered Agent Shell sample and terminal input over the receiver
socket. Both frames showed the same buffer and the PC retained the edited
draft and its original Emacs process after the phone frame closed.
The physical check is to continue that draft from the iPhone and reopen it.

** NEXT 2. Route speech to the frame that requested it

In the test server, give the PC and phone separate speech destinations
and queues. Capture the destination when the command runs and carry it
through deferred output. Retire the association when the phone frame
closes. Pass when both frames display the same buffer and alternating
navigation and Stop affect only the device that issued each command.
Verify this before attaching to the everyday Emacs server.

On 22 November 2026 the [[file:README.org::*Route each frame to its own speaker][routed trial]] passed with an Xvfb desktop frame
and a real terminal frame. Alternating Control+n and Stop affected the
expected speech process. The same test passed over SwiftNIO SSH to a
disposable existing Emacs. Listen on the PC and iPhone together to finish
this slice.

** NEXT 3. Deliver replies and permission requests across reconnects

Route asynchronous events to the frame subscribed to the conversation.
Keep permission identity and urgency through playback. During rapid
navigation, hear the request finish, review it and answer it. Explicit
Stop silences both phone lanes. On reconnect, announce a still-pending
request once from current Emacs state. Resolved requests and old audio
stay silent. Check the policy against the
[[file:../../docs/adr/0009-foreground-and-notification-speech-lanes.org][main and notification lane rules]].

WSL tests cover a delayed Agent Shell update after focus moves,
permission identity, reconnect and resolution, and an Emacs Stop
acknowledgement. Expo Go uses protected permission playback on its
single synthesizer. The native receiver has an independent notification
synthesizer. Hearing a permission finish during navigation and reviewing
and answering one on the phone are still open.

** NEXT 4. Put SSH and an accessible terminal in the signed app

Test SSH authentication,
host-key verification, interactive terminal allocation and resize against
the isolated server. Try SwiftNIO SSH and SwiftTerm in the signed app.
Keep the SSH key in the iOS Keychain. Run =emacsclient -t -s SERVER= and
keep terminal input and local speech available in the same foreground app.

The [[file:README.org::*Exercise the SSH transport in WSL][WSL SSH test]] on =prototype/iphone-ssh= uses the Swift transport against
a temporary loopback OpenSSH server. On 22 November 2026 it attached to
an existing Agent Shell sample, dispatched the destination line through
Emacsvox, resized the Emacs frame, saved UTF-8 input and reattached to
the same buffer. The current phone app pins the SSH host key, uses a device-only
Keychain identity and presents a SwiftTerm terminal. A hosted simulator build
compiled and packaged these components. On 22 November 2026,
hosted macOS produced the Ad Hoc device build of =438705434=. WSL verified
its distribution signer, signed arm64 executable and registered iPhone.
The [[file:README.org::*Start the signed app against the test server][device trial]] covers physical SSH, keyboard input and VoiceOver focus.

On 23 November the installed signed app spoke “Cobalt lighthouse” and
“Amber orchard” for two external-keyboard moves over SSH. A second voice
echoed a typed letter even with Emacs character and word echo disabled.
The second device trial routes the previously tested keyboard field through
the same native SSH session. WSL also verified reconnect to the last edit
buffer and point while a permission remained pending.

Pass when the app verifies the host, attaches its terminal to the chosen
server and supports the keyboard workflows below. Use VoiceOver to move
to Stop Speech, return to the terminal and resume navigation.

** NEXT 5. Prove native audio with Eloquence on the phone

Build a small Swift audio module in the same Expo app. Ask iOS for Reed's
speech samples, start playback as samples arrive, and mix one generated
tone and one preloaded earcon. On Stop, clear scheduled audio immediately
and discard later callbacks for the cancelled utterance. Use the existing
relay and PC keyboard so this experiment changes only the phone audio path.

Use the signed app from slice 4. Start with “Test iPhone Voice”, then
activate “Use native mixer” and “Test mixed audio”. The device build
includes the JavaScript and both playback modes. [[https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer/write%28_%3Atobuffercallback%3A%29][Apple speech buffers]].

Compare keypress to audible cue, keypress to first word, and Stop to
silence for direct speech and the mixer. Use one recording clock for the
key and the audible result. For each output route, record first use,
typical and slow repeated moves, and any stale speech or cues heard during
rapid replacement. Label internal callback timings separately.
Use direct Expo Go speech on the same output route as the baseline.
With VoiceOver active, the mixer should cut off the old line, start the new
one and respond to Stop at least as promptly. Cancelled audio must stay
silent. If Reed's samples arrive too late, keep direct speech and separate
cues usable while investigating.

The [[file:README.org::*Native mixer experiment][native mixer experiment]] includes direct and mixed playback, cancellation,
a fixed tone and the Accent recording. On 22 November 2026 the
hosted simulator build of =dd21276ef= succeeded. The downloaded iOS
Simulator app contained the compiled Swift mixer. All 14 WSL receiver and
relay tests passed. Eloquence sample delivery and acoustic timing on
speaker and headphones still need a physical check.

A hosted simulator build of =838ad97f5= also packaged the separate
permission synthesizer, cancellable generated tones, SwiftTerm and SSH.
The inclusion of these components was checked in the downloaded app.

On the first signed build, a single 480 ms Emacs tone sounded broken in
about six places. Both audio modes gave the same impression. WSL counted
one tone and one dispatch. The revised player renders that cue in one
23,040-frame buffer. The [[file:README.org::*Check the second device build][phone checks]] cover audible continuity, the extra
typing voice, interruption, pending permissions and lock recovery.

* Verified prototype baseline

** Hear Emacs navigation on the iPhone

On 22 November 2026, the phone spoke a selected line in a rendered Agent
Shell sample over Tailscale. The receiver at =6c4d0ec72= prefers Eloquence
Reed at 1.5 times normal speed. Ten automated receiver and relay tests passed.
A graphical Emacs test also verified the two real =C-n= commands, replies,
characters, permission output and Stop. The [[file:README.org::*Listen from the PC keyboard][listening setup]] is the baseline.

** Compare interruption and an earcon in Expo Go

1. With the PC keyboard and VoiceOver on, press =C-n= halfway through a
   long line. Stop a long reply on the phone during a network stall.
   Disconnect, move twice in Emacs, reconnect and move once more. Listen
   for a prompt cutoff, silence on reconnect and just the new line.
2. Open Agent Shell's compose editor in the isolated profile to trigger
   the Accent =open-object= cue. Forward the cue selected by Emacsvox and
   preload its recording on the phone. Check the trigger and cue order in
   WSL. Listen for the cue once at the same action on desktop and phone.
   Check that the next navigation command still interrupts. [[https://docs.expo.dev/versions/v58.0.0/sdk/audio/][Expo Audio]].
3. Record the voice, rate, output route, and how the cue and interruption
   felt on the phone speaker and your usual headphones. Use this comparison
   to set the latency target for the native experiment.

On 22 November 2026, with receiver =e532818dd= in Expo Go, a second =C-n=
promptly cut off the old line on the iPhone. Opening the compose editor
played the Accent Open Object sound and spoke “Compose prompt”. Stop Speech
silenced a long phrase straight away during an eight-second relay pause.
Two moves while disconnected stayed silent on reconnect. The next =C-n=
spoke its line. All 13 WSL tests passed, and a fresh graphical Emacs
sent the configured cue before the compose announcement.

On headphones, Eloquence at 1.5 times normal speed had a small,
acceptable delay. The built-in iPhone speaker felt a little quicker.
These are listening impressions. Keypress-to-sound timing and the
source of the delay have yet to be measured.

** Edit from the iPhone external keyboard

The [[file:README.org::*Try the external keyboard in Expo Go][Expo Go keyboard test]]
connects the phone field to a separate terminal Emacs over the private relay.
WSL checks cover two response lines, speech interruption, UTF-8 file
editing, buffer switching and reconnect. On 22 November 2026, the first
listening trial with the keyboard connected to the iPhone indicated that
the two =C-n= presses worked in an Agent Shell response. Typing and
saving worked on the phone with no audible duplicate echo. On the
external keyboard, =Alt+x= opened the command prompt and =Alt+f= moved
by word. Dired worked and Tab completed filenames in Shell mode.
At the =M-x= prompt, Tab completed =forward-cha= to =forward-char= and
Emacsvox announced the completion.
