16.3.1 Source checkout and byte-code lifecycle ¶

Use the Emacs selected by the ignored repository-local local.mk. When Emacs 30.2 or newer is not the system emacs, set its absolute path there: 

EMACS=/path/to/emacs-31/bin/emacs

Run make check-emacs before diagnosing compilation. After an ordinary Lisp edit, use the incremental build: 

make bytecode

After switching branches, pulling changes, or changing a macro or public interface, use: 

make bytecode-rebuild

That target removes ignored generated .elc files and recompiles them with the selected Emacs; it does not clean or discard source changes. make bytecode-check is the non-mutating preflight for startup or deployment. It reports missing, stale, orphaned, or wrong-Emacs byte-code.

Each make config fully regenerates ‘lisp/emacsvox-loaddefs.el’ from the current sources, including edited autoloads, new modules, and deleted modules. The build targets make bytecode, make bytecode-rebuild, make emacsvox, and make all run configuration before compiling; make compat-test runs it before testing. The portable command emacs -Q --batch -l etc/configure-emacsvox.el uses the same full regeneration. Saving a source file or starting Emacs does not regenerate autoloads. Neither make bytecode-check nor make docs-release-check does so. Regenerating the index alone does not force all modules to be recompiled.

Tests deliberately prefer source and therefore do not prove that the byte-code used by a live profile is current. Verify rebuilt byte-code in a fresh Emacs rather than relying on a file reload when compiled dependants may already be resident.

During development, load the changing setup source explicitly: 

(load-file "/path/to/emacsvox/lisp/emacsvox-setup.el")

The setup entry point warns and prefers source when newer Lisp would otherwise be hidden by stale local byte-code. In a stable checkout with current .elc files, (load-library "emacsvox-setup") may be used. Do not use load-library as the first load after editing the source tree: Emacs can select an old emacsvox-setup.elc before the newer source checker runs.

  1. Background startup ownership and failure recovery

    emacsvox starts two named background tasks: core-advice loads core command feedback and package-preparation registers optional package adapters. The private task registry retains each thread, state, start/end times, and original error for the Emacs session. Repeated startup reuses these records, including completed and failed tasks, instead of starting duplicate background work. Other startup effects, including speech-server initialization, still run when emacsvox is called again; this is not a general-purpose retry command.

    Registration completion is separate from adapter loading. An already-loaded package triggers its adapter immediately; another package gets a deferred load callback. Each package/adapter pair is registered once. Both load paths record failures without aborting later registrations. Failed or completed adapters are not automatically retried on another package load. User quit is recorded and still propagates. Source fallback from the setup guard is preserved in both background tasks and deferred callbacks.

    M-x emacsvox-startup-status speaks a summary and selects a Help report with task durations and original adapter errors. Calling emacsvox-startup-status from Lisp returns the summary without speech or a window. Failures also issue a warning and attempt a notification in interactive Emacs; retained records remain available if either feedback path fails. Successful completion adds no new unconditional announcement. The protocol and routing checkpoints defined in the startup ADRs retain their separate meanings; task completion does not declare the speech server ready, or establish that every adapter has loaded.

    Correct the reported cause and verify in a fresh session, rebuilding changed Lisp first. A failed adapter can leave partial advice or hooks: error isolation does not roll those effects back. Do not clear private ownership tables as a retry mechanism, since deferred callbacks can still refer to their records. Retain error details, selected Emacs version, and phase durations when debugging. Background scheduling is preserved; these records do not guarantee that core advice finishes before the first input command, and batch timings do not measure interactive startup latency.

    The focused tests exercise real deferred loads, failure isolation, task reuse, source fallback, and spoken status with speech intercepted. Check source with the selected Emacs using ‘test/emacsvox-startup-tests.el’. For fresh compiled parity, first run make bytecode-check, then set ‘EMACSVOX_STARTUP_TEST_LOAD=compiled’ when loading the same test file in a new batch Emacs. This selects ‘emacsvox.elc’ explicitly; it does not make every test dependency compiled. Audible diagnosis and real startup latency still need an isolated interactive session.

  2. Supported Emacs versions

    The Lisp runtime and all platform routes support Emacs 30.2 and newer. Run make compat-test for the core compatibility contracts without installing third-party packages. CI builds all maintained modules and runs this gate on Emacs 30.2 and 31.1. The full make test suite additionally requires the optional integration packages, including lua-mode on Emacs 30.

    The separate core speech CI job runs make core-test, make trace-test, and make compiled-aural-test on both versions with a private home directory. It covers speech, voice configuration, transport, Voice Workbench, startup, and golden speech traces without optional Emacs packages. It requires GNU Make, Git, a POSIX shell, and Tcl (tclsh); missing prerequisites fail before the core tests run. The fresh CI checkout exercises source, followed by an isolated compiled Aural check. Optional integration suites remain outside this job.

    The separate integration CI job runs Agent Shell, Notmuch, and EAT tests on both versions with a private home directory and six reviewed dependency snapshots. make test-deps verifies the archive hashes in ‘test/integration-dependencies.json’ and stages sources and autoloads under ignored ‘.test-deps/’; it never changes personal packages. make integration-test verifies that prepared tree before loading it and fails on missing dependencies or skipped tests. Pin updates require upstream review, new archive hashes, and fresh preparation for both Emacs versions. These source tests capture speech events and exercise disposable EAT subprocesses; they do not replace listening tests or compiled integration checks. See ‘test/README.org’ for preparation checks, directory overrides, recovery, and coverage boundaries.

    Keep each Emacs version’s build in a separate checkout; never reuse .elc files across versions. All platforms, including native Windows x64, use this minimum. The documentation toolchain retains its independent pin.

  3. Native Windows builds

    Use a separate checkout on a Windows drive. The native installer regenerates autoloads and all modules from the ‘lisp/Makefile’ inventory with the selected Windows Emacs. Its launcher verifies that byte-code in a fresh process. Do not share generated byte-code with a WSL checkout using another Emacs.

    Run the native installer checks from that Windows checkout: 

    .\test\emacsvox-windows-install-tests.ps1 -Emacs "C:\path\to\emacs.exe"
.\bin\emacsvox-install.ps1 -Role Desktop -Check
.\bin\emacsvox-install.ps1 -Role Desktop
.\bin\emacsvox.ps1 -Check

    The PowerShell tests use temporary fixtures and an existing native Emacs. They check doctor behavior, explicit selections, incomplete installations, platform rejection, checksums, archive paths, argument handling, and atomic configuration replacement. ‘test/emacsvox-native-bytecode-tests.el’ compares the native inventory with GNU Make and checks dependency order and byte-code preflight failures. Keep the WSL x64/ARM64 and remote installer tests passing.

    Actual acquisition acceptance must start with a private toolchain and the pinned archives, not a reused developer runtime. Keep MSYS2 package versions, compiler/configure/build/install logs, and ‘emacsvox-build.json’ with the installed Emacs. The installation logs also include ‘native-install-provenance.json’ with Lisp source hashes and selected pins. MSYS2 packages are signed rolling inputs; these records do not claim a frozen or bit-identical compiler environment. Verify fresh graphical startup, acknowledged routing, and tracked completion on both speech lanes with a PATH that contains neither WSL nor MSYS2 tools. Human listening remains a separate acceptance step. Native Windows x64 is supported; remote workstation speech remains preview, as recorded in ADR 0014.

  4. Remote preview validation

    Keep remote installer fixtures separate from connected acceptance. In the Omnivox checkout, run make dev followed by make remote-test; set OMNIVOX_REMOTE_TEST_SLOW=1 to cover heartbeat expiry. Set OMNIVOX_REMOTE_TEST_EMACS to the selected Emacs and OMNIVOX_REMOTE_TEST_EMACSVOX to the matching Emacsvox checkout for client acceptance. The Omnivox docs/REMOTE.md guide records Windows relay tests, real-device options, and retained evidence. Null-output tests do not establish audible playback or acceptance through a separate SSH host. Remote access remains preview independently of native Windows desktop support.

16.3.2 Debian package builds ¶

make deb builds a local development package in dist/ using Python 3, dpkg-deb, Git and the selected Emacs. It stages runtime sources and generates autoloads in a private directory, preserving checkout byte-code and personal configuration. The deb has architecture all, an Emacs 30.2 dependency (including terminal and graphical alternatives), and an Omnivox recommendation. It loads source and does not install emacsen-common hooks or compile on install. The ownership and release boundaries are recorded in ADR 0013.

make deb-test checks the actual archive, reproducibility, source startup, remote diagnosis, dependency metadata and refusal of an unprepared release. CI additionally installs, reinstalls and purges the package in a disposable Ubuntu 26.04 container using test/debian-install-smoke.sh. It uploads the development deb and checksum as CI artifacts, without publishing a release.

After preparing the checked source archive using the release procedure below, make release-deb produces dist/emacsvox_VERSION-1_all.deb and its checksum. The script itself verifies the existing clean-source artifact gate before and after packaging. Local versions instead contain +git with the source commit and source hash, and revision -0local1. The included BUILD-INFO.json records the exact source identity and autoload Emacs version. Neither package target creates a tag, uploads release assets, adds an apt repository or changes the manual release publication approval boundary.

After a maintainer publishes a stable GitHub release, the Release Debian package workflow checks out its exact annotated tag and downloads the source archive, checksum and provenance from that release. It checks the source identity, installs from the archive, builds the release deb, and tests install, startup, reinstall and removal in Ubuntu 26.04 before attaching the deb and checksum. Build jobs have read-only repository access; only the attachment job can write release assets. A rerun accepts identical existing assets and refuses to replace different files. CI does not create tags or releases.

This workflow uses Emacs 30.2 for autoload generation; its recorded toolchain can differ from a locally prepared package. Let CI attach the release deb instead of uploading a differently built local package with the same name.

16.3.3 Emacsvox release staging and publication ¶

The repository-level VERSION file is the canonical stable release identifier. Calendar-versioning policy, including delayed patches and backports, is recorded in ADR 0002. When advancing a release, update VERSION, the literal package header in lisp/emacsvox.el, and the current heading in etc/NEWS together, then run: 

make version-check

Between releases, etc/NEWS uses the Emacsvox Unreleased heading, so changes can be recorded before deciding whether the next publication is a patch or a new feature-release series. After publishing, preserve those notes verbatim as etc/NEWS-VERSION and start a new unreleased file. Ordinary version-check accepts that state; release-check, release-tag, and release-publish require the current NEWS heading to match VERSION exactly.

Prepare an artifact only from a separate clean, committed worktree. Build fresh byte-code and run the guarded artifact target: 

make bytecode-rebuild
make release-artifact

release-artifact runs the complete test and documentation gates before creating dist/emacsvox-YYYY.MONTH.PATCH.tar.bz2, its SHA-256 checksum, and a provenance record naming the checked source commit. For a patch-zero feature release, the series must match the current month. A corrective or backport release retains its original non-future series as required by ADR 0002. The source archive includes the maintained utils/ tools needed by the installers, launchers and build. Before recording checked provenance, the artifact target extracts the actual archive into a temporary directory and runs the remote-only installer with the selected Emacs in a private home. It checks fresh compiled startup, the offline manual and the remote helper’s credential validation without opening a workstation connection or playing speech. make source-archive-check repeats this check on an existing archive; make source-archive-test checks export contents and rejection of missing helpers, local configuration and byte-code. CI runs both checks before a release as well. On native Windows, run test/emacsvox-source-archive-tests.ps1 -Archive PATH -Emacs PATH to check the actual archive’s installer doctor, complete native compilation and fresh byte-code validation in a temporary Windows directory.

Inspect the archive, checksum, and provenance before proceeding.

Stop after artifact inspection unless fresh explicit permission names the release to be tagged and published. Preparing an artifact, committing or pushing a branch, publishing documentation, or receiving a general instruction to continue is not permission to create or push a release tag. Once that separate authorization has been given, the guarded commands are: 

make release-tag
make release-publish

release-tag validates the artifact against the still-clean HEAD and creates a local annotated, unsigned tag; it does not push the tag. The unsigned-tag policy and its trust boundary are recorded in ADR 0006. release-publish repeats the artifact and source-commit validation, pushes only that exact tag, and creates the GitHub release in the repository identified by RELEASE_REMOTE. This explicit selection prevents the GitHub CLI from choosing an upstream remote when releasing from a fork. No release target pushes master or the documentation branch. Use make release-check alone when a non-mutating preflight is wanted without creating an artifact.

16.3.4 Future Aural contract decisions ¶

The completed Aural implementation diary is preserved under archive/emacsvox/migrations/ rather than serving as current instructions. Three questions from that diary remain deliberately undecided and require an explicit architecture decision before implementation:

  • whether a critical alert may be completely suppressed or must retain an alternative presentation;
  • which deterministic ordering policy would apply before minor-mode selectors can participate in the presentation cascade; and
  • whether a new presentation occasion belongs to the core semantic contract or to a module-owned extension.

Do not infer answers from the archived proposals. Current behavior is defined by the Aural implementation, its generated reference, and accepted ADRs.

16.3.5 Voice-style metadata ownership ¶

The private emacsvox-aural--voice-style-fields table in ‘lisp/emacsvox-aural-rules.el’ owns accepted field names, groups, value types, and integer bounds. The existing public dimension lists and private accepted key list are derived from it; validation traverses the descriptors directly. Composition and provenance continue to consume the accepted-key inventory.

Keep the two established orders explicit. Validation checks preset, family, the four numeric ACSS fields, post-synthesis fields, relative rate, and legacy rate. The accepted-key inventory places relative and legacy rate before the post-synthesis fields. ACSS dimension order also determines positional legacy personality settings, and rich dimension order determines adjustment rows.

Every accepted field allows nil. Validation preserves the original plist, including duplicate fields, for which the first value is used. Field absence, explicit nil, and zero remain distinct during composition and persistence. Legacy :rate is accepted for loading saved data but is not applied as a new rate; nonzero legacy values produce the existing retuning degradation. The table supplies no implicit defaults and does not declare engine support.

An explicit nil over a preset is a compatibility behavior to characterize, not an authoring decision settled by the metadata table. For example, the current compiler clears the reported average-pitch value for (:preset base :average-pitch nil) while retaining the base voice command and emitting no pitch-reset command. The tests preserve this distinction. A future inheritance, omission, or reset policy needs a separate decision.

Compiler conversion, backend wire names, capability discovery, normalization, and delivery stay in their existing owners. When adding a field, update those consumers explicitly and test final serialized output or an explicit degradation. The common voice editor uses the shared field metadata for bounds and neutral values. It covers portable ACSS and optional rate and post-synthesis adjustments in the same retained draft.

Input grammar remains UI policy. In the common voice editor, blank numeric entry requests the adapter default; zero is explicit. Individual choice fields distinguish shared inheritance, custom values and explicit adapter defaults. Rule-editor input has its own scoped inheritance semantics; do not substitute one editor’s blank-input behavior for the other’s.

The common editor displays low-pass and high-pass as amounts from zero through nine, increasing with stronger filtering. Low-pass converts between amount and stored cutoff with ‘9 - value’; high-pass retains its numeric direction. Zero is labelled neutral. Stored cutoffs and adapter-default nil retain their meaning. Invalid boundary steps must fail before history, dirty state, refresh or audition changes.

Delivery preparation has the limited helper boundaries described below; asynchronous operation ownership remains a separate refactoring proposal.

The rule tests state field inventories, bounds, error precedence, and composition expectations independently of the metadata. Scheme tests cover saved rich palettes and explicit-nil rules; transport tests check distinct ACSS mappings, zero and omitted wire fields, effects, and preset behavior. make compiled-aural-test also runs these style contracts with the isolated compiled subsystem loaded, checking that the implementations stay in that build. The voice-style-ui tests exercise common-editor entry, inherited reset and draft retention in source and compiled runs. Editor tests also cover numeric bounds, explicit defaults, undo and comparison. They capture auditions and do not start audio. The connected saved-style regression edits a custom ‘bolden’, reads its saved data back, and compares common-editor and Workbench previews with the final normal-speech wire for ‘voice-bolden’. Workbench uses the compiler’s palette resolution and the shared effect normalizer: gain and pan level five must remain exactly neutral at 0.5. Preserve both this path and the independently specified Workbench scale cases when changing preview or palette lookup. Preserve final-write, timeout, reentrancy, and trace regressions when working on later delivery slices; metadata validation alone cannot establish process lifecycle or audible behavior.

16.3.6 Timeline preparation boundaries ¶

Two private helpers in ‘lisp/emacsvox-aural-transport.el’ make preparation inputs explicit. emacsvox-aural--timeline-effect-transition takes previous effects, normalized next effects, and a span ID, returning a directive and the next state. Replacement copies the saved state separately from the directive; retention preserves the previous state. The builder still owns the state accumulator, span numbering, and when normalization runs. Suppressed or empty content does not advance effects, while spoken boundary actions do.

emacsvox-aural--encode-timeline-delivery-fields takes a policy and replacement key. The existing emacsvox-aural--timeline-delivery-fields wrapper reads the dynamic submission variables at the end of timeline construction. Preserve that capture point: resource resolution earlier in construction can re-enter Lisp and change the submission state. The serializer preserves ordered defaults, key conversion, circular printing, diagnostics, and byte bounds.

The complete builder is not pure. Cue resolution through omnivox-remote-resource may perform I/O; relative-rate support comes from the live speech process. Those operations, action placement, dispatch registration, framing, fallback, and process writes retain their existing owners and sequence. Separating a complete delivery candidate from those effects requires further design and failure-path characterization.

The delivery-preparation tests in ‘test/emacsvox-aural-transport-tests.el’ check complete serialized timelines and final writes, semantic bindings, state ownership, policy inputs, and capture timing. The compiled Aural gate also runs these contracts and existing stop and send-failure regressions with the compiled implementation resident. Keep the full failure, reentrancy, and golden-trace suites as regression checks; captured writes establish protocol behavior, not audible playback.

16.3.7 Aural interface source ownership ¶

Ordinary-buffer entry captures a source buffer, a marker, and a guarded source line. Child interfaces and Help inherit that context through the inspection and shared UI helpers. Use emacsvox-aural-inspection-call-in-source for contextual commands so that moving the source cursor does not retarget an open interface. Re-entry from an ordinary buffer deliberately captures a new target. A dead or replaced source is reported rather than resolved through an unrelated recent-buffer fallback.

Current-item lookup may reuse a frozen history record only when the captured source identity, position, and modification tick still match. Source identity is a buffer-local, data-only token that distinguishes buffers sharing a name; history continues to retain no buffer objects or markers. Explicit historical selection remains valid after the source changes and is explained from its frozen plan. Prepared current-item rules carry a source guard checked before their saved or live rule layer changes.

Find rule editors by scope and target identity, not by a formatted buffer name. Buffer scopes belong to buffer objects, fragment scopes to fragment identifiers, and personal/session scopes each share one working editor. Reopening a dirty editor preserves its draft and source association.

16.3.8 Remote speech recovery ¶

Ordinary tts-initialize startup schedules the existing remote retry when main speech starts but a configured notification connection fails. The scheduler respects omnivox-remote-auto-reconnect, explicit suspension, and its single pending timer. The retry restores only missing lanes; it keeps a working main process and negotiates fresh configuration for the new notifier. omnivox-remote-disconnect cancels the timer and suspends even a retry callback that has already been dispatched. Local speech and disabled notification streams do not start remote recovery. Exercise these boundaries in test/omnivox-remote-tests.el with controlled connection failures and timers.

16.3.9 Omnivox voice configuration applies ¶

omnivox-apply-voice-configuration captures one generation and its definitions for the original speech processes. Applies may overlap. Each owns its request identifiers and retires only those callbacks when a process result becomes terminal. Acknowledging routing precedes logical registration; one aggregate reports applied, partial, or failed after all participating processes finish.

The timeout closes pending results as failed with phase timeout, cancels the timer, and releases the apply’s pending callbacks. A late acknowledgement cannot start another phase, update acknowledged configuration, or publish a second terminal result. A reply from a stopped or replaced process also cannot advance its old apply. Request ownership must remain correct when replies are dispatched while a send is still returning.

This closes client work; it cannot undo a change already sent to the server. The Workbench therefore describes a timeout as an unconfirmed server outcome and offers reapplication of the committed profile. No late-reply history is retained for expired applies. Keep request-table, late-reply, overlapping-apply, and replacement regressions in test/emacsvox-tts-tests.el and spoken timeout feedback coverage in test/emacsvox-aural-voice-workbench-tests.el.

16.3.10 Notmuch contracts ¶

The live module is registered as an optional package integration. Its stable extension points are the Hello, Search, Show, and Tree mode hooks; Search and Show mode maps; public interactive commands; and public Search/Show accessors. Advice is installed only when a target exists and is target-aware, so a nested or programmatic upstream call does not claim the outer user’s feedback.

The Show landing and visibility paths also read renderer metadata such as :headers-overlay, :message-visible, message extents, :notmuch-part, part-hidden state, and Notmuch part-button types. Missing optional metadata should reduce presentation detail rather than authorize an operation. Review these adapters whenever the Notmuch renderer changes.

Each user-owned asynchronous Search process carries its own completion state as a process property. The upstream sentinel renders first; Emacsvox then clears that property before delivering exactly one terminal result. The owning buffer and process status are authoritative. A killed owner remains silent, concurrent buffers cannot overwrite one another, and the global refresh-all path intentionally acquires no ownership.

Run make notmuch-test for the explicit source suite. After current byte-code exists, run make compiled-notmuch-test; it verifies the exact loaded emacsvox-notmuch.elc, compiler version, and the same focused selector, including real displayed-window reading for both advance paths.

16.3.11 Agent Shell contracts ¶

Use M-x emacsvox-agent-shell-enable to reinstall speech hooks after deliberately disabling them or while testing live integration changes.

  1. Internal ownership and renderer tests

    The main ‘lisp/emacsvox-agent-shell.el’ module requires the internal ‘lisp/emacsvox-agent-shell-render.el’ module. The renderer module depends only on Emacs libraries, with no reverse dependency on the main integration. Its private helper names and argument contracts remain available through the main module.

    OwnerResponsibilities
    Renderer moduleInterpret prompt faces and chat label strings, current and legacy status glyphs, semantic fragment provenance, decorative controls, answer body ranges, and legacy clipboard properties. Most helpers inspect supplied strings; fragment classification can also read the current buffer without changing it.
    Main integrationCapture buffer and overlay context; apply user customization, speech limits, and delivery; own response accumulation, event subscriptions, timers, callback generations, navigation, permission handling, activation, and cleanup.

    Renderer metadata supplies presentation and navigation facts; it does not authorize permission responses or establish lifecycle completion. Status label customization stays with the main integration. Keep compatibility interpretation together in the renderer module, and keep registration and speech side effects in the main owner.

    This is the first bounded separation of responsibilities. Event state, navigation and table commands, and permission handling still share the main module. Assess their private dependencies and lifecycle contracts before considering another extraction; a heading or a line count alone is not a reason to create a module.

    The independent ‘test/emacsvox-agent-shell-render-tests.el’ suite runs in the core and integration gates without needing optional packages of its own. It checks property-preserving copies, compatibility renderings, group provenance, answer selection, and a fresh module load without integration registrations. With the Emacs selected by ‘local.mk’, it can also run directly: 

    /path/to/emacs -Q --batch -L lisp \
  -l test/emacsvox-agent-shell-render-tests.el -f ert-run-tests-batch-and-exit

    Keep the existing Agent Shell integration tests alongside these smaller contracts. They exercise real pinned upstream renderers, speech delivery, enable/disable, and buffer-death cleanup. After preparing the pinned dependencies with make test-deps, run source and compiled parity checks: 

    make integration-test
make bytecode
make bytecode-check
EMACSVOX_AGENT_SHELL_TEST_LOAD=compiled make integration-test

    The environment setting selects the exact renderer and main integration .elc files in a fresh Emacs; other dependencies retain the runner’s source preference. Without it, both modules load explicitly from .el sources. The tests capture speech events and do not establish audible playback.

  2. Upstream contract layers

    The integration uses three deliberately different contract layers:

    The lifecycle subscription currently consumes init-started, init-finished, session-selected, session-restored, input-submitted, turn-complete, and error. Dedicated subscriptions consume permission-request, permission-response, and tool-call-update. Add new semantic behavior at the public event layer when Agent Shell exposes it; keep renderer and private fallbacks isolated and covered by compatibility tests.

    The lifecycle subscription also observes config-option-update. Configuration snapshots suppress initial inventory and duplicate callback/event confirmation. Late tool details are compared only for permissions established by a public permission-request event, and their snapshots are removed on resolution.

    Current Agent Shell omits rendered Codex rawOutput and textual diffs from tool-call-update. A narrow agent-shell--on-notification adapter joins that public event to the body rendered during the same call, matching both the owning buffer and qualified fragment ID.     Until upstream exposes public steering and push lifecycle events, small adapters wrap the structured steering request’s callbacks and the accepted session/push lifecycle. Push speech finishes before the original completion callback can drain the next queued prompt. Callback generations invalidate pending speech feedback on session change or integration cleanup; original transport callbacks still run. No transcript text is interpreted as a steering outcome or push completion.

    The queue adapter marks actual queue draining and lets input-submitted confirm that a queued prompt started. Prompt list editing and diff entry have native command feedback. New asynchronous tool, queue, steering, setting, and permission-detail submissions explicitly select the notification lane; list editing and diff entry remain foreground interactions. All new events and their outcome, count, or setting attributes are registered by the workflow semantic provider so Aural rules can customize their presentation.

16.3.12 Magit contracts ¶

Staging and selected synchronous operations collect Git outcomes at magit-process-finish, before Magit can raise an error. One interactive command owns the aggregate result across nested calls. A process that Magit starts and waits for contributes only to the collector attached when it was started; unrelated process callbacks cannot change that result. Uncollected asynchronous completions explicitly select the notification lane. Neither a command’s return value nor the absence of an Emacs error proves Git succeeded.

Magit’s positional highlight overlays must not become source personalities. The integration suppresses legacy overlay voice mirroring for those highlights and excludes their faces from source capture. It preserves text faces, deliberate personalities, and customized hash voices. Navigation still emits section facts; empty lines supply the core line-condition facts without a competing selection icon.

Regression tests use isolated repositories for real Git failures and real section trees for highlighting and visibility. Run the Magit tests from source, then again in a fresh Emacs with EMACSVOX_MAGIT_TEST_LOAD=compiled after bringing byte-code current. A live buffer created with the former highlight mirroring needs a Magit refresh to rebuild its source properties.

16.3.13 WSL2 Omnivox development staging ¶

The ordinary WSL2 user route is implemented by bin/emacsvox-wsl-install and pinned by etc/wsl-install.conf. Treat either file as release tooling. When advancing GNU Emacs or Omnivox, update the version, archive name, URL, and SHA-256 together; exercise x64 and ARM64 selection in the isolated installer tests; and perform one real installation of the newly pinned archive before updating the user manual. The installer must remain per-user, must not invoke sudo or edit shell startup files, and must preserve an explicit EMACS or local.mk selection rather than silently replacing it.

The installed Omnivox executable is recorded as an absolute WSL path in the data-only $XDG_CONFIG_HOME/emacsvox/omnivox-program file. Launcher selection is explicit OMNIVOX_PROGRAM, that per-user file, developer staging, then PATH. Keep the selection tests synchronized with this order. A configured but invalid path is a visible configuration error; silently falling through would hide a stale or damaged user installation.

This section describes the reproducible source-build path, not the ordinary pre-built WSL2 installation. The complete source-build prerequisite checklist is in Building Omnivox For WSL2. Dependency ownership is deliberately split across three boundaries:

make verify-windows-omnivox-toolchain prepares the cached Roslyn inputs, builds the Docker image, and validates this boundary before compilation. The full target then builds Omnivox’s two 32-bit helper sources deterministically, builds native Windows Omnivox plus its RHVoice, Flite, and RuTTS helpers in the container, and stages their licenses, provenance, and checksums. The clean target also builds Piper support and verifies that the pinned companion and main executable identify the same Omnivox source commit. A host Rust installation, MinGW installation, Visual Studio, .NET SDK, or system eSpeak installation is not an input to this release path. RHVoice’s native library, languages, and voices remain external user-supplied runtime inputs. Flite’s CMU US SLT voice is compiled into its checksum-locked helper. RuTTS’s built-in male and female Russian voices are compiled from the checksum-locked 6.3.3 source; RuLex is not included.

After staging, the static verifier rechecks manifests, provenance, the Windows-local copy, and all configured external inputs. The separate live verifier executes that exact Windows-local runtime, prewarms the bounded eSpeak voice cache tied to the verified content-addressed data, discovers the compiled Flite and RuTTS voices, and requires real WAV synthesis from both helpers. Use make verify-windows-omnivox-live to repeat only the executable smoke gate.

OMNIVOX_PIPER_MODEL is an optional staging input, not a release payload. When supplied, the target validates the adjacent configuration, copies both files into a content-addressed Windows-local model cache, records their hashes, and writes the Windows path used by the launcher. The recursive runtime manifest deliberately excludes model files. A different model therefore creates a distinct local build identity without changing the pinned companion. The public-domain engineering voice used in Omnivox CI is approved only for that bounded test purpose and is not a model-distribution default.

Maintainers testing tracked Emacsvox or Omnivox changes may use make windows-omnivox-dev. That target records both worktree-diff hashes and labels the result as a development build. It builds the RHVoice, Flite, and RuTTS companions but omits Piper, because the currently pinned Piper companion must not be mixed with later Omnivox source. It also rejects OMNIVOX_PIPER_MODEL. Advance the checked Piper companion and source commit together before these integrations enter the clean release path. See servers/omnivox-release/README.org for the pinned toolchain, licensing, provenance, and restaging contract.

To test Piper before that release-pin advance, commit and push a clean Omnivox revision and run its Piper Native Validation workflow. Download the omnivox-piper-windows-x64 artifact, which contains the companion archive and piper-sha256sums.txt, then stage it with a reviewed model: 

OMNIVOX_PIPER_DEVELOPMENT_ARCHIVE=/absolute/path/to/omnivox-1.10.0-piper-windows-x64.zip \
  OMNIVOX_PIPER_DEVELOPMENT_ARCHIVE_SHA256=64-character-sha256 \
  OMNIVOX_PIPER_MODEL=/absolute/path/to/voice.onnx \
  make windows-omnivox-piper-dev

This is a development-only bridge, not a release-pin bypass. It verifies the outer archive hash, rejects unsafe archive members and symbolic links, checks the companion’s internal manifest, and requires its source provenance to name the exact clean Omnivox HEAD and the Windows MSVC target. The staged runtime records the artifact hash and companion tree hash and labels the companion github-actions-native-development-build with version development-ci. The version-looking archive filename comes from Omnivox’s current package metadata and does not assert that post-tag code was released. The final live gate loads the separately cached model and requires Piper to enumerate that voice and synthesize a non-empty WAV.

The ordinary windows-omnivox-dev target remains appropriate for uncommitted Omnivox work because it rebuilds all included companions locally and omits Piper. The CI-artifact target deliberately rejects a dirty Omnivox checkout: commit and push the change, let the native workflow build that exact commit, then use its new artifact. Emacsvox itself may contain tracked changes; their diff hash remains part of the local runtime identity.

After one complete development runtime has been staged, use make windows-omnivox-main-dev for changes confined to the main Rust server or its main-only audio output. This guarded path uses the same pinned toolchain to rebuild only omnivox.exe, derives a new content-addressed runtime from the current hash-verified development payload, records the original complete build and reused manifest in provenance, hard-links the unchanged payload, and runs a focused live check of the new Windows main executable. It refuses reuse when helper, helper-protocol, dependency, toolchain, or companion inputs changed; in that case rerun make windows-omnivox-dev. Run make verify-windows-omnivox-runtime verify-windows-omnivox-live when a complete development audit is useful. The clean make windows-omnivox release path always rebuilds and verifies every payload and never uses incremental reuse.

The development target accepts OMNIVOX_RHVOICE_LIBRARY and OMNIVOX_RHVOICE_DATA together, plus an optional OMNIVOX_RHVOICE_CONFIG directory. It resolves WSL or Windows absolute paths, requires the C API DLL and the language/voice data layout, records content digests in provenance and machine-local Windows path pointers beside the selected runtime, and leaves all RHVoice files external. Those pointers let the launcher restore the variables for every fresh Emacsvox process. The runtime verifier rejects missing or changed external inputs. Omitting all three variables leaves RHVoice unconfigured without affecting Flite, RuTTS, or the other engines. RuTTS requires no external installation; the staged helper always provides its built-in male and female Russian voices without RuLex.

Do not bypass the Omnivox release target manually or clean either repository to make its release guard pass. Use make windows-omnivox only for the reproducible clean-release path documented in the user-facing WSL2 route.

16.3.14 Windows staging implementation and fixtures ¶

Make owns option and clean-source guards, toolchain verification, companion preparation, Docker compilation, and final runtime verification. Its windows-omnivox target passes prepared build outputs to the internal ‘servers/omnivox-release/stage-runtime.sh’ script. Use the guarded Make targets rather than invoking this script directly.

The script owns host-side payload staging: input checks, content hashes, optional voice-data caches, diagnostics, provenance, path files, and selection of the completed runtime. Make passes the Emacsvox root as EMACSVOX_STAGE_ROOT, the resolved OMNIVOX_* source/build/runtime paths and feature switches, and the two pinned Roslyn/reference-assembly archive hashes. The assignments at the call site and the script’s initial parameter checks define the complete internal input list. Optional user inputs retain their OMNIVOX_PIPER_MODEL, OMNIVOX_RHVOICE_*, and OMNIVOX_ECI_DLL environment variables. Main-only development staging remains separately owned by ‘stage-main-dev.sh’ with its existing reuse restrictions.

Run make windows-staging-test on a GNU/Linux host with Python 3, Git, Make, and the standard GNU file/checksum tools. The tests use private repositories, prepared payloads, runtime directories, and a simulated LocalAppData. Docker, Windows commands, and compiler/verifier boundaries are replaced by fixtures; Git guards, copying, hashing, provenance, and link activation execute normally. The suite is also included in make test and its own CI job. It exercises clean/development variants, optional companions and external voice inputs, paths containing spaces, corrupt caches, missing inputs, rejected main-only reuse, interruption, and activation failure.

Preserve the current activation sequence during maintenance. The script selects the staged runtime before Make’s final runtime and live checks; a failure in those final checks does not restore the previous selection. Interruption before activation can leave temporary files in a new version directory while preserving the current link. The fixture tests characterize these existing behaviors and successful retry. Changing cleanup or rollback requires a separate fix and acceptance decision. Fixture success does not establish native compiler reproducibility, real Windows path conversion, engine startup, or audible playback; run the existing native gates for that acceptance in an appropriate staging environment.

16.3.15 Aural experiments and guided changes ¶

Physical experiments use the common voice editor with an exact engine/voice selector, an immutable opening snapshot, a mutable working style and undo history. Navigation uses the ordinary voice. Experiments write no settings; Keep prepares a named-voice draft, including any reviewed row placement and adjustment scope. The destination still requires an explicit save.

The unified palette contract is recorded in ADR 0018. Every nonroot palette uses complete schema 3 entries and an explicit parent chain to ‘acss-default’. Palette definitions and immutable local-choice snapshots are saved through the common coordinator. Frozen proposals retain separate persistence and apply completion, and retry does not repeat a successful write. Save failures, acknowledged application and actual playback evidence remain separate. Workstation routing profiles contain global engine policy, not per-name routes.

Labelled comparisons use one controlled preview sequence, with identical sample text and separately configurable labels. Each sequence belongs to its speech lane. Stopping that lane cancels remaining entries and invalidates late callbacks; stopping foreground speech must not cancel notifications. Requested parameters and advertised capabilities are distinct from playback reports. Do not fabricate exact effective numeric values when the adapter reports only support, acceptance, or degradation.

Guided feedback changes use existing declarative rules and registered facts. The draft selects a component, matching criteria, and lifetime separately; preview dynamically overlays the intended layer without mutating live rules. Explicit buffer-rule snapshots in captured context must also be overlaid. Generated IDs remain stable for the matched component; new rules follow existing explicit order within the layer. Apply checks a Current-item source guard and refuses to overwrite another unfinished editor for the same scope. Historical selection chooses a frozen part when a transaction contains several runs. Original replay uses that part; proposed preview deliberately resolves it with current rules and the captured buffer context.

Shared Help and offline task nodes preserve the original source and exact return position. New interfaces should use the shared parent modes and add a task-node mapping to emacsvox-aural-ui-manual-nodes. Row action predicates should hide operations that cannot apply to that row; this includes editing built-in options and reordering items outside the active-order view.
