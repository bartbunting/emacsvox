16.3 Integration Maintenance ¶

This chapter collects source-level contracts that are deliberately omitted from the user task guides. Optional package APIs and renderers evolve, so recheck the upstream interfaces and keep compatibility behavior bounded when changing an integration.

  • Source checkout and byte-code lifecycle
  • Emacsvox release staging and publication
  • Future Aural contract decisions
  • Notmuch contracts
  • Agent Shell contracts
  • WSL2 Omnivox development staging

16.3.1 Source checkout and byte-code lifecycle ¶

Use the Emacs selected by the ignored repository-local local.mk. When Emacs 31 or newer is not the system emacs, set its absolute path there: 

EMACS=/path/to/emacs-31/bin/emacs

Run make check-emacs before diagnosing compilation. After an ordinary Lisp edit, use the incremental build: 

make bytecode

After switching branches, pulling changes, or changing a macro or public interface, use: 

make bytecode-rebuild

That target removes ignored generated .elc files and recompiles them with the selected Emacs; it does not clean or discard source changes. make bytecode-check is the non-mutating preflight for startup or deployment. It reports missing, stale, orphaned, or wrong-Emacs byte-code.

Tests deliberately prefer source and therefore do not prove that the byte-code used by a live profile is current. Verify rebuilt byte-code in a fresh Emacs rather than relying on a file reload when compiled dependants may already be resident.

During development, load the changing setup source explicitly: 

(load-file "/path/to/emacsvox/lisp/emacsvox-setup.el")

The setup entry point warns and prefers source when newer Lisp would otherwise be hidden by stale local byte-code. In a stable checkout with current .elc files, (load-library "emacsvox-setup") may be used. Do not use load-library as the first load after editing the source tree: Emacs can select an old emacsvox-setup.elc before the newer source checker runs.

16.3.2 Emacsvox release staging and publication ¶

The repository-level VERSION file is the canonical stable release identifier. Calendar-versioning policy, including delayed patches and backports, is recorded in ADR 0002. When advancing a release, update VERSION, the literal package header in lisp/emacsvox.el, and the current heading in etc/NEWS together, then run: 

make version-check

Between releases, etc/NEWS uses the Emacsvox Unreleased heading, so changes can be recorded before deciding whether the next publication is a patch or a new feature-release series. After publishing, preserve those notes verbatim as etc/NEWS-VERSION and start a new unreleased file. Ordinary version-check accepts that state; release-check, release-tag, and release-publish require the current NEWS heading to match VERSION exactly.

Prepare an artifact only from a separate clean, committed worktree. Build fresh byte-code and run the guarded artifact target: 

make bytecode-rebuild
make release-artifact

release-artifact runs the complete test and documentation gates before creating dist/emacsvox-YYYY.MONTH.PATCH.tar.bz2, its SHA-256 checksum, and a provenance record naming the checked source commit. For a patch-zero feature release, the series must match the current month. A corrective or backport release retains its original non-future series as required by ADR 0002. Inspect the archive, checksum, and provenance before proceeding.

Stop after artifact inspection unless fresh explicit permission names the release to be tagged and published. Preparing an artifact, committing or pushing a branch, publishing documentation, or receiving a general instruction to continue is not permission to create or push a release tag. Once that separate authorization has been given, the guarded commands are: 

make release-tag
make release-publish

release-tag validates the artifact against the still-clean HEAD and creates a local annotated, unsigned tag; it does not push the tag. The unsigned-tag policy and its trust boundary are recorded in ADR 0006. release-publish repeats the artifact and source-commit validation, pushes only that exact tag, and creates the GitHub release in the repository identified by RELEASE_REMOTE. This explicit selection prevents the GitHub CLI from choosing an upstream remote when releasing from a fork. No release target pushes master or the documentation branch. Use make release-check alone when a non-mutating preflight is wanted without creating an artifact.

16.3.3 Future Aural contract decisions ¶

The completed Aural implementation diary is preserved under archive/emacsvox/migrations/ rather than serving as current instructions. Three questions from that diary remain deliberately undecided and require an explicit architecture decision before implementation:

  • whether a critical alert may be completely suppressed or must retain an alternative presentation;
  • which deterministic ordering policy would apply before minor-mode selectors can participate in the presentation cascade; and
  • whether a new presentation occasion belongs to the core semantic contract or to a module-owned extension.

Do not infer answers from the archived proposals. Current behavior is defined by the Aural implementation, its generated reference, and accepted ADRs.

16.3.4 Notmuch contracts ¶

The live module is registered as an optional package integration. Its stable extension points are the Hello, Search, Show, and Tree mode hooks; Search and Show mode maps; public interactive commands; and public Search/Show accessors. Advice is installed only when a target exists and is target-aware, so a nested or programmatic upstream call does not claim the outer user’s feedback.

The Show landing and visibility paths also read renderer metadata such as :headers-overlay, :message-visible, message extents, :notmuch-part, part-hidden state, and Notmuch part-button types. Missing optional metadata should reduce presentation detail rather than authorize an operation. Review these adapters whenever the Notmuch renderer changes.

Each user-owned asynchronous Search process carries its own completion state as a process property. The upstream sentinel renders first; Emacsvox then clears that property before delivering exactly one terminal result. The owning buffer and process status are authoritative. A killed owner remains silent, concurrent buffers cannot overwrite one another, and the global refresh-all path intentionally acquires no ownership.

Run make notmuch-test for the explicit source suite. After current byte-code exists, run make compiled-notmuch-test; it verifies the exact loaded emacsvox-notmuch.elc, compiler version, and the same focused selector, including real displayed-window reading for both advance paths.

16.3.5 Agent Shell contracts ¶

Use M-x emacsvox-agent-shell-enable to reinstall speech hooks after deliberately disabling them or while testing live integration changes.

The integration uses three deliberately different contract layers:

LayerAgent Shell ownerEmacsvox rule
Public structured APIagent-shell-subscribe-to, agent-shell-unsubscribe, agent-shell-status, and agent-shell-shell-buffer; lifecycle, permission, and tool eventsPrimary authority for processing, completion, errors, permission urgency, and tool status. The public turn boundary triggers inspection of renderer-owned response sections. Event and response data is treated as untrusted content and bounded before automatic Aural submission.
Experimental renderer metadataagent-shell-ui-state, agent-shell-ui-section, rendered Markdown table/source properties, and renderer-owned facesFeature-detected navigation and presentation input. Renderer group provenance outranks provider-controlled IDs; prose and IDs cannot manufacture structured permission or lifecycle authority.
Private compatibility fallbackThe aggregate agent-shell--state, the legacy viewport ownership resolver, viewport position helpers, and legacy face, prompt, or ID inferenceKept in narrow adapter functions for older Agent Shell releases or incomplete renderers. A missing optional detail may reduce header or navigation richness but must not create a permission action or completed response.

The lifecycle subscription currently consumes init-started, init-finished, session-selected, session-restored, input-submitted, turn-complete, and error. Dedicated subscriptions consume permission-request, permission-response, and tool-call-update. Add new semantic behavior at the public event layer when Agent Shell exposes it; keep renderer and private fallbacks isolated and covered by compatibility tests.

16.3.6 WSL2 Omnivox development staging ¶

The ordinary WSL2 user route is implemented by bin/emacsvox-wsl-install and pinned by etc/wsl-install.conf. Treat either file as release tooling. When advancing GNU Emacs or Omnivox, update the version, archive name, URL, and SHA-256 together; exercise x64 and ARM64 selection in the isolated installer tests; and perform one real installation of the newly pinned archive before updating the user manual. The installer must remain per-user, must not invoke sudo or edit shell startup files, and must preserve an explicit EMACS or local.mk selection rather than silently replacing it.

The installed Omnivox executable is recorded as an absolute WSL path in the data-only $XDG_CONFIG_HOME/emacsvox/omnivox-program file. Launcher selection is explicit OMNIVOX_PROGRAM, that per-user file, developer staging, then PATH. Keep the selection tests synchronized with this order. A configured but invalid path is a visible configuration error; silently falling through would hide a stale or damaged user installation.

This section describes the reproducible source-build path, not the ordinary pre-built WSL2 installation. The complete source-build prerequisite checklist is in Building Omnivox For WSL2. Dependency ownership is deliberately split across three boundaries:

BoundarySupplied byDependencies
Windows and WSL hostMaintainerWSL interoperation, powershell.exe, wslpath, Windows .NET Framework 4.7.2 or newer, Docker with Linux/AMD64 support, Git, Make, download and checksum tools, standard GNU shell utilities, network access, and writable Windows LocalAppData.
Pinned release toolchainEmacsvox targetThe immutable Rust/Debian container, MinGW cross tools and runtime DLLs, CMake, Clang and libclang, eSpeak build dependencies, Roslyn, .NET 4.0 reference assemblies, and official Windows Piper companion. The exact versions, source commit, and downloaded-package hashes live in servers/omnivox-release/toolchain.lock.
Build sourceGit checkoutsThe current Emacsvox checkout and the Omnivox checkout selected by OMNIVOX_DIR, including Omnivox’s locked Rust dependencies and checksum-locked Flite and RuTTS source inputs.

make verify-windows-omnivox-toolchain prepares the cached Roslyn inputs, builds the Docker image, and validates this boundary before compilation. The full target then builds Omnivox’s two 32-bit helper sources deterministically, builds native Windows Omnivox plus its RHVoice, Flite, and RuTTS helpers in the container, and stages their licenses, provenance, and checksums. The clean target also builds Piper support and verifies that the pinned companion and main executable identify the same Omnivox source commit. A host Rust installation, MinGW installation, Visual Studio, .NET SDK, or system eSpeak installation is not an input to this release path. RHVoice’s native library, languages, and voices remain external user-supplied runtime inputs. Flite’s CMU US SLT voice is compiled into its checksum-locked helper. RuTTS’s built-in male and female Russian voices are compiled from the checksum-locked 6.3.3 source; RuLex is not included.

After staging, the static verifier rechecks manifests, provenance, the Windows-local copy, and all configured external inputs. The separate live verifier executes that exact Windows-local runtime, prewarms the bounded eSpeak voice cache tied to the verified content-addressed data, discovers the compiled Flite and RuTTS voices, and requires real WAV synthesis from both helpers. Use make verify-windows-omnivox-live to repeat only the executable smoke gate.

OMNIVOX_PIPER_MODEL is an optional staging input, not a release payload. When supplied, the target validates the adjacent configuration, copies both files into a content-addressed Windows-local model cache, records their hashes, and writes the Windows path used by the launcher. The recursive runtime manifest deliberately excludes model files. A different model therefore creates a distinct local build identity without changing the pinned companion. The public-domain engineering voice used in Omnivox CI is approved only for that bounded test purpose and is not a model-distribution default.

Maintainers testing tracked Emacsvox or Omnivox changes may use make windows-omnivox-dev. That target records both worktree-diff hashes and labels the result as a development build. It builds the RHVoice, Flite, and RuTTS companions but omits Piper, because the currently pinned Piper companion must not be mixed with later Omnivox source. It also rejects OMNIVOX_PIPER_MODEL. Advance the checked Piper companion and source commit together before these integrations enter the clean release path. See servers/omnivox-release/README.org for the pinned toolchain, licensing, provenance, and restaging contract.

The development target accepts OMNIVOX_RHVOICE_LIBRARY and OMNIVOX_RHVOICE_DATA together, plus an optional OMNIVOX_RHVOICE_CONFIG directory. It resolves WSL or Windows absolute paths, requires the C API DLL and the language/voice data layout, records content digests in provenance and machine-local Windows path pointers beside the selected runtime, and leaves all RHVoice files external. Those pointers let the launcher restore the variables for every fresh Emacsvox process. The runtime verifier rejects missing or changed external inputs. Omitting all three variables leaves RHVoice unconfigured without affecting Flite, RuTTS, or the other engines. RuTTS requires no external installation; the staged helper always provides its built-in male and female Russian voices without RuLex.

Do not bypass the Omnivox release target manually or clean either repository to make its release guard pass. Use make windows-omnivox only for the reproducible clean-release path documented in the user-facing WSL2 route.
